# 리플리케이션 환경에서 각 명령이 동작하는 방식

arcus EE는 **Map만 복제**한다. usearch 그래프는 복제되지 않는다. 그래서 switchover
직후 승격된 노드는 원소는 전부 가지고 있지만 그것을 검색할 그래프가 없다.

이 문서는 그 상황에서 `vcreate` / `vadd` / `vdel` / `vget` / `vsim`이 각각 어떻게
동작하는지를 명령 단위로 정리한 것이다. 설계 근거는
[스펙](superpowers/specs/2026-08-12-arcvector-replication-recovery-design.md)과
[내부구조](내부구조.md)에 있고, 여기서는 "그래서 무슨 일이 일어나는가"만 다룬다.

---

## 1. 상태값은 `owner` 하나다

판단에 쓰이는 값은 하나뿐이다.

| 값 | 어디서 읽나 | 무엇을 답하나 |
|---|---|---|
| **owner** | Map의 메타데이터 원소 (`AV META`) | 내 그래프가 이 Map을 설명하는가 |

`owner`는 그래프를 만들 때마다 새로 발급하는 64비트 토큰이다. 인덱스 객체도 자기가
어느 토큰으로 만들어졌는지 들고 있고, **모든 명령이 이 둘을 비교**한다.

`0`은 예약값이라 절대 발급되지 않는다. 그래서 별도 플래그 없이 "복구 중"을 표현할 수
있고, 비교 한 번으로 네 가지 경우가 갈린다.

| Map의 owner | 메모리의 owner | 의미 | 처리 |
|---|---|---|---|
| 토큰 | 같은 토큰 | 내가 만든 그래프가 맞다 | 그대로 서빙 |
| 토큰 | 다른 값 | 그 사이 다른 노드가 서빙했다 | 인수(take over) → 복구 |
| `0` | `0` | **내가** 지금 복구 중이다 | 조회는 `UNREADABLE`, 쓰기는 그대로 |
| `0` | 토큰 | 복구하던 노드가 사라졌다 | 인수 → 복구 |

세 번째 줄이 핵심이다. 복구를 진행 중인 노드만 메모리에도 `0`을 들고 있으므로,
"Map은 `0`인데 나는 토큰을 들고 있다"는 상황은 곧 **복구하던 주체가 없어졌다**는
뜻이고, 그때 남아 있는 그래프야말로 믿으면 안 되는 그래프다.

### 마스터/슬레이브를 따로 묻지 않는 이유

초기 구현에는 `get_stats("replication")`으로 role을 읽는 검사가 있었다. 지금은 없다.
`owner` 비교가 같은 질문에 이미 답하기 때문이다.

- **토큰이 어긋난 레플리카**는 인수를 시도하고, 인수는 **아무것도 버리기 전에** Map에
  stamp부터 한다. 그건 쓰기라서 엔진이 `ENGINE_REPL_SLAVE`로 거부한다. 그래프는
  그대로 남고, 클라이언트는 엔진이 준 에러로 여기가 레플리카임을 알게 된다.
- **토큰이 일치하는 레플리카**의 그래프는 실제로 그 Map을 정확히 설명한다. 마스터는
  원소를 쓰기 **전에** 토큰을 먼저 바꾸고, 둘 다 같은 Map 아이템에 대한 쓰기라
  복제가 그 순서대로 전달한다. 그래서 레플리카가 "일치하는 토큰 + 낡은 데이터"를
  동시에 들고 있을 수 없다. 답이 맞으므로 거부할 이유가 없다.

결과적으로 role 검사는 `owner`가 이미 주는 것을 명령마다 엔진 호출 한 번을 더 써서
사는 셈이었다. 대신 정책이 하나 바뀌었다. **레플리카는 토큰이 일치하는 동안 읽기를
답하고, 마스터가 인수하는 순간 답하지 않는다.**

## 2. 명령별 동작

각 명령을 **단계 순서**로 적고, 그 아래에 두 가지를 따로 논증한다.

- **중간에 끊기면** — 임의의 단계에서 프로세스가 죽거나 switchover가 나도 벡터가 사라지지 않는가
- **동시에 들어오면** — 같은 인덱스·같은 id에 여러 스레드가 붙어도 상태가 어긋나지 않는가

밑바닥에 깔린 규칙은 하나다. **Map이 원본이고 그래프는 캐시다.** 그래서 모든 쓰기는
Map을 먼저 바꾸고 그래프를 나중에 바꾼다. 그 순서 덕분에 "그래프에는 있는데 Map에는
없다"가 생기지 않고, 반대인 "Map에는 있는데 그래프에는 없다"만 생긴다. 후자는 검색에
잠깐 안 보일 뿐 복구가 고쳐준다.

### 공통 진입: `resolve`

모든 명령이 실제 작업 전에 통과한다.

```
1. get_elem(name, "AV META")            엔진 읽기 1회
     ├ 없음/디코딩 실패  → Damaged
     ├ 상위 버전         → Newer      → NOT_FOUND (손대지 않음)
     └ 정상              → (meta, layout)

2. Damaged이면
     getattr(name)으로 flags 확인
       ├ 우리 Map이 아님 → NOT_FOUND (손대지 않음)
       └ 우리 Map임      → drop_map + 레지스트리 제거 → NOT_FOUND

3. 레지스트리 조회
     ├ 있음  → 그 인덱스
     └ 없음  → getattr로 maxcount 확보 → 메타데이터로 빈 그래프 생성
               insert_or_get가 "내가 넣었는지"를 알려줌 (fresh)

4. fresh || meta.owner != 내 owner
     → 인수(take_over) 후 반환      ← 여기서 끝. 아래 5번은 건너뜀

5. 내가 복구 중이고 그래프가 다 채워졌다면
     → claim_refilled: 새 토큰 발급·기록, 복구 상태 해제
```

2단계의 판정이 **손상 판정 전부**다. 여기서 걸리지 않은 것은 모두 정상 메타데이터이므로,
이후 단계는 metric·HNSW 파라미터가 있다고 가정해도 된다.

3단계의 `fresh`가 왜 필요한지는 4번과 묶어서 봐야 한다. 여기서 만든 그래프는 **비어
있다.** Map이 뭐라고 적혀 있든 채워야 하므로 무조건 인수한다. 이게 없으면 복구가 실패해
레지스트리 항목만 사라진 상태(Map은 `0`)가 "누가 복구 중"으로 보여서 아무도 복구를 걸지
않는 교착이 된다.

---

### `vcreate` — 생성

```
1. max_element_bytes로 dim 상한 검사        (엔진에 물어봄, 쓰기 없음)
2. getattr(name)
     └ Map이 이미 있다 → resolve를 태우고 EXISTS   ← 절대 지우지 않는다
3. AnnIndex::new                             (메모리만)
4. create_map(name, maxcount+1, exptime)     ★ 첫 번째 쓰기
5. put_elem(name, META, owner=새 토큰)       ★ 두 번째 쓰기
6. 레지스트리 등록 → CREATED
```

**중간에 끊기면.** 위험 구간은 4와 5 사이 하나뿐이다. 여기서 죽으면 **빈 Map + 메타데이터
없음**이 남는다. 다음 `resolve`가 이걸 Damaged로 판정하고, flags가 우리 것이므로 Map을
지운다. 지워지는 건 원소가 하나도 없는 Map이라 **잃을 데이터가 없다**. 이 구간이 안전한
이유는 순서 때문이다 — 원소는 5번 이후에만 들어올 수 있으므로, 데이터가 있는 Map이
메타데이터 없이 존재하는 상태는 만들어지지 않는다.

3번이 4번보다 앞인 것도 같은 이유다. 그래프 생성은 metric·quant 조합이 맞지 않으면
실패하는데, 그 실패가 Map을 만든 뒤에 나면 위의 빈 Map 상태를 일부러 만드는 셈이 된다.

**동시에 들어오면.** 같은 이름으로 둘이 동시에 들어와도 `create_map`은 엔진의 아이템
생성이라 하나만 성공한다 — 실제로 확인하면 두 번째는 `EXISTS`로 거부된다.

```
$ printf 'mop create avdup 0 0 100\r\nmop create avdup 0 0 100\r\n' | nc 127.0.0.1 11311
CREATED
EXISTS
```

진 쪽은 4번에서 에러를 받고 끝나며 Map을 건드리지 않는다. 2번의 `getattr`과 4번 사이에
다른 노드가 Map을 만드는 경우도 같은 지점으로 수렴한다.

`MAXCOUNT n`은 Map을 **n+1**로 만든다(엔진 상한까지 clamp). 메타데이터가 한 칸을 쓰므로,
사용자가 요청한 n은 온전히 벡터 몫이 된다.

### `vadd` — 삽입

```
1. resolve                                   (복구 중이어도 통과)
2. ATTR JSON 검증, max_element_bytes 재검사   ← 런타임에 낮아졌을 수 있음
3. 오버플로 검사
     ann.key_of(id)가 없고 && ann.len() >= maxcount → OVERFLOWED
4. 양자화 + 원소 인코딩                       (메모리만)
5. put_elem(name, id, value)                 ★ Map 먼저 — upsert
     ├ Overflow  → OVERFLOWED
     ├ KeyGone   → 레지스트리 제거 + IndexEvicted
     └ ReplicaSlave → SERVER_ERROR …replica…
6. ann.add(id, quantized)                    그래프 나중
     a. ensure_capacity(live+1)              ← 락 밖. 필요하면 inner 쓰기락
     b. permit 획득                          ← usearch 스레드 컨텍스트 수 제한
     c. inner.read()  →  ids.write()         ← 항상 이 순서
     d. intern(id): 이미 있으면 index.remove(key) 후 add
7. STORED
```

**중간에 끊기면.** 5와 6 사이가 유일한 구간이고, 여기서 죽으면 **Map에는 있고 그래프에는
없다**. 벡터는 살아 있고 `vget`으로 읽히며, `vsim`에만 안 보인다. 다음 복구가 넣어준다.
순서가 반대였다면 검색에는 나오는데 실제 데이터가 없는 상태가 되고, 그건 복구로도 못
고친다(그래프가 원본이 아니므로).

**동시에 들어오면.**

- *같은 id에 두 `vadd`* — 5번은 엔진이 원소 단위로 직렬화하므로 둘 중 하나가 최종값이
  된다. 6번은 `inner.read()` + `ids.write()`를 **d단계 전체에 걸쳐 잡고** 있어서,
  remove-then-add 사이에 다른 스레드가 끼어들 수 없다. 그래서 그래프에도 하나만 남는다.
  다만 5번과 6번이 원자적이지는 않으므로, 두 `vadd`의 Map 최종값과 그래프 최종값이 서로
  다른 쓰기에서 올 수는 있다. 이건 마지막-쓰기-승 의미론의 한계이고, 다음 복구가 Map
  쪽으로 맞춘다.
- *`vadd`와 `vdel`이 같은 id에* — 6d와 `remove`가 같은 두 락을 같은 순서로 잡으므로 둘
  중 하나가 먼저 완료된다. 중간 상태는 관측되지 않는다.
- *`vadd`와 복구 스레드* — 복구는 `add_unless_known`을 쓴다. 이미 `intern`된 id는
  건너뛰므로 방금 들어온 새 벡터를 스냅샷의 옛 값으로 덮지 않는다.
- *`vadd`와 검색* — 6d의 remove-then-add 창 동안 검색이 그 벡터를 놓칠 수 있다. Map은
  그대로이므로 잃는 건 없고, 그 순간의 검색 결과에서만 빠진다.
- *용량 증설* — 6a가 락 밖인 이유는 `reserve`가 노드 배열을 재할당해 `inner` **쓰기**락이
  필요하기 때문이다. 삽입은 읽기락을 잡으므로, 안에서 증설하면 스스로를 막는다.

3번의 오버플로 검사가 `key_of`로 기존 여부를 먼저 보는 것도 의미가 있다. 기존 id의
갱신은 원소 수를 늘리지 않으므로 가득 찬 인덱스에서도 통과해야 한다.

---

### `vget` — 키 조회

```
1. resolve
2. 복구 중이면 UNREADABLE
3. get_elem(name, id) → 원소 디코딩 → ATTR 반환
```

그래프를 **한 번도 보지 않는다.** 그래서 이 경로는 항상 원본을 읽고, 복제가 방금 배달한
원소도 그대로 읽힌다. 동시성 관점에서 볼 게 없다 — 엔진의 원소 읽기 하나뿐이다.

복구 중에 막는 건 정확성 때문이 아니라 **일관성** 때문이다. `vget`만 답하고 `vsim`이
막히면 같은 노드에서 두 조회 경로가 다른 세계를 보여준다.

---

### `vsim` — 벡터 검색

```
1. resolve
2. 복구 중이면 UNREADABLE                     ← 반드시 필요
3. ann.search(query, k, accept)
     - permit 획득, inner.read()
     - accept(key): ids.read()로 id를 얻고 → get_elem으로 ATTR을 읽어 FILTER 평가
                    읽기 실패(사라짐)면 후보에서 제외
4. 히트마다 다시 get_elem으로 원소를 읽어 응답 구성
     - 여기서도 사라진 것은 건너뜀
5. 살아남은 것만 세어 QUERY 헤더에 개수를 적고 출력
```

**2번이 왜 반드시 필요한가.** usearch에는 "아직 준비 안 됨"이라는 상태가 없다. 절반만
채워진 그래프에 검색을 걸면 아무 불평 없이 그 절반에서 답을 만들어 준다. 그래서 거부는
이쪽에서 해야 한다.

**그래프와 Map이 어긋나도 결과는 어긋나지 않는다.** 3번과 4번이 후보마다 Map을 다시
읽고, 없으면 버린다. 그래서 `vadd`/`vdel`이 6번에서 실패해 남긴 유령 노드는 검색 결과에
나타나지 않는다. 개수를 5번에서 세는 것도 같은 이유다 — 헤더에 적힌 수와 실제 행 수가
어긋나지 않으려면 걸러낸 뒤에 세야 한다.

`accept`가 `id_of`에서 `Arc<str>`을 복제해 돌려받는 것도 동시성 때문이다. 술어는 이어서
엔진 호출을 하는데, 그 사이 `ids` 락을 붙들고 있으면 모든 쓰기가 검색 한 건에 묶인다.

---

### `vdel` — 삭제

```
1. resolve                                   (복구 중이어도 통과)
2. delete_elem(name, id)                     ★ Map 먼저
     ├ 성공        → existed = true
     ├ ElemGone/KeyGone → existed = false
     └ ReplicaSlave → SERVER_ERROR …replica…
3. ann.remove(id)                            그래프 나중
     - permit 획득
     - inner.read() → ids.write()            ← vadd와 같은 순서
     - 복구 중이면 forget_tombstoned (id를 기억), 아니면 forget
4. existed ? DELETED : NOT_FOUND
```

**중간에 끊기면.** 2와 3 사이에서 죽으면 그래프에 **유령 노드**가 남는다. 위에서 본 대로
`vsim`이 Map 재조회로 걸러내므로 결과에는 나오지 않고, 다음 복구가 정리한다. 반대 순서
였다면 그래프에서는 지워졌는데 Map에는 남아 `vget`으로는 읽히는 상태가 되고, 이건 복구가
오히려 그래프에 되살려 놓는다.

**복구와 겹치면.** 3번이 tombstone을 남기는 게 핵심이다. 복구 스레드는 `get_all`로 뜬
**한 시점의 스냅샷**을 들고 일하므로, 그 뒤에 삭제된 id는 스냅샷에 아직 남아 있다. 그냥
지우기만 하면 복구가 되살린다. tombstone은 `is_known`에 포함되므로 `add_unless_known`이
건너뛴다.

그리고 삭제와 복구의 삽입이 **`ids` 쓰기락을 "판단 + 실행" 전체에 걸쳐** 잡는다는 점이
중요하다. 쓰기락이므로 둘은 배타적이고, 판단과 실행이 쪼개지지 않으므로 `is_known`을
확인한 뒤 `intern` 하기 전에 삭제가 끼어드는 창이 없다.

배타성은 **`ids` 하나에서만** 나온다는 점을 짚어둘 필요가 있다. `inner`는 여기서 공유
읽기락이라 `add`와 `remove` 사이에 아무 직렬화도 만들지 않는다. usearch 호출이 `ids`
쓰기락 **안쪽**에 들어가 있어서, 결과적으로 그래프 변경까지 그 락의 순서를 따라갈 뿐이다.

```rust
// remove                                  // add_unless_known
let index = self.inner.read();             let index = self.inner.read();
let mut ids = self.ids.write();  // ←── 같은 락 ──→ let mut ids = self.ids.write();
let key = if rebuilding {                  if ids.is_known(id) { return Ok(false) }
    ids.forget_tombstoned(id)              let (key, _) = ids.intern(id);
} else { ids.forget(id) };
index.remove(key)?;                        self.typed_add(&index, key, vector)?;
// 여기까지 락을 쥔 채로                    // 여기까지 락을 쥔 채로
```

그래서 어느 쪽이 먼저 락을 잡든 결과가 정해진다.

| 먼저 잡는 쪽 | 벌어지는 일 | 최종 상태 |
|---|---|---|
| 삭제 | tombstone이 남고, 뒤따르는 삽입이 `is_known`에서 걸려 건너뜀 | 삭제됨 |
| 복구의 삽입 | 벡터가 들어가고, 뒤따르는 삭제가 그것을 지움 | 삭제됨 |

별도 자료구조에 삭제 집합을 두면 그 집합과 usearch 호출이 서로 다른 락 아래 놓여
판단과 실행 사이가 벌어진다. 그래서 그렇게 하지 않았다.

tombstone은 복구가 끝날 때 한 번에 비운다. 복구 중이 아니면 아예 기록하지 않으므로
평상시 메모리 비용은 0이다.

---

### `vdrop`, `vlist`

`vdrop`은 레지스트리에서 빼고 `drop_map`을 부른다. 복구 중에도 허용되며, 복구가 끝날 때
Map을 다시 읽어 확인하므로 사라진 인덱스에 대한 복구 결과는 그 시점에 폐기된다.

`vlist`는 메모리만 읽는다. 복구 중인 인덱스는 빠진다(아직 설명할 내용이 없다).

### 요약: 왜 데이터가 안 사라지는가

| 명령 | 첫 쓰기 | 두 번째 쓰기 | 사이에서 죽으면 남는 것 | 누가 고치나 |
|---|---|---|---|---|
| `vcreate` | `create_map` | 메타데이터 기록 | 빈 Map (원소 0개) | 다음 `resolve`가 손상으로 판정해 제거 |
| `vadd` | Map 원소 | 그래프 노드 | 검색에 안 보이는 벡터 | 다음 복구 |
| `vdel` | Map 원소 삭제 | 그래프 노드 삭제 | 그래프의 유령 노드 | `vsim`이 결과에서 제외, 다음 복구가 정리 |

세 경우 모두 **남는 쪽이 Map이고 잃는 쪽이 캐시**다. 이게 순서를 이렇게 고정한 이유이고,
복구가 항상 Map → 그래프 한 방향인 이유이기도 하다.

### 요약: 왜 상태가 안 어긋나는가

락은 두 개이고, 별개이며, 하는 일이 다르다.

| 락 | 무엇을 막나 | 어떻게 잡히나 |
|---|---|---|
| `inner: RwLock<Index>` | `reserve`(노드 배열 재할당) 대 나머지 전부 | add/remove/search는 **읽기**락 — 서로 안 막음 |
| `ids: RwLock<IdMap>` | id 매핑의 판단과 실행 | add/remove가 **쓰기**락, search가 노드당 짧게 읽기락 |

그래프 자체의 동시 변경은 usearch가 내부에서 처리한다. 그래서 `inner`는 동시성 장치가
아니라 **재할당 배제 장치**다. 바깥에서 usearch에 별도 락을 얹지 않은 것도 의도다 —
라이브러리가 이미 하는 일이라 한 번 더 잡으면 동시성만 깎인다.

Map 쪽은 엔진이 아이템/원소 단위로 직렬화하므로 이 두 락과 무관하다.

**순서 규칙은 정확성이 아니라 데드락 회피다.** 락을 잡는 곳은 `add`,
`add_unless_known`, `remove`, `search`, `clear` 다섯 군데뿐이고 전부 `inner` → `ids`
순서인데, 이건 검색 술어가 `inner.read()` 아래에서 `ids.read()`를 잡기 때문에 나머지를
거기 맞춘 것이다. 삽입 대 삭제의 경합을 막는 건 위에서 본 대로 `ids` 쓰기락 하나다.

**대가.** 모든 `add`/`remove`가 `ids` 쓰기락을 usearch 호출까지 쥐고 있으므로 **쓰기는
인덱스 전체에서 직렬화된다.** id가 서로 달라도 마찬가지다. 검색은 `ids.read()`를 노드당
짧게만 잡으므로 서로 막지 않고 쓰기와도 거의 겹치지 않는다. usearch가 내부적으로
지원하는 동시 삽입을 이 구조에서는 쓰지 못하는 셈인데, 그게 tombstone의 판단과 실행을
한 락 아래 붙여두는 값이다. 복구가 `reserve`를 미리 한 번에 잡아두는 것도 이 직렬화
구간을 짧게 유지하기 위해서다.

## 3. 복구가 실제로 도는 순서

```
워커 스레드   Map의 owner를 0으로 기록
              그래프와 id 맵을 비운다
              복구 큐에 이름을 넣는다
                 │
                 ▼
복구 스레드   메타데이터 읽기 (손상 판정)
              원소 수만큼 용량 미리 확보
              get_all → 원소마다 add_unless_known
              "다 채웠다" 표시만 하고 끝.  쓰기는 하지 않는다
                 │
                 ▼
워커 스레드   (다음 명령이 도착하면)
              Map을 다시 읽어 아직 0인지 확인
              새 토큰 발급 → 메타데이터에 기록 → 복구 플래그 해제
              이제부터 조회 가능
```

### 복구 스레드가 쓰기를 하지 않는 이유

커넥션이 없는 스레드에는 cookie가 없고, 엔진의 쓰기 경로는 그것을 역참조한다.
`do_check_master_switchover_done`이 `get_thread_index(cookie)`를 널 가드 없이
호출하기 때문에, 스위치오버 중인 마스터에서 detached 스레드가 쓰기를 하면 데몬이
죽는다. 그리고 스위치오버 중이라는 건 곧 복구가 돌고 있을 시점이다.

이건 가정이 아니라 실제로 겪은 일이다. 초기 구현에서 복구 스레드가 자기 완료 토큰을
직접 기록하게 했더니 `get_thread_index`에서 SIGSEGV로 데몬이 내려갔다.

읽기는 안전하다. `ACTION_BEFORE_READ`는 `ENABLE_MIGRATION` 없이는 비어 있고,
`rp_after_check`는 thread-local cookie가 널이면 즉시 반환하며, arcus 자신도 slave
switchover 검사를 cookie 없이 호출한다(로그에 "zk thread"로 찍힌다).

### 동시 쓰기와 스냅샷이 부딪히는 두 경우

| 순서 | 문제 | 처리 |
|---|---|---|
| 스냅샷 이후 `vadd` | 그래프엔 이미 새 벡터가 있는데 복구가 옛 값으로 덮어씀 | `add_unless_known` — id 맵이 이미 아는 id는 건너뜀 |
| 스냅샷 이후 `vdel` | 스냅샷에 남아 있어 되살아남 | tombstone — 복구가 끝날 때 정리 |

둘 다 `usearch/index.rs` 안에서, 모든 경로가 지키는 하나의 락 순서(`inner` → `ids`,
검색 술어와 같은 순서)로 처리된다. 레지스트리가 따로 맞춰줘야 하는 별도 자료구조를
두지 않았다.

### 그래프를 비우고 시작하는 이유

새 그래프를 옆에 만들어 두면 복구 중에도 계속 서빙할 수 있지만 메모리가 두 배가 된다.
usearch는 비어 있지 않은 인덱스 하나당 약 16.8 MB에서 시작하고 그 위에 벡터가 얹히므로,
1024차원 `i8` 벡터 100만 개면 대략 1 GB짜리를 두 벌 들고 있어야 한다. 이미 낡은 것으로
판명된 그래프에서 답을 주는 것보다 `UNREADABLE`이 정직하다.

## 4. 실패했을 때

| 상황 | 응답 | Map은? |
|---|---|---|
| 메타데이터 손상 (없음/매직 불일치/타입 불일치/JSON 파싱 실패) | `NOT_FOUND` | **삭제**, 로그에 크게 남김 |
| 모르는 **상위 버전** 메타데이터 | `NOT_FOUND` | 손대지 않음 |
| 그 외 복구 실패 (할당 실패, 디코딩 실패 등) | `SERVER_ERROR` | 손대지 않음 |
| 레플리카에서의 인수/쓰기 | `SERVER_ERROR this node is a replica…` (엔진이 준 것) | 손대지 않음 |
| 레플리카에서의 읽기, 토큰 일치 | 정상 응답 | — |

**지우는 실패는 손상 하나뿐이다.** flags가 우리 것이라고 말하는 Map인데 metric과 HNSW
파라미터가 없으면 다시는 인덱스가 될 수 없다. 남겨두면 이후 모든 명령이 성공할 수 없는
복구를 반복한다. 지우기 때문에 실패 backoff도 필요 없다 — 재시도할 대상 자체가 없다.

상위 버전은 손상이 아니라 **새 노드의 포맷**이고, 롤링 업그레이드에서 정상적으로
발생한다. 여기서 지우면 구 노드가 신 노드의 데이터를 파괴한다.

그 외 실패는 레지스트리 항목만 버린다. 다음 명령이 빈 그래프를 새로 만들고 무조건
인수하므로 복구가 다시 시작된다. (이 "무조건"이 없으면 Map은 `0`인데 레지스트리는
비어 있는 상태가 "누군가 복구 중"으로 보여서 아무도 복구를 걸지 않는 교착이 된다.)

## 5. 이 설계가 막는 시나리오

### switchover 두 번 (A→B→A)

A의 프로세스는 죽지 않았으므로 마스터 시절 그래프를 그대로 들고 있다. 그 사이 B의
쓰기는 **확장 모듈 아래쪽**인 복제 경로로 A의 Map에 도달했고, A는 그 사실을 통보받지
못한다. 그대로 두면 A는 자기 Map을 설명하지 못하는 그래프로 서빙을 재개한다.

증상은 두 조회 경로의 불일치로 나타난다.

```
Map 실제         VALUE 0 4        ← 원소 4개
vlist            count=3          ← 그래프는 3개라고 말함
vget  v4         VALUE v4         ← Map을 직접 읽으니 찾음
vsim  (v4 방향)  v3, v2, v1       ← 거리 0인 v4가 안 나옴
```

**마스터/슬레이브를 폴링해서는 절대 잡을 수 없다.** A→B→A는 전후 모두 `master`로 읽히므로 아무리
자주 샘플링해도 변화가 없다. 달라진 건 *그래프*이고, 그래서 표식은 그래프마다 다르고
양쪽 노드가 다 볼 수 있는 곳 — 즉 Map — 에 있어야 한다. 그게 `owner`다.

카운터가 아니라 토큰인 이유: 원소에는 CAS가 없다. 증가는 read-modify-write이고,
switchover 중 두 노드가 동시에 만들면 같은 숫자에 도달할 수 있다. 토큰은 서로 다르기만
하면 된다.

### 아무 일도 없었을 때는 조용하다

승격만 되고 아무 명령도 받지 못한 노드는 복구하지 않으므로 토큰을 건드리지 않는다.
그리고 아무것도 서빙하지 않은 노드는 아무것도 쓰지 않았다. 불변식은 이렇다.

> 토큰은 누군가 복구했을 때만 바뀌고, 복구는 서빙하려 할 때만 일어난다.
> 아무도 복구하지 않았다면 아무도 쓰지 않았다.

### 막지 못하는 것

`mop insert`처럼 ArcVector를 거치지 않고 인덱스 키에 벡터 원소를 직접 넣으면 데이터는
바뀌는데 토큰은 그대로다. 그런 원소는 `AV` 매직이 없어 다음 복구 때 디코딩에서 걸리지만,
그 전까지는 검색에 보이지 않는다. 이 구멍은 이 설계 이전부터 있었고 이 설계로 닫히지
않는다.

메타데이터 원소는 예외다. 필드명이 `AV META`라 공백이 들어 있고, ASCII 프로토콜은 공백이
든 필드를 표현할 방법이 없다 — `mop insert`의 필드는 명령행 토큰이고, `mop get`/`delete`는
공백으로 쪼갠 개수가 `numfields`와 맞아야 한다. 그래서 메타데이터를 직접 덮어써서 인덱스를
망가뜨릴 수는 없다. 전체 덤프(`mop get <key> 0 0`)로 보이기는 하므로 관측은 된다.

## 6. 비용

- owner 확인: 알려진 필드 하나를 `map_elem_get` 하는 것. 왕복 실측으로 `vget` 26 µs
  (이미 같은 종류의 읽기를 한 번 한다), `vsim` k=10 65 µs, `vadd` 73 µs. 가장 싼 명령
  기준으로도 왕복의 일부에 불과하고, 주기적으로 확인하는 대안은 그 차이를 "샘플링
  간격만큼 틀린 답을 하는 것"과 맞바꾼다.
- 복구 속도: 벡터 3,999개 기준 0.5초.
- 동기 마스터에서 쓰기 501건 모두 ack 이전에 응답(EWOULDBLOCK은 실패가 아니라 "썼으니
  아직 답하지 말라"는 뜻이다).

## 7. 레플리카에서의 읽기

role 검사를 없앤 결과로 생긴 동작이라 따로 적어둔다.

```
switchover 직후, 강등된 노드
  토큰 일치  →  vsim/vget 정상 응답      (그래프가 실제로 자기 Map을 설명함)

승격된 노드에서 vadd 한 번
  → 인수하며 새 토큰을 Map에 기록 → 복제로 강등 노드에도 전달

그 다음, 강등된 노드
  토큰 불일치 →  인수 시도 → stamp가 엔진에 거부됨 → SERVER_ERROR …replica…
```

즉 레플리카는 **자기 그래프가 최신임이 증명되는 동안만** 읽기를 답한다. 마스터가
ArcVector를 통해 뭔가 쓰는 순간 토큰이 움직이고, 그 뒤로는 답하지 않는다. 읽기 분산을
쓸 거라면 이 성질을 알고 써야 한다 — 가용성이 마스터의 쓰기 여부에 달려 있다.

`tests/replication.rs`의 `a_demoted_node_answers_until_the_new_master_takes_over`가
이 두 단계를 그대로 검증한다.

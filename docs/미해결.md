# 미해결 항목

알고 있으면서 지금 고치지 않은 것들. 각 항목에 **증상**, **왜 지금 안 고치는가**,
**고치려면 무엇이 필요한가**를 적는다. 해결하면 여기서 지우고 해당 문서로 옮긴다.

---

## 1. 벡터 쓰기가 슬레이브 ack를 기다리지 않는다

**증상.** 동기 모드 복제 마스터에서도 `vadd`·`vdel`의 응답이 슬레이브 ack보다 먼저
나간다. 즉 벡터 쓰기는 설정과 무관하게 **비동기 내구성**이다. 마스터가 ack 직전에 죽으면
클라이언트는 성공을 받았는데 슬레이브에는 없는 원소가 생긴다.

실측: 동기 마스터에서 `vadd` 501건 전부 ack 이전에 응답.

**왜 이렇게 되나.** 엔진은 제대로 신호를 준다. `rp_after_check`가 연산 성공 후 호출자를
대기자로 등록하고 `ENGINE_EWOULDBLOCK`을 돌려준다 — "일어나지 않았다"가 아니라 "아직
답하지 말라"는 뜻이다. 내장 명령은 그것을 받아 `c->ewouldblock`을 세우고, 워커가
`conn_parse_cmd` 끝에서 연결을 event loop에서 떼어낸 뒤 `notify_io_complete`를 기다린다.

확장에는 그 경로가 없다.

**조사한 것.** 재료 자체는 서버 API에 노출돼 있다. EE는 `MULTI_NOTIFY_IO_COMPLETE`를
켜두고(`types.h:51`), 그 방식은 `conn` 내부 필드가 아니라 카운터로 동작한다.

```c
void (*waitfor_io_complete)(const void *cookie);   /* current_io_wait += 1 */
void (*notify_io_complete)(const void *cookie, ENGINE_ERROR_CODE status);
```

그런데도 확장이 쓸 수 없는 이유가 둘이다.

**(a) 진입 조건이 여전히 `c->ewouldblock`이다.**

```c
/* memcached.c — conn_parse_cmd:14622, conn_nread:14729 둘 다 같은 모양 */
if (c->ewouldblock) {
    c->ewouldblock = false;
    if (should_io_blocked(c)) {   /* current_io_wait를 보는 유일한 곳 */
        return false;             /* blocked */
    }
}
```

확장이 `waitfor_io_complete`로 카운터를 올려도 저 `if`에 걸리지 않는다.
`process_extension_command`는 `execute`의 반환값으로 `ewouldblock`을 세우지 않는다 —
`false`면 연결 종료, `true`면 그대로 다음 상태로 간다.

> **경고.** 그래서 확장에서 `waitfor_io_complete`를 부르면 안 된다. 올린 카운터가 소비되지
> 않고 남아, 같은 연결에서 나중에 내장 명령이 `ewouldblock`을 세우면 오지 않을 notify를
> 기다리며 **연결이 영구히 멈춘다.** 고치는 게 아니라 망가뜨리는 쪽이다.

**(b) 재진입 지점이 없다.** 블록이 풀리면 상태 기계는 `conn_parse_cmd`로 돌아간다. 내장
명령은 `c->aiostat`을 보고 이어서 처리하지만, 확장 명령에는 "아까 그 명령을 마저 끝내라"는
진입점이 없어서 그 시점에 응답을 만들 방법이 없다.

`perform_callbacks` 쪽도 확인했으나 `ON_CONNECT` / `ON_DISCONNECT` / `ON_AUTH` /
`ON_SWITCH_CONN` / `ON_LOG_LEVEL`뿐이라 IO 완료와 무관하다.

**고치려면.** arcus 본체 패치가 필요하다. 가장 작은 변경은
`process_extension_command`에서 `execute` 반환 후 카운터를 보는 것이다.

```c
if (!cmd->execute(...)) {
    conn_set_state(c, conn_closing);
} else if (c->current_io_wait > 0) {
    c->ewouldblock = true;          /* 이 한 줄이 (a)를 푼다 */
}
```

(b)는 확장이 응답을 **미리 만들어 출력 버퍼에 넣고** 블록을 걸면 우회된다 — 연결이 깨어날
때 나가므로 "ack 전에는 안 보낸다"가 재진입 없이 성립한다. 다만 그러면 슬레이브가 거부해도
성공 응답이 나가므로, 결과를 반영하려면 확장용 재진입 콜백이 따로 있어야 한다.

**지금 하는 것.** 그냥 둔다. 비동기로라도 동작은 하고, 확장 쪽 우회는 전부 연결을 멈추게
만들 위험이 있다. 이 성질을 [내부구조.md §8](내부구조.md#8-ewouldblock은-실패가-아니라-기다려다)에
명시해 두었다.

## 2. `mop insert`로 인덱스 키를 직접 건드리면 그래프가 모른다

**증상.** ArcVector를 거치지 않고 인덱스 키에 벡터 원소를 넣거나 바꾸면 데이터는 바뀌는데
소유 토큰이 갱신되지 않는다. 그래프는 그 변화를 모르고, `vget`은 찾는데 `vsim`은 못 찾는
불일치가 생긴다.

**왜 지금 안 고치나.** 막으려면 엔진이 아이템 쓰기를 확장에 통지해야 하는데 그런 콜백이
없다. 이 설계 이전부터 있던 한계다.

원소 헤더의 `AV` 매직이 **일부** 도움이 된다. 다른 용도로 쓰던 Map과 키가 겹쳤다거나 하는
사고는 디코딩에서 걸린다. 다만 **고의는 못 막는다** — 매직과 버전을 맞춰서 넣으면 그대로
통과해 그래프에 들어간다. 애초에 막을 수도 없다. 그 키에 `mop insert`를 할 수 있는 주체는
`delete`로 Map을 통째로 지울 수도 있으니, 원소 헤더는 신뢰 경계가 아니다.

메타데이터 원소는 이 구멍에서 제외된다. 필드명 `AV META`의 공백 때문에 ASCII 프로토콜로는
만들 수도 지정할 수도 없다.

**고치려면.** 아이템 변경 콜백이 필요하다. 없으면 주기적 검증밖에 없는데, 그 비용이 이
구멍의 실제 위험보다 크다.

## 3. 레플리카의 읽기 가용성이 마스터의 쓰기에 종속된다

**증상.** 레플리카는 토큰이 일치하는 동안 조회를 답한다. 마스터에서 `vadd`가 한 번 일어나
인수가 발생하면 토큰이 바뀌고, 그 뒤로 레플리카의 읽기는 전부 `SERVER_ERROR`가 된다.
클라이언트 입장에서는 자기가 하지 않은 다른 노드의 쓰기 때문에 읽기가 죽는다.

**왜 이렇게 두나.** 정확성 문제가 아니라 정책의 귀결이다. 역할 검사를 없애면서 의도적으로
받아들인 성질이고, 대안(항상 거부)은 정확한 데이터를 거부하는 것이라 더 나쁘다고 판단했다.
[design-replication-recovery.md](design-replication-recovery.md) §4.1.

**고치려면.** 레플리카가 자기 그래프를 복제된 원소로부터 따라가게 해야 하는데, 그러려면
2번과 같은 통지가 필요하다.

## 4. 저장 형식에 버전이 없다

**증상.** 아이템 플래그는 `0x4156_0000`뿐이고 원소에도 버전이 없다. 저장 형식을 바꾸면 구
버전 빌드가 새 인덱스를 읽지 못하고, 손상으로 판정해 **Map을 지운다.** 롤링 업그레이드 중
switchover가 겹치면 인덱스가 소실된다(슬레이브인 동안은 엔진이 쓰기를 막지만, 마스터가 되면
지운다).

**왜 지금 안 두나.** 아직 배포된 적이 없다. 형식은 이 프로젝트에서 이미 여러 번 바뀌었고,
그때마다 기존 인덱스를 버리면 그만이었다.

**고치려면.** 형식을 바꾸기 **전에** 버전을 먼저 넣는 릴리스가 필요하다. 나중에 넣어도 그
넣는 변경 자체는 지켜지지 않는다 — 버전 없는 빌드를 소급해 고칠 수 없기 때문이다. 자리는
둘 중 하나다.

| | 판정 시점 | 비고 |
|---|---|---|
| 아이템 플래그 하위 절반 | `getattr`만으로, 원소 읽기 전 | 클라이언트가 `mop create`로 설정 가능 |
| `AV META` JSON의 키 | 그 원소를 읽은 뒤 | 프로토콜로 쓸 수 없어 위조 불가 |

## 5. 큰 `M`은 워커 스레드를 오래 붙든다

**증상.** `vcreate x 2 M 1000000` 같은 요청이 usearch의 그래프 할당에서 오래 걸린다.
실측으로 응답이 수 초 내에 오지 않았고, 그동안 그 워커 스레드가 묶인다. 서버는 죽지 않고
결국 완료되며, `M`이 훨씬 크면(`2^53`) usearch가 "failed to reserve memory"로 거부한다.

`vcreate`가 그래프를 Map보다 먼저 만들기 때문에 실패해도 빈 Map은 남지 않는다.

**왜 지금 안 고치나.** `M`·`EFC`·`EFS`에 상한을 두면 되는데, usearch가 실제로 받는
최댓값(`u32::MAX`)까지는 정상 동작하므로 어디서 잘라야 할지가 임의적이다. 그리고 이
파라미터를 크게 주는 것은 잘못된 사용이지 공격 경로로 보기는 어렵다 — 같은 클라이언트가
그냥 큰 인덱스를 여러 개 만들어도 된다.

**고치려면.** `parse_create`에서 세 값에 상한을 두고 `CLIENT_ERROR`로 답한다. 상한을 정할
근거가 필요하다.

## 6. 자동 테스트가 없는 경로

| 경로 | 왜 없나 |
|---|---|
| ABI 불일치 래치 | 일부러 어긋나게 빌드한 라이브러리가 필요해 통합 하네스로 만들 수 없다. 전역 래치라 단위 테스트에서 켜면 같은 프로세스의 다른 테스트를 오염시킨다. 손으로 검증했다 |
| `persistence` | 퍼시스턴스를 켠 EE 서버가 있어야 재시작 후 복구를 볼 수 있다. `data/`의 서버는 `ENABLE_PERSISTENCE`가 꺼져 있다 |
| 복구 꺼진 빌드(`cfg(not(recovery))`) | OSS 서버로 손으로 검증했다. 통합 스위트는 한 번에 한 조합만 돌므로, 두 조합을 다 도는 타깃을 만들어야 한다 |

**고치려면.** 앞의 둘은 별도 테스트 타깃과 전용 서버가 필요하다. 마지막 것은
`cargo test --features integration`을 피처 조합별로 두 번 도는 Makefile 타깃이면 된다.

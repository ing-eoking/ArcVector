# ArcVector 코드 리뷰 가이드

이 문서는 **코드를 옆에 두고 읽는 용도**다. 각 절이 실제 소스 조각 하나와 그 조각이 왜 그렇게
생겼는지, 그리고 **리뷰어가 무엇을 확인해야 하는지**를 짝지어 놓았다.

- 코드 블록은 전부 소스에서 줄 범위째로 뽑았다. 손으로 옮긴 것은 없다.
- **소스에 주석이 없다.** 전부 지웠으므로, 코드가 왜 그 모양인지는 이 문서와
  [내부구조.md](내부구조.md)에만 있다. 근거를 코드에서 찾지 말 것.
- 블록 위의 `파일:줄` 링크가 원본 위치다. **줄 번호는 아래 기준 커밋의 것**이고, 코드가 바뀌면
  밀린다. 내용이 어긋나 보이면 링크가 아니라 함수 이름으로 찾으면 된다.
- `☐`로 시작하는 줄이 확인 항목이다. 근거가 코드 안에 있는 것만 적었다.

> **이 파일은 생성물이다.** 고칠 것은 [코드리뷰.src.md](코드리뷰.src.md)이고, `@@경로:대상@@`
> 마커가 소스에서 그 조각을 그대로 끌어온다. 대상은 `fn 이름` · `struct 이름` ·

## 0. 먼저 알아야 할 여섯 가지

이 모듈의 거의 모든 코드가 아래 여섯 중 하나 때문에 그 모양이다. 리뷰 중 "왜 이렇게 복잡하지"
싶은 곳이 나오면 대개 여기로 돌아온다.

### I1. 인덱스 하나 = arcus Map 아이템 하나. 그래프는 캐시다

벡터 하나가 Map 원소 하나이고, usearch 그래프는 **언제든 Map에서 다시 만들 수 있어야 하는
사본**이다. 복제도 영속화도 Map만 따라간다. 그래서 모든 쓰기가 "엔진 먼저, 그래프 나중"이고,
그 반대는 없다.

### I2. usearch 키 = 그 원소의 주소. refcount가 그것을 지킨다

`key → id`가 조회가 아니라 **역참조**다. 원소가 자기 필드 바이트를 들고 있고 그게 id다.
주소가 계속 그 원소를 가리키려면 원소가 해제되면 안 되고, 그래서 그래프가 원소마다 refcount를
하나씩 든다.

읽는 도중에 그 refcount가 돌아가면 안 되는데, **검색은 락을 잡지 않는다.** 대신 해제를 미룬다 —
"이 삭제보다 먼저 시작한 조회가 전부 끝났다"가 반납 조건이다(§1.5).

### I3. 원소는 링크된 뒤로 불변이다

`FILTER` 술어가 **엔진 락 없이** 원소 바이트를 읽는다(I2 때문에 가능한 일이다). 그러니 링크된
원소를 제자리에서 고치면 읽는 도중에 바뀐다. 값이 바뀌는 것은 언제나 "새 원소를 링크하고 헌
것을 unlink"다. `vsetattr`이 `map_elem_update`를 안 쓰는 이유다.

### I4. 실패할 수 있는 일은 전부 `CLOG_MAP_ELEM_INSERT` 앞에

`do_map_elem_link`가 그 로그를 내보내는 순간 쓰기가 이 노드를 떠난다(복제본·영속화 로그).
그 뒤에 실패하면 **복제본이 master가 포기한 쓰기를 갖는다.** `map_elem_alloc`은 로그를 남기지
않으므로, 할당·정원 확보·그래프 삽입이 전부 그 앞이다.

### I5. 데몬은 죽지 않는다

메모리가 없으면 응답으로 답하지, abort하지 않는다. Rust 표준 컬렉션은 늘리지 못하면 abort하므로
자라는 자료구조는 전부 `try_reserve`를 먼저 부르고, 실패는 에러로 돌아간다.

☐ 새로 추가된 `Vec`/`HashSet`/`HashMap` 삽입이 `try_reserve` 없이 자라지 않는가
☐ **와이어에서 온 수가 할당 크기로 들어가지 않는가** — `Vec::with_capacity(k)`가 그랬다.
  `k`는 파싱에서 `MAX_RESULTS`로 막고, 버퍼는 실제 히트 수에서 잡는다
☐ `try_reserve`의 결과를 버리는 곳이 없는가 (`let _ = …reserve()` 뒤에 삽입이 오면 abort다)
☐ `unwrap()`/`expect()`/인덱싱/`panic!`이 명령 경로에 새로 들어오지 않았는가
☐ 락 순서가 `inner`(그래프) → `held`(보유 집합)인가. 반대로 잡는 곳이 하나라도 있으면 교착이다.
  **쓰기 경로에만 해당한다** — 읽는 쪽은 `held`를 아예 안 잡는다
☐ 레지스트리 가드를 든 채 `Arc<VectorIndex>`를 떨구는 곳이 없는가 (§1.6)

### I6. 이 그래프가 이 Map에서 나온 것인가 — owner 토큰

노드가 그래프를 메모리에 들고 있어도, 그 밑의 Map이 그 사이에 **다른 프로세스의 것이 됐을 수
있다**(스위치오버, Map 재생성). 그래서 Map의 META 원소가 자기를 만든 프로세스의 토큰을 들고
있고, 명령마다 그것을 메모리 쪽과 대조한다(§1.7 `resolve`).

**[src/owner.rs:12-24](../src/owner.rs#L12-L24)**

```rust
pub fn ours() -> &'static str {
    OURS.get_or_init(|| {
        let node = match node_address() {
            Some(mac) => mac.iter().fold(String::new(), |mut out, byte| {
                use std::fmt::Write as _;
                let _ = write!(out, "{byte:02x}");
                out
            }),
            None => format!("{:016x}", unpredictable()),
        };
        format!("{node}/{}/{}", std::process::id(), started())
    })
}
```

프로세스마다 한 번, **기동 시**에 만들어 고정한다. `{mac}/{pid}/{시작시각}` 문자열 그대로이고
해싱하지 않는다 — 세 값이 이미 안 겹치는데 해시로 뭉개면 충돌 가능성만 생긴다. 기동 때 만드니
명령 경로에서 `/sys`를 읽거나 `getifaddrs`를 부르는 일이 없고, MAC을 못 읽었다는 사실이 기동
배너에 남는다.

메모리 쪽 값은 문자열이 아니라 **상태**다. `SERVING`이면 우리 토큰, 아니면 `-`(`NOBODY`)를
답한다(§1.6). 남의 토큰이 메모리에 들어오는 경로가 없으므로 그것으로 충분하다.

☐ 토큰을 명령 경로에서 만들지 않는가 (기동 시 한 번)
☐ 토큰이 그대로 비교되는가 — 해시나 잘라 쓰기가 들어오면 서로 다른 프로세스가 같은 토큰을 가질 수 있다
☐ owner를 확인하는 곳이 `resolve` 하나인가 — 늘리면 명령 하나가 두 시점의 판정을 섞는다

## 1.1 element — 저장 바이트

**`src/handler/arcus/element.rs`** · 순수 함수만. 엔진도 그래프도 여기 안 들어온다.

원소 하나의 배치는 `alen(2) + ATTR(128) + 벡터 + 종단(2)`이다.

**[arcus/element.rs:48-57](../src/handler/arcus/element.rs#L48-L57)**

```rust
impl Layout {
    pub const VECTOR_OFFSET: usize = HEADER_LEN + ATTR_BYTES;

    pub const fn new(dim: usize, quant: Quant) -> Self {
        Self { dim, quant }
    }

    pub const fn vector_bytes(&self) -> usize {
        self.quant.vector_bytes(self.dim)
    }
```

`VECTOR_OFFSET`이 **상수**인 것이 핵심이다. ATTR이 가변이면 벡터 시작점이 `alen`에 따라
움직이고, `attr_of`와 디코딩이 매번 계산을 하게 된다.

### 벡터는 recovery 빌드에만 들어간다

**[arcus/element.rs:61-69](../src/handler/arcus/element.rs#L61-L69)**

```rust
    #[cfg(recovery)]
    pub const fn element_len(&self) -> usize {
        Self::VECTOR_OFFSET + self.vector_bytes()
    }

    #[cfg(not(recovery))]
    pub const fn element_len(&self) -> usize {
        Self::VECTOR_OFFSET
    }
```

Map의 벡터를 읽는 곳은 재구축 하나뿐이고, 그건 recovery 빌드에만 있다. `vsim KEY`의 질의
벡터는 그래프에서 읽는다(§1.5 `vector_of`). 768차원 f32면 원소가 3204 → 132 바이트가 된다.

☐ `element_len()`을 쓰는 자리와 `full_stored_len()`을 쓰는 자리가 뒤바뀌지 않았는가 —
  차원 한도만 후자를 쓴다(빌드에 따라 받는 차원이 달라지면 안 되므로)
☐ `#[cfg(recovery)]`로 잘린 `vector` 필드를 읽는 코드가 non-recovery 빌드에서 컴파일되지 않는가

### ATTR 영역은 통째로 다시 쓴다

**[arcus/element.rs:161-178](../src/handler/arcus/element.rs#L161-L178)**

```rust
    pub fn set_attr(&self, buf: &mut [u8], attr: &[u8]) -> Result<(), CodecError> {
        if attr.len() > ATTR_BYTES {
            return Err(CodecError::AttrTooLarge {
                limit: ATTR_BYTES,
                got: attr.len(),
            });
        }
        if buf.len() < Self::VECTOR_OFFSET {
            return Err(CodecError::Truncated {
                need: Self::VECTOR_OFFSET,
                got: buf.len(),
            });
        }
        buf[0..HEADER_LEN].copy_from_slice(&(attr.len() as u16).to_le_bytes());
        buf[ATTR_OFFSET..Self::VECTOR_OFFSET].fill(0);
        buf[ATTR_OFFSET..ATTR_OFFSET + attr.len()].copy_from_slice(attr);
        Ok(())
    }
```

`fill(0)`이 빠지면 안 된다. 엔진이 준 원소 몸통은 **슬랩에 있던 쓰레기**이고, 그 바이트도
그대로 저장되고 복제된다. 갱신에서는 예전 ATTR의 꼬리가 같이 나간다.

☐ ATTR을 쓰는 모든 경로가 `write` 또는 `set_attr`를 지나는가 (직접 `copy_from_slice` 금지)
☐ `set_attr`가 `buf.len()`을 바꾸지 않는가 — 바꾸면 I3의 "교체" 전제가 깨진다

### 헤더 파싱은 신뢰하지 않는다

**[arcus/element.rs:198-210](../src/handler/arcus/element.rs#L198-L210)**

```rust
fn parse_header(buf: &[u8]) -> Result<Header, CodecError> {
    if buf.len() < HEADER_LEN {
        return Err(CodecError::Truncated {
            need: HEADER_LEN,
            got: buf.len(),
        });
    }
    let attr_len = u16::from_le_bytes([buf[0], buf[1]]) as usize;
    if attr_len > ATTR_BYTES {
        return Err(CodecError::LayoutMismatch);
    }
    Ok(Header { attr_len })
}
```

`attr_len`은 **저장된 바이트에서 읽은 값**이다. `ATTR_BYTES`를 넘으면 그 원소는 우리가 쓴 것이
아니거나 형식이 다른 것이므로 슬라이싱 전에 거절한다.

☐ `buf[..]` 슬라이싱 앞에 길이 검사가 있는가 (`attr_of`, `decode` 둘 다)

## 1.2 engine::error — 엔진 코드를 어떻게 읽는가

**`src/handler/arcus/engine/error.rs`**

이 파일에서 리뷰할 것은 사실상 한 줄이다.

**[arcus/engine/error.rs:74-76](../src/handler/arcus/engine/error.rs#L74-L76)**

```rust
pub(super) fn completed(code: u32) -> bool {
    code == ENGINE_ERROR_CODE_ENGINE_SUCCESS || code == ENGINE_ERROR_CODE_ENGINE_EWOULDBLOCK
}
```

**`EWOULDBLOCK`은 실패가 아니다.** 동기 복제 master에서 연산은 *이미 성공한 뒤* 호출자를 슬레이브
ack 대기자로 등록한다. "아직 답하지 말라"는 뜻이지 "일어나지 않았다"가 아니다. 실패로 읽으면
방금 link된 원소를 해제하게 되고, `map_elem_free`가 `assert(elem->linked == 0)`에서 죽는다 —
**이 모듈이 실제로 서버를 죽인 적 있는 자리다.**

☐ 새 엔진 호출이 `check()`/`completed()`를 지나는가. 코드를 직접 `== ENGINE_SUCCESS`로 비교하면
  `EWOULDBLOCK`이 실패가 된다
☐ `KeyGone`(Map 없음)과 `ElemGone`(원소 없음)을 뒤섞은 곳이 없는가 — 앞은 그래프를 놓는 근거이고
  뒤는 그냥 `NOT_FOUND`다

## 1.3 engine::elem — 엔진 원소 다루기

**`src/handler/arcus/engine/elem.rs`** · 이 모듈에서 `unsafe`가 가장 많은 파일이다.

### PendingElem — 아직 아무도 못 보는 원소

**[arcus/engine/elem.rs:22-44](../src/handler/arcus/engine/elem.rs#L22-L44)**

```rust
#[must_use = "an uninserted element is invisible; insert it or drop it"]
pub struct PendingElem<'a> {
    store: &'a Store,

    key: &'a str,
    item: *mut eitem,

    value: *mut u8,
    value_len: usize,
}

impl Drop for PendingElem<'_> {
    fn drop(&mut self) {
        if self.item.is_null() {
            return;
        }
        let Some(elem_free) = self.store.vtable().map_elem_free else {
            return;
        };

        unsafe { elem_free(self.store.handle(), self.store.cookie, self.item) };
    }
}
```

`Drop`이 `map_elem_free`를 부르므로 조기 반환·`?`·패닉 어디서도 누수가 없다. I4가 성립하는
이유가 이것이다 — 몸통을 먼저 잡아 두고, 실패할 수 있는 일을 전부 한 다음, 마지막에 `insert`.

**[arcus/engine/elem.rs:64-90](../src/handler/arcus/engine/elem.rs#L64-L90)**

```rust
    fn publish(mut self, attr: *mut item_attr, replace_if_exist: bool) -> Result<Published> {
        let Some(insert) = self.store.vtable().map_elem_insert else {
            return Err(StoreError::Unavailable);
        };
        let mut replaced = false;
        let mut created = false;

        let code = unsafe {
            insert(
                self.store.handle(),
                self.store.cookie,
                self.key.as_ptr().cast::<c_void>(),
                as_int(self.key.len()),
                self.item,
                replace_if_exist,
                attr,
                ptr::from_mut(&mut replaced),
                ptr::from_mut(&mut created),
                0,
            )
        };

        check(code)?;

        self.item = ptr::null_mut();
        Ok(Published { created, replaced })
    }
```

`self.item = ptr::null_mut()`가 소유권 이전이다. 이 줄이 `check(code)?` **뒤에** 있어야 한다 —
앞에 있으면 실패한 insert의 원소가 새고, 더 뒤로 밀리면 성공한 insert의 원소를 두 번 해제한다.

☐ `check(code)?` 와 `self.item = null` 의 순서가 그대로인가
☐ `insert`의 반환값 `replaced`를 무시하는 호출자가 있는가 — `vsetattr`은 그것으로 부활을 막는다(§2.4)

### 주소를 잡는 두 가지 — hold_addr / take_addr

**[arcus/engine/elem.rs:296-320](../src/handler/arcus/engine/elem.rs#L296-L320)**

```rust
    pub fn hold_addr(&self, key: &str, field: &str) -> Result<HeldAddr<'_>> {
        let elems = self.fetch(key, Some(field))?;
        let addr = match elems.as_slice() {
            Some(items) => items[0] as u64,
            None => return Err(StoreError::ElemGone),
        };

        std::mem::forget(elems);
        Ok(HeldAddr { store: self, addr })
    }

    pub fn take_addr(&self, key: &str, field: &str) -> Result<Option<HeldAddr<'_>>> {
        match self.fetch_with(key, Some(field), true) {
            Ok(elems) => {
                let addr = match elems.as_slice() {
                    Some(items) => items[0] as u64,
                    None => return Ok(None),
                };
                std::mem::forget(elems);
                Ok(Some(HeldAddr { store: self, addr }))
            }
            Err(StoreError::ElemGone) => Ok(None),
            Err(e) => Err(e),
        }
    }
```

`std::mem::forget(elems)`가 요점이다. `Elems`의 `Drop`은 refcount를 반납하는데, 여기서는
**반납하지 않고 `HeldAddr`로 옮긴다.** 그래서 주소가 계속 그 원소를 가리킨다(I2).

`take_addr`는 읽기와 삭제를 한 호출로 한다(`map_elem_get`의 `delete` 플래그). 두 호출로 나누면
그 사이에 쓰기가 들어온다.

☐ `forget` 뒤에 `HeldAddr`(또는 그것을 `keep()`한 결과)가 반드시 그래프나 `release_held`로
  이어지는가 — 끊기면 refcount 누수다
☐ `HeldAddr::keep()`을 부른 자리마다, 그 주소를 받은 쪽이 해제 책임을 진다는 것이 코드로 보이는가

### stage — 이름 없는 노드

**[usearch/index.rs:311-324](../src/handler/usearch/index.rs#L311-L324)**


용량을 먼저 잡는 이유는 그것이 `inner`의 **쓰기** 락을 잡기 때문이다. `+ THREAD_SLOTS`는 동시에

**비싼 것이 여기 있고, 여기는 읽기 락이다.** HNSW 삽입(`typed_add`)이 `inner.read()` 아래에서
돌므로 여러 커넥션이 동시에 들어간다. `inner`가 배제하는 것은 `reserve`와 `reset`뿐이고,
`ensure_capacity`는 정원이 남아 있으면 원자 변수 하나 읽고 빠져나간다(정원을 두 배씩 늘리므로
원소 N개에 쓰기 락은 O(log N)번).

`at_epoch`를 여기서 적어 둔다. 이것이 `insert_published`의 `live` 판정이 보는 값이고, 그 사이에
그래프가 리셋됐는지를 알려준다.

☐ `ensure_capacity`가 `inner` 읽기 락 **밖**에서 불리는가 (안에서 부르면 자기 자신과 교착)
☐ `stage`가 `inner`를 **읽기**로 잡는가 — 쓰기로 바꾸면 모든 삽입이 직렬화된다
☐ `Staged`가 `Drop`으로만 카운트를 내리는가 — `publish`/`discard`가 직접 내리면 패닉 경로에서 샌다

`insert_published`와 같은 모양으로 끝난다. `give_up(old, tombstone)`으로 헌 주소를 넘기고,
노드를 못 옮겼으면 새 주소를 `Published::Unindexed`로 호출자에게 돌려준다.

**`had`가 `false`인 경우가 재구축 중에는 정상이다.** `refill`이 아직 그 주소까지 안 갔으면
`held`에 없다. 예전에는 여기서 새 원소를 release하고 `Ok(Some(()))`로 성공을 답했는데, 그러면
Map에는 새 원소가 있고 그래프에는 아무것도 없었다. 지금은 `vsetattr`이 `kept_vector`로 그
원소를 그래프에 넣는다(§2.4).

☐ `give_up`이 `write(value)` **뒤**에 오는가 — 앞이면 쓰기가 실패했을 때 노드를 잃는다
☐ `had`가 `false`인 경로가 새 주소를 release하지 않고 `Unindexed`로 넘기는가
☐ `rename`의 `Ok(1)`을 확인하는가

### remove_published — vdel

**[usearch/index.rs:764-789](../src/handler/usearch/index.rs#L764-L789)**

```rust
    pub fn remove_published<E>(
        &self,
        take: impl FnOnce() -> std::result::Result<Option<u64>, E>,
    ) -> std::result::Result<Option<bool>, PublishError<E>> {
        let _slack = InFlight::new(&self.in_flight);
        let mut held = self.held.write().unwrap_or_else(PoisonError::into_inner);

        let tombstone = self.rebuilding.load(Ordering::Acquire);
        if tombstone && let Err(e) = held.reserve_tombstone() {
            return Err(PublishError::Mapping(Error::Index(format!(
                "the held set could not grow: {e}"
            ))));
        }

        let Some(addr) = take().map_err(PublishError::Store)? else {
            return Ok(None);
        };

        let had_node = held.give_up(addr, tombstone);
        drop(held);

        if had_node && self.unlink_node(addr) {
            self.retire(&[addr]);
        }
        Ok(Some(had_node))
    }
```

tombstone 자리를 **엔진 삭제보다 먼저** 잡는다. 삭제된 뒤에는 실패를 보고할 자리가 없다 —
삭제는 이미 복제본으로 가는 중이다.

`give_up`은 이 셋(`insert_published`·`update_published`·`forget_unreadable`)이 공유한다.
재구축 중이면 묘비를 남기고, 아니면 그냥 뺀다 — 세 곳이 같은 규칙을 쓰는지가 중요하다.
한 곳만 빠져 있어서 생긴 버그가 있었다(§1.5 `insert_published`).

☐ `reserve_tombstone`이 `take()` 앞인가
☐ `drop_node`가 hold를 놓은 뒤인가
☐ `reserve_tombstone`의 **결과를 보는가.** `forget_unreadable`이 한때
  `let _ = held.reserve_tombstone();` 뒤에 그냥 삽입했다 — 자리를 못 잡았을 때 abort다.
  지금은 자리가 있을 때만 tombstone을 남기고, 없으면 그것 없이 뺀다

### 지연 회수 — 검색이 락을 안 잡는 이유

읽는 쪽이 주소를 역참조하는 동안 그 원소가 해제되면 안 된다. 예전에는 읽는 내내 락을 들어서
막았다. 지금은 **해제를 미뤄서** 막는다.

**[usearch/index.rs:84-111](../src/handler/usearch/index.rs#L84-L111)**

```rust
impl<'a> Searching<'a> {
    fn new(index: &'a AnnIndex) -> Self {
        let stamp = crate::server::coarse_now();
        let home = HOME.with(|home| *home);
        let slot = (0..READER_SLOTS)
            .map(|step| (home + step) % READER_SLOTS)
            .find(|slot| {
                index.readers[*slot]
                    .compare_exchange(NO_READER, stamp, Ordering::AcqRel, Ordering::Relaxed)
                    .is_ok()
            });
        if slot.is_none() {
            index.unslotted.fetch_add(1, Ordering::AcqRel);
        }
        Searching { index, slot }
    }
}

impl Drop for Searching<'_> {
    fn drop(&mut self) {
        match self.slot {
            Some(slot) => self.index.readers[slot].store(NO_READER, Ordering::Release),
            None => {
                self.index.unslotted.fetch_sub(1, Ordering::AcqRel);
            }
        }
    }
}
```

검색이 시작하면 스탬프를 슬롯 하나에 꽂고, 끝나면 뺀다. 슬롯은 **고정 배열 128개**라 자라지
않고, 스레드마다 자기 홈에서 시작해 CAS하므로 0번 칸을 두고 다투지 않는다. 다 차면 그 검색은
등록 없이 돌되 `unslotted`를 올려 **회수를 전부 막는다** — 드물고, 안전한 쪽이다.

**[usearch/index.rs:516-543](../src/handler/usearch/index.rs#L516-L543)**

```rust
    fn retire(&self, addrs: &[u64]) {
        if addrs.is_empty() {
            return;
        }
        let after = crate::server::coarse_now() + 1;
        let done = self.oldest_reader();

        if done >= after && self.queued.load(Ordering::Relaxed) == 0 {
            self.elements.release(addrs);
            return;
        }

        let mut ready: Vec<u64> = Vec::new();
        {
            let mut retired = self.retired.lock().unwrap_or_else(PoisonError::into_inner);
            if retired.try_reserve(addrs.len()).is_err() {
                drop(retired);
                self.drain_then_release(addrs, after);
                return;
            }
            retired.extend(addrs.iter().map(|addr| (*addr, after)));
            take_ready(&mut retired, done, &mut ready);
            self.queued.store(retired.len(), Ordering::Relaxed);
        }
        if !ready.is_empty() {
            self.elements.release(&ready);
        }
    }
```

`retire`가 기록하는 `after`는 **그 시점 스탬프 + 1**이고, 반납 조건은 "아직 도는 검색 중 그보다
오래된 것이 없다"다. 즉 **이 삭제보다 먼저 시작한 조회가 전부 끝났다.** 그 뒤에 시작한 검색을
안 세도 되는 이유는 `retire`를 **노드를 그래프에서 뺀 다음에** 하기 때문이다 — 그 이후 검색은
그 노드에 도달할 수가 없다.

`oldest_reader()`가 세는 것이 **끝난 개수가 아니라 아직 도는 것 중 가장 오래된 스탬프**다.
개수로 세면 틀린다:

```
A 시작        B 시작        retire(after=S)
              B 종료        C 시작·종료      ← 끝난 개수는 둘인데 A가 아직 돈다
```

☐ `retire`가 `drop_node` **뒤**인가. 앞이면 그 사이에 시작한 검색이 노드를 볼 수 있다
☐ 회수 판정이 개수가 아니라 **최솟값**인가
☐ `unslotted > 0`이면 아무것도 안 놓는가
☐ 큐가 못 자랄 때(`try_reserve` 실패) 즉시 반납하지 않고 기다리는가

### 스탬프는 서버 시계에서 온다

```rust
        let pending = {
            let mut stuck = self.stuck.lock().unwrap_or_else(PoisonError::into_inner);
            if stuck.is_empty() {
                return;
            }
            std::mem::take(&mut *stuck)
```

`index.remove`는 usearch가 free list를 못 늘리면 거절한다. 그러면 노드가 그래프에 남고, 검색이

대가는 그 노드가 지워진 id로 계속 답하는 것이고, 청소 스레드가 틱마다 재시도해 그것을 끝낸다.

☐ `drop_node`가 실패한 주소를 retire하지 않는가 — 하면 해제된 주소를 역참조하게 된다
☐ 물리는 refcount가 **하나뿐**인가 (밀려난 원소는 둘을 빚지는데 여분은 바로 retire한다)

### search — 술어와 락

**[usearch/index.rs:832-864](../src/handler/usearch/index.rs#L832-L864)**

```rust
    pub fn search(
        &self,
        query: &[u8],
        k: usize,
        accept: Option<Accept<'_>>,
    ) -> Result<Vec<(u64, Arc<str>, f32)>> {
        if query.len() != self.layout.vector_bytes() {
            return Err(Error::bad_request(format!(
                "query is {} bytes, expected {}",
                query.len(),
                self.layout.vector_bytes()
            )));
        }

        let _searching = Searching::new(self);
        let entered = self.epoch.load(Ordering::Acquire);

        let k = k.saturating_add(self.in_flight.load(Ordering::Relaxed));

        let matches = {
            let index = self.inner.read().unwrap_or_else(PoisonError::into_inner);
            match accept {
                None => self.unfiltered(&index, query, k),

                Some(matches) => self.matches(&index, query, k, |key| {
                    !held::is_staged(key) && matches(key)
                }),
            }?
        };

        let hits: Vec<(u64, f32)> = matches.keys.into_iter().zip(matches.distances).collect();
        Ok(self.resolve(&hits, entered))
    }
```

**검색은 락을 하나도 잡지 않는다.** 노드당 하는 일이 `is_staged` 비트 검사와 술어 호출뿐이다.
`inner.read()`는 순회 동안 들지만 그건 공유 락이라 배제하는 것이 `reserve`/`reset`뿐이다(§1.5 위).

**`k`를 부풀린다.** 스테이징된 노드가 결과 자리를 하나 먹으므로, 진행 중인 쓰기 수만큼 더
요청한다. 그러지 않으면 가지치기 반경이 이름 없는 노드의 거리에서 닫혀 진짜 이웃이 후보에서
잘린다.

**`Searching::new(self)`가 티켓을 집는다.** 이것이 지연 회수의 등록이고, 검색당 딱 한 번이다.

☐ `Searching`이 `search` 전체를 덮는가. 이게 없으면 회수가 읽는 중인 주소를 놓는다
☐ `epoch`를 검색 시작에 읽고 `resolve`에서 비교하는가 — 그 사이 `clear`가 있었으면 결과를 버려야 한다
☐ `is_staged` 검사가 역참조보다 앞인가 (가짜 키를 역참조하면 안 된다)

### 인덱스의 다섯 상태

**[registry.rs:36-55](../src/handler/registry.rs#L36-L55)**


`state` 하나가 "이 그래프를 지금 믿어도 되는가"를 답한다.

| 상태 | 뜻 | 그래프 | `stamped_as()` |
|---|---|---|---|
| `BUILDING` | `vcreate`가 이름만 잡아 둠. Map이 아직 없거나 방금 생김 | 빈 | `-` |
| `SERVING` | 정상 | Map과 일치 | `owner::ours()` |
| `DRAINING` | 남의 owner를 본 명령이 넘겨 둠. drain 스레드가 버리는 중 | 버려지는 중 | `-` |
| `COLD` | 그래프가 비었음. Map은 멀쩡 | 빈 | `-` |
| `FILLING` | 스냅숏이 서 있고 build 스레드가 채우는 중 | 절반 | `-` |

**`SERVING`이 아니면 `stamped_as()`가 `-`(`owner::NOBODY`)를 답한다.** Map에도 같은 `-`가 찍혀
있어서, 재구축 중에 재진입해도 자기 자신을 남으로 오해하지 않는다. 그 사이에 프로세스가 죽으면
Map에 `-`가 남아 다음 프로세스가 "미완의 재구축"으로 알아본다.

**쓰기가 막히는 것은 `DRAINING`뿐이다.** `COLD`·`FILLING`에서는 통과한다 — 그것이 묘비가
존재하는 이유다. 읽기만 채우기를 기다린다.

☐ 상태를 새로 추가할 때 `stamped_as()`가 그것을 `SERVING`으로 세지 않는가
☐ 쓰기 경로가 `DRAINING`만 거르는가 — `COLD`/`FILLING`을 같이 거르면 스위치오버 직후 적재가 전부 막힌다

☐ `BUILDING` 검사가 세대 비교 **앞**인가 — 미발행 항목은 `published_at()`이 0이라 시간 비교만으로는 지워진다

```rust
fn coldest_of<'a>(entries: impl Iterator<Item = (u64, &'a str)>, limit: usize) -> Vec<String> {
    let mut all: Vec<(u64, &str)> = Vec::new();
    for entry in entries {
        if all.try_reserve(1).is_err() {
            return Vec::new();
        }
        all.push(entry);
    }
    all.sort_unstable();
    all.truncate(limit);
    all.into_iter().map(|(_, name)| name.to_string()).collect()
}
```

```rust
pub fn drain(store: &Store, index: &Arc<VectorIndex>) -> Result<()> {
    let was = index.state();
    if was == DRAINING {
        return Ok(());
    }
    index.mark_state(DRAINING);
    index.refilled.store(false, Ordering::Release);

    if let Err(e) = stamp(store, &index.name, owner::NOBODY) {
        index.mark_state(was);
        return Err(e);
    }

    if index.ann.is_empty() {
        index.mark_state(COLD);
        return Ok(());
    }
    DRAINER.enqueue(Arc::clone(index));
    Ok(())
```

커넥션이 하는 일은 도장 하나와 넘기기뿐이다. 그래프를 비우는 일 — `reset`, 보유 집합 비우기,
주소 N개 반납 — 은 drain 스레드가 한다. 한때 이것을 전부 커넥션이 했고, 원소가 많은 인덱스면

순수한 철거다.

이미 비어 있는 그래프는 큐를 건너뛰고 바로 `COLD`로 간다.

```rust

    if !index.enter(COLD, FILLING) {
        return Ok(());
    }
    index.refilled.store(false, Ordering::Release);
    index.ann.begin_fill();

    let held = match store.hold_all(&index.name) {
        Ok(held) => held,
        Err(e) => {

            index.mark_state(COLD);
            return Err(e.into());
        }
    };

    BUILDER.enqueue(&index.name, held);
```

```rust
fn refill(store: &Store, index: &VectorIndex, held: &mut HeldMap) -> Result<usize> {
    index.ann.reserve(held.len())?;

    let layout = index.ann.layout;
    let mut added = 0usize;
    for (addr, field, value) in held.read(store) {
        if field == META_FIELD.as_bytes() {
            continue;
        }
        if index.state() != FILLING {
            return Ok(added);
        }
        let element = layout.decode(&value).map_err(|e| {
            Error::bad_request(format!(
                "{e} in element {}",
                String::from_utf8_lossy(&field)
            ))
        })?;
        let vector = element.vector.to_vec();
        let replayed = index
            .ann
            .add_unless_known(addr, || Ok(Some(vector.clone())))?;
        if replayed {
            added += 1;
            held.keep(addr);
        }
    }
    Ok(added)
}
```

`add_unless_known`이 보유 집합 쓰기 락 아래에서 판정한다 — `vadd`가 두 등록에 걸쳐, `vdel`이
tombstone에 걸쳐 잡는 바로 그 락이다. 그래서 라이브 경로가 건드린 id는 여기서 이미 알려져 있고
건너뛴다.

☐ 재구축 스레드가 쓰기를 하지 않는가 — 토큰 기록(`stamp`)이 전부 워커에 있는가
☐ `keep`이 그래프에 넘어간 주소에만 불리는가 (§1.3 `HeldMap::drop`)

등록이 엔진을 만지기 **전**이다(I4). 자라야 하는 자료구조가 레지스트리 하나뿐이라 그것을 먼저
치운다. ②와 ⑤ 사이에는 "이름은 인덱스인데 아직 쓸 수 없는" 구간이 생기고, 그것을 막는 것이
**`BUILDING` 상태**다. 그 구간에 들어온 명령은 `resolve`에서 바로 "없는 인덱스"로 답하고,
`remove_if_stale`도 `coldest`도 그 항목을 건드리지 않는다.

owner 토큰은 `crate::owner::ours()`다 — 프로세스마다 한 번, 기동 시 `{mac}/{pid}/{시작시각}`
문자열로 만들어 고정한다(§0). 해싱하지 않으므로 충돌이 없고, 명령 경로에서 `/sys`를 읽거나
`getifaddrs`를 부르지 않는다.

**probe하지 않는다.** probe는 이미 지나간 순간에 대한 답이고, 그것이 보고할 수 있는 모든 경우가

|---|---|---|
| `Ok(true)` | 비어 있었다 | 발행 + `mark_ours`, 밀려난 낡은 항목을 `retire` → `CREATED` |
| `Ok(false)` | 메타데이터 없는 Map | 우리 것 아님. `unput` + 원소 되빼기 |
| `Err(ElemExists)` | 이미 인덱스 | recovery면 인수, 아니면 `vdrop` 안내 |
| `Err(BadType)` | Map이 아닌 아이템 | `CLIENT_ERROR` |

`replace_if_exist=false`도 못 막는다 — 덮어쓸 원소가 없으니 그냥 들어간다.

☐ `unput`이 "이름이 아직 이 호출의 항목을 들고 있을 때만" 하는가 (경쟁하는 `vcreate`의 것을

☐ `Ok(false)`에서 `delete_elem`이 `drop_if_empty=false`인가 — 남의 Map을 비웠다고 지우면 안 된다
☐ 낡은 항목을 놓는 자리가 `Ok(true)` **뒤**인가 (probe 실패로 놓던 예전 코드는 멀쩡한 인덱스를
  날리는 경로였다)
☐ `mark_ours()`가 `publish()`와 같은 자리에 있는가 — 떨어져 있으면 그 사이에 `resolve`가 Map의
  우리 토큰과 `-`를 비교해 방금 만든 인덱스를 drain으로 보낸다

## 2.2 vadd

**[cmd/vector.rs:65-83](../src/handler/cmd/vector.rs#L65-L83)**

```rust
fn index_it(
    index: &std::sync::Arc<crate::handler::registry::VectorIndex>,
    name: &str,
    addr: u64,
    vector: Vec<u8>,
) {
    match index.ann.add_unless_known(addr, || Ok(Some(vector))) {
        Ok(true) => {}
        Ok(false) => index.ann.unclaimed(addr),
        Err(e) => {
            eprintln!(
                "ArcVector: '{name}' stored an element its graph would not take ({e}); \
                 dropping the graph so the next read rebuilds it from the Map"
            );
            index.ann.unclaimed(addr);
            registry::remove_observed(name, index);
        }
    }
}
```

`add_unless_known`이 `held.is_known(addr)`로 거르므로 `refill`이 먼저 넣었으면 no-op이다. 어느
쪽이 이기든 수렴한다 — 경주가 없다. 그래프가 끝내 못 받으면 인덱스를 놓아 다음 읽기가 Map에서
다시 만들게 하고, 그래도 **`STORED`를 답한다**. 원소는 Map에 있고 Map이 진실의 출처이며, 어긋난
채로 남은 그래프가 없기 때문이다.

☐ `pending.addr()`를 믿지 않고 `hold_addr`로 **다시 읽는가** — 그 사이에 무엇이 링크됐든 Map이
  실제로 들고 있는 원소가 키가 되어야 한다
☐ `stamp`가 `for_write` **뒤**인가 (이 쓰기의 항목은 이미 발행돼 있다)
☐ `Unindexed`를 무시하는 경로가 없는가 — 무시하면 Map에는 있고 `vsim`에는 없는 원소가 남는다
☐ `index_it`이 실패했을 때 주소를 release하는가 (`held`가 안 가져갔으므로 아무도 안 든다)
☐ `PublishError::Mapping`이 에러 응답이지 abort가 아닌가 (I5)

## 2.5 vdel

```
① for_write       메타 읽고 소유권
② hold · take     원소 unlink + 주소   arcus  ← 엔진 먼저
③ hold · take     노드 제거            usearch
```

**[cmd/vector.rs:231-264](../src/handler/cmd/vector.rs#L231-L264)**

```rust
pub fn vdel(store: &Store, name: &str, id: &str) -> Result<Reply> {
    let index = for_write(store, name)?;
    let stamp = registry::now();

    let mut map_gone = false;

    let mut taken = None;
    let removed = index
        .ann
        .remove_published(|| match store.take_addr(name, id) {
            Ok(held) => {
                let addr = held.as_ref().map(HeldAddr::addr);
                taken = held;
                Ok(addr)
            }
            Err(StoreError::KeyGone) => {
                map_gone = true;
                Ok(None)
            }
            Err(e) => Err(e),
        });
    drop(taken);

    if map_gone {
        map_is_gone(name, stamp);
    }
    match removed {
        Ok(Some(_)) => Ok(Reply::Deleted),
        Ok(None) => Ok(Reply::NotFound),
        Err(PublishError::Store(e)) => Err(e.into()),

        Err(PublishError::Mapping(e)) => Err(e),
    }
}
```

**엔진 먼저**다(I1). 그래프만 지운 삭제는 재구축에서 되살아난다.

`taken`의 hold가 unlink보다 오래 사는 것이 요점이다 — 그동안 주소가 여전히 그 원소를 뜻하므로
그래프에 그 주소를 물어볼 수 있다.

순서는 **엔진 unlink → 집합에서 제거 → 락 해제 → 노드 제거 → retire**다. 노드를 먼저 떼는
쪽으로 바꾸면 엔진 호출이 하나 늘고(원자적 get+delete를 못 쓴다) 실패 모드가 뒤집힌다 —
"노드는 없는데 원소는 남는" 쪽이 되고, non-recovery 빌드는 그것을 복구하지 못한다.

☐ `drop(taken)`이 `remove_published` **뒤**인가
☐ `map_is_gone`이 hold **밖**인가 — 안에서 부르면 레지스트리 해제가 그래프를 떨구는데 그 락이
  hold 안이다
☐ refcount가 `release`가 아니라 `retire`로 가는가 (§1.5)

**FILTER 경로가 이 모듈에서 가장 뜨거운 코드다.** 방문 노드마다 도는데, 키가 곧 주소라

통과한 것은 **바이트를 복사해 둔다** — refcount를 잡는 게 아니라. ATTR이 최대 128바이트라
원소를 붙드는 것보다 싸고, 엔진 호출이 술어 경로에서 사라진다. 한때 여기서 `hold_elem`
(= `map_elem_get`, 전역 캐시 락)을 통과 노드마다 불렀고, 그 refcount를 검색이 끝날 때까지 들고
있었다.

**이 역참조가 안전한 근거는 락이 아니라 지연 회수다**(§1.5). 검색이 티켓을 든 동안에는 그
주소의 refcount가 돌아가지 않는다. 술어가 하는 판정이 결과 집합 전체를 좌우하므로 — 잘못된
`true`가 가지치기 반경을 좁혀 진짜 이웃을 자른다 — 이 읽기는 반드시 유효해야 한다.

`judged`는 질의 하나짜리 지역 변수다. `RefCell`인 이유는 usearch 술어가 `Fn`이라서고,
`try_reserve`로 자란다 — 방문 노드 수만큼 자랄 수 있는 자료구조라 상한이 `k`가 아니다.

☐ `WITHATTR`이 아니면 히트당 엔진 호출이 0인가

☐ `Vec::with_capacity`에 클라이언트가 정하는 값이 들어가지 않는가

## 2.7 vdrop · vlist · vstats

```rust
pub fn vdrop(store: &Store, name: &str) -> Result<Reply> {
    let dropped = match store.drop_map(name) {
        Ok(()) => true,
        Err(StoreError::KeyGone) => false,
        Err(e) => return Err(e.into()),
    };
    let known = registry::remove(name);

    Ok(if known || dropped {
        Reply::Dropped
    } else {
        Reply::NotFound
    })
}
```

Map을 먼저 지운다. 진짜 실패는 레지스트리를 건드리면 안 된다 — 아직 있는 Map을 인덱스가
안 섬기게 되고, 클라이언트는 `DROPPED`를 듣는다. 레지스트리와 무관하게 시도하므로 고아 Map도
치울 수 있다.

☐ `known || dropped`인가 (둘 중 하나만 있어도 뭔가 지운 것이다)

`vlist`는 **어느 저장소도 부르지 않는다** — 레지스트리만 읽는다. `vstats`는 usearch만 부른다.

# 부록 · 리뷰 체크리스트 한 장

**전역**

☐ 자라는 컬렉션이 `try_reserve`를 지나는가 (I5)
☐ 와이어에서 온 수가 할당 크기에 들어가지 않는가
☐ `try_reserve`/`reserve`의 결과를 버리고 삽입하는 곳이 없는가
☐ 명령 경로에 `unwrap`/`expect`/`panic!`/슬라이스 인덱싱이 새로 없는가
☐ 락 순서 `inner` → `held`
☐ 레지스트리 가드를 든 채 `Arc<VectorIndex>`를 떨구지 않는가

**엔진 경계**

☐ 새 호출이 `check()`를 지나는가 (`EWOULDBLOCK` = 성공)
☐ `abi.rs`의 `REQUIRED`에 그 함수가 있는가, 선언 순서대로인가
☐ 커넥션 없는 스레드가 키를 받는 API를 부르지 않는가

**주소를 키로 쓰는 것에서 오는 것**

☐ `forget(elems)` 뒤의 refcount에 주인이 있는가
☐ `take`가 `true`를 준 뒤 **락을 놓기 전에** 반납하는가
☐ 링크된 원소를 제자리에서 고치지 않는가 (I3)
☐ 역참조가 지연 회수의 보호 아래인가 (`Searching` 티켓)
☐ `retire`가 `drop_node` 뒤인가. 실패한 `drop_node`의 주소를 retire하지 않는가

**그래프를 놓는 것**

☐ 엔진이 "없다"고 말한 뒤에만 놓는가
☐ `stamp`를 읽기 앞에서 집는가
☐ `remove_if_stale` / `remove_observed`를 쓰는가 (이름만으로 `remove` 금지)

**순서**

☐ 실패할 수 있는 일이 전부 `map_elem_insert` 앞인가 (I4)
☐ 삭제가 엔진 먼저인가 (I1)

**Map과 그래프가 어긋나지 않는가**

☐ 엔진이 원소를 받았는데 그래프가 못 받은 경로가 성공을 답하고 끝나지 않는가 —
  `Published::Unindexed`로 넘겨 색인하든, 인덱스를 놓아 재구축시키든, 어긋난 채로 두지 않는다
☐ 재구축 중에 주소를 빼는 모든 곳이 `give_up(addr, tombstone)`을 쓰는가 —
  한 곳만 평범한 `take`여도 `refill`이 지워진 원소를 되살린다
☐ `rename`의 반환값이 `Ok(1)`인지 보는가 (`Ok(0)`은 에러가 아니다)
☐ 상태가 `SERVING`인 동안에만 그래프를 믿는가

**상태와 스레드**

☐ 쓰기가 막히는 상태가 `DRAINING`뿐인가
☐ 커넥션이 O(N) 작업을 하지 않는가 — 철거는 drain 스레드, 채우기는 build 스레드
☐ 스레드가 부르는 엔진 호출이 §1.7 표의 아래 두 줄에만 있는가

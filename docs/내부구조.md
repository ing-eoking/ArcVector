## 1. 무엇인가

arcus-memcached 서버는 **ASCII 프로토콜 확장**을 적재할 수 있다. 콜백 서술자를 등록하고 그
대가로 명령어 이름을 점유하는 공유 라이브러리다. ArcVector가 그런 확장이고, 서버 프로세스
*안에서* 서버의 워커 스레드 위에 얹혀 돌며, memcached 자신이 쓰는 것과 같은 `engine_interface_v1`
vtable로 스토리지 엔진과 이야기한다.

인덱스는 두 계층이다.

```
질의 ──▶ usearch HNSW 그래프 ──▶ 근접 키 ──▶ arcus Map ──▶ 속성
         (탐색 가속)                          (원본)
```

인덱스 하나가 Map 아이템 하나(키 = 인덱스 이름), 벡터 하나가 Map 원소 하나(필드 = 벡터 id).
Map을 고른 이유는 키 조회·복제·TTL이 이미 그 경로에 있기 때문이다.

**전체를 지배하는 규칙이 하나 있다.**

> usearch 인덱스는 언제든 Map으로부터 재구성 가능한 **캐시**다.
> Map에 없으면 존재하지 않는다.

재시작, 축출, TTL 만료, 복제 슬레이브가 전부 여기서 따라 나온다 — 네 가지 사례가 아니라
하나다. 그리고 **모든 쓰기는 Map을 먼저, 그래프를 나중에** 바꾼다. 그 순서 때문에 "그래프에는
있는데 Map에는 없다"는 상태가 구조적으로 생기지 않는다.

## 2. 빌드와 실행

### 2.1 빌드

```sh
cargo build --release          # → target/release/libarcusv.{so,dylib}
```

`build.rs`가 `include/`의 arcus 헤더에 bindgen을 돌리므로 libclang이 필요하고, usearch가
C++ 코어를 컴파일하므로 C++17 툴체인도 필요하다. 생성물은 `OUT_DIR`로 나가 소스 트리를
건드리지 않는다.

### 2.2 피처 — 축이 둘이다

이 크레이트의 피처는 **기능 요청이 아니라 memcached 서버에 대한 사실 선언**이다. 켠다는
건 "내가 붙일 서버가 그렇게 빌드돼 있다"는 뜻이므로, 서버의 `config.h`를 보고 맞춰야 한다.

**축 1 — vtable 레이아웃.** 선택이 아니다. 틀리면 엉뚱한 함수를 부른다.

| 피처 | 효과 |
|---|---|
| `replication` | `engine_interface_v1`에 멤버 7개 추가 |
| `migration` | 멤버 6개 추가 |
| `cluster-aware` | `SERVER_CORE_API`에 2개 추가 |

피처 이름은 서버의 `configure` 플래그에서 arcus가 붙이는 `ENABLE_` 접두사만 뗀 것이다.
`build.rs`가 그 접두사를 도로 붙여 bindgen에 넘기므로 — `replication` → `-DENABLE_REPLICATION`
— 이름을 두 군데 적지 않는다. `ENABLE_`은 우리가 고른 이름이 아니라 헤더가 `#ifdef`로
검사하는 매크로라서 그대로 정의해야 한다.

**축 2 — 복구를 돌릴 것인가.** 배포 선택이다.

| 피처 | ABI 영향 | 의미 |
|---|---|---|
| `persistence` | **없음** | 서버가 재시작 때 아이템을 복원한다 |

`ENABLE_PERSISTENCE`는 `engines/default/*.h`에만 있고 `include/memcached/`에 닿지 않아
define을 넘기지 않는다. 순수한 사실 선언이다.

`build.rs`는 **replication이나 persistence 중 하나라도 켜지면** `cfg(recovery)`를 켠다.
둘 다 없다는 건 그래프보다 오래 사는 것이 없다는 뜻이므로, 소유 토큰 비교도 명령마다의
메타데이터 읽기도 복구 스레드도 전부 컴파일되지 않는다. §7.6.

```sh
cargo build --release --features replication
cargo build --release --features replication,persistence
cargo build --release                                    # 복제도 퍼시스턴스도 없는 서버
ARCVECTOR_ENGINE_INCLUDE=/path/to/tree/include cargo build --release   # 다른 헤더 트리
```

### 2.3 적재와 확인

```sh
memcached -E .../default_engine.so -X .../libarcusv.so
```

적재 직후 첫 엔진 호출 때 지문 한 줄이 로그에 나온다. **왼쪽이 서버, 오른쪽이 빌드**다.

```
ArcVector: memcached 0.9.5-E-139, built for ee tree, 76 members,
           features=[replication,scan], headers=include
```

`features`는 우리가 요청한 값이 아니라 **생성된 vtable을 되읽은 결과**다. `scan`처럼
헤더에서 딸려온 것과, 요청했는데 안 들어온 것을 구분하기 위해서다. 오프셋을 정하는 건
실제 구조체 모양이니까.

`ARCVECTOR_ABI_DEBUG=1`을 주면 필요한 멤버가 각각 해소됐는지 나열한다.

### 2.4 테스트

| 종류 | 명령 | 서버 |
|---|---|---|
| 단위 | `make unit` | 불필요 |
| 통합 | `make test` (컨테이너) | 이미지가 포함 |
| 복제 | `cargo test --features replication-tests --test replication -- --test-threads=1` | 마스터/슬레이브 짝을 직접 띄워야 함 |

통합 테스트를 호스트에서 돌리려면 서버 경로를 준다.

```sh
ARCVECTOR_MEMCACHED=/path/memcached ARCVECTOR_ENGINE=/path/default_engine.so \
  cargo test --features integration,replication
```

> **신선도 검사가 있다.** `cargo test`는 서버가 적재하는 `cdylib`을 다시 빌드하지 않으므로,
> 소스가 라이브러리보다 새로우면 **패닉으로 거부한다.** 낡은 결과는 없는 결과가 아니라
> 틀린 결과다. `cargo build`를 먼저 돌려야 한다.

**복제 짝 구성.** ZooKeeper와 EE 서버가 필요하다. 필수 스위트에 넣지 않은 이유는, 초록불이
switchover를 검증했다는 뜻이 되면 안 되기 때문이다.

```sh
# 1. ZK에 서비스 코드와 복제 그룹 znode 등록 (한 번)
#    /arcus_repl/cache_list/<svc>/<ip>:<port>-<hostname>
#    /arcus_repl/cache_server_group/<svc>/<group>/{lock,<ip>:<port>}
# 2. 두 노드를 같은 그룹으로 띄운다
memcached -E .../default_engine.so -X .../libarcusv.so \
          -l 127.0.0.1 -p 11311 -m 256 -z 127.0.0.1:2181
memcached ... -p 11312 -z 127.0.0.1:2181
# 3. 역할 확인
printf 'stats replication\r\n' | nc 127.0.0.1 11311 | head -1
```

테스트는 시작할 때마다 역할을 다시 조회한다. switchover가 짝을 뒤집으므로 어느 쪽이
마스터인지 가정하지 않는다.

## 3. 명령 API

| 명령 | 형태 | 응답 |
|---|---|---|
| `vcreate` | `vcreate <index> <dim> [METRIC][QUANT][M][EFC][EFS][MAXCOUNT][EXPTIME]` | `CREATED` · `EXISTS` |
| `vadd` | `vadd <index> <id> <veclen> <dim> [ATTR <len> <json>]` + 본문 | `STORED` · `OVERFLOWED` |
| `vget` | `vget <index> <id>` | `VALUE`+attr+`END` · `NOT_FOUND` |
| `vdel` | `vdel <index> <id>` | `DELETED` · `NOT_FOUND` |
| `VSIM VECTOR` | `VSIM VECTOR <index> <num> <bytes> <dim> [FILTER <n> <term>…]` + 본문 | `QUERY` 그룹들 + `END` |
| `VSIM KEY` | `VSIM KEY <index> <num> <key> [FILTER …]` | 위와 동일 |
| `vdrop` | `vdrop <index>` | `DROPPED` · `NOT_FOUND` |
| `vlist` | `vlist` | `INDEX …` 여러 줄 + `END` |
| `vstats` | `vstats` | 모듈 메모리 + `END` |

이름·키워드·열거값은 대소문자를 가리지 않는다. 좌표는 **공백으로 구분된 십진 텍스트**다.
에러는 요청 잘못이면 `CLIENT_ERROR`, 우리 쪽이면 `SERVER_ERROR`.

복구 중 조회는 `UNREADABLE`로 답한다. 엔진이 정의한 `ENGINE_UNREADABLE`이라 클라이언트
어휘가 늘지 않는다.

자세한 옵션과 예시는 [README](../README.md)에 있다.

## 4. 모듈 지도

두 갈래다. **`command`는 와이어, `handler`는 실행**이고, 백엔드 셋은 handler 안에 있다.
괄호는 테스트를 뺀 줄 수.

```
lib.rs (170)              C ABI — 등록과 memcached의 네 콜백
  command/                와이어: 명령행 하나 들어와 타입 하나 나간다   (순수)
    tokens (121)            토큰 배열을 읽고 응답 한 줄을 쓴다
    request/
      mod (147)             명령당 타입 하나
      parse (271)           토큰 → 요청
    pending (…)             본문을 기다리는 명령 — 연결 슬롯에 얹힘
    filter/
      mod (294)             FILTER 절의 작은 언어
      json (159)            ATTR에서 필드 하나 읽기 — 무할당
  handler/                명령을 수행하는 모든 것
    mod (…)                 run — Store를 만들고 명령을 배분
    access (126)            어느 그래프로 서빙할 것인가  ★
    coords (49)             십진 텍스트 → f32                          (순수)
    index (176)             vcreate, vdrop, vlist, vstats
    vector (122)            vadd, vget, vdel
    search (123)            vsim 두 형태
    quant (156)             한 좌표를 어떻게 표현하는가   (순수, 양쪽이 씀)
    arcus/                  저장 — 원본
      element (352)           그 바이트가 원소 어디에 놓이는가         (순수)
      engine/
        mod (141)             핸들 해소와 Store             (원시 포인터)
        error (85)            엔진 코드, 그중 무엇이 실패인가  ★
        map (107)             Map 아이템
        elem (313)            그 안의 원소들
      abi (211)               빌드-서버 vtable 대조
    usearch/                검색 — 캐시
      index (321)             용량과 락                      ★
      idmap (64)              String ↔ u64, 복구용 tombstone
      metric (70)             거리 척도
      threads (53)            예약 컨텍스트 불변식
    registry (110)          살아 있는 인덱스 목록과 VectorIndex
    recovery/               그래프가 Map과 어긋났을 때        ★
      mod (151)               인수·복구 스레드·토큰 발급
      metadata (56)           인덱스가 무엇인지 적은 예약 원소
  server (…)              memcached가 준 호스트 핸들 (SERVER_HANDLE_V1)
  error (142)             단일 에러 타입과 책임 소재
```

★ 표시가 최근 작업에서 논리가 바뀐 곳이다. **`handler/access` → `handler/recovery` →
`usearch/index`** 순으로 보면 복구 전체가 이어진다.

`quant`이 `arcus`·`usearch`와 형제인 이유는 **둘 다 쓰기 때문**이다. 어떤 종류가 존재하는지는
usearch의 `ScalarKind`가 정하고(`b1`의 비트 순서까지), 그것이 원소에서 몇 바이트를 차지하는지는
`arcus::element::Layout`이 정한다. 어느 한쪽에 넣으면 다른 쪽이 그 안을 들여다보게 된다.

`registry`와 `recovery`가 갈린 이유도 같다. 앞은 **지금 무엇이 살아 있는가**(이름 → 쌍)이고,
뒤는 **그 쌍이 어긋났을 때 무엇을 하는가**이다. 메타데이터 원소는 복구가 그래프를 다시 만들 때
쓰는 것이라 `recovery` 안에 있다. 의존은 한 방향이다 — `recovery`가 `registry`를 쓰고 그 반대는
없다.

### 왜 백엔드가 handler 안에 있나

**엔진에 닿는 유일한 길이 명령을 수행하는 모듈이 되도록** 하기 위해서다. `command`는
엔진도 인덱스도 이름조차 부르지 않는다 — 토큰을 값으로 바꾸고 끝난다. 그래서 파서를
서버 없이 시험할 수 있고, 문법 규칙이 사는 곳이 정확히 한 군데다.

파서가 필요로 하는 어휘 셋(`Quant`, `Metric`, `ATTR_BYTES`)만 크레이트 루트에 재수출한다.
명령행이 그 이름들을 부르기 때문이지 백엔드 내부를 알아야 해서가 아니다.

`error`는 루트에 남는다. 모두가 쓰는 공용 어휘라서다.

### 경계 두 개

**파싱은 상태를 건드리지 않는다.** `request`는 토큰을 `Line`/`Body`로 바꾸고 끝나고,
`handler`는 그 값을 받고 토큰을 보지 않는다. 디렉터리가 갈라져 있어 규칙이 아니라 구조로
지켜진다.

**원시 포인터는 `arcus::engine`에만 산다.** `Store::for_cookie`가 유일한 `unsafe`
생성자이고, 그 아래는 전부 `&self`를 받아 Rust 값을 돌려준다.

### 방향

`arcus/`는 "엔진을 쓰는 모든 것"이 아니라 *벡터가 arcus에 저장되는 방식*이다. `element`는
엔진 호출을 하나도 안 하지만 그 모양을 결정하는 건 arcus다 — 크기 상한이
`max_element_bytes`이고, 고정 130바이트 오버헤드(헤더 2 + ATTR 128)도 arcus가 정한다.

`usearch/index`가 `arcus/element`에 의존하는 것도 같은 이유다. 인덱스는 저장된 레이아웃으로
구성되고 스토어가 든 바로 그 바이트를 받는다. 그래서 복구가 무손실이고, 의존 방향이
고정된다 — **캐시가 스토어를 알고 그 반대는 없다.**

## 5. 요청 흐름

memcached는 확장에 콜백 넷을 준다. 넷 다 쓴다.

| 콜백 | 역할 |
|---|---|
| `get_name` | 확장 식별 |
| `accept` | 명령 점유, 본문 바이트 수 결정 |
| `execute` | 실행하고 응답 |
| `abort` | 전송 도중 죽은 명령의 상태 해제 |

대부분은 명령행에서 바로 `execute`로 끝난다. `vadd`와 `VSIM VECTOR`는 바이트 수를 선언하고
좌표를 뒤이어 보낸다(`nread`). 이 둘은 `accept`가 버퍼를 등록하고 `execute`가 **빈 토큰
배열**로 한 번 더 호출된다 — 그게 본문이 도착했다는 신호다.

```
클라이언트 ──▶ accept ──▶ (본문 수신) ──▶ execute(빈 토큰) ──▶ 응답
                 │                            │
                 │                            ├─ command::parse()  ─▶ Request
                 │                            └─ handler::run(Request)
                 └─ 파싱 실패도 Result로 pending에 실어 보낸다
```

**`command`와 `handler`는 서로를 부르지 않는다.** `lib.rs`가 하나를 부르고 그 결과를
다른 하나에 넘긴다. 둘이 공유하는 건 `Request` 타입뿐이다.

```rust
let outcome = unsafe { command::parse(cookie, &tokens) }
    .and_then(|request| unsafe { handler::run(cookie, request) });
```

### 두 콜백 사이에 상태를 어디 두나

`accept`와 `execute`는 별개의 호출이고 공통점은 **연결 cookie 하나**다. `accept`가 파싱한
것을 `execute`가 찾아야 하는데, memcached는 그 자리를 하나 준다 — `conn`마다 `void *` 하나,
`store_engine_specific`/`get_engine_specific`으로 넣고 꺼낸다.

연결은 만들어질 때 한 스레드에 묶이고(`thread.c:361`, `assert(c->thread == NULL)`) 옮겨가지
않으므로, 그 슬롯을 두 스레드가 만질 일이 없다. **곁다리 표도 락도 필요 없다.**

회수는 `abort`가 보장한다. `conn_close`가 `ascii_cmd`가 걸려 있으면 `abort`를 부르고
(`memcached.c:979`), 그 다음에야 `conn_cleanup`이 슬롯을 비운다(`:950`). 전송 도중 연결이
죽어도 포인터를 돌려받는다.

이름이 `engine_specific`인 것은 원래 스토리지 엔진 몫이라서다. 이 트리의 어느 엔진도 쓰지
않는 것을 확인하고 썼다 — 나중에 엔진이 쓰기 시작하면 서로 덮어쓰므로, 그때는 곁다리 표로
되돌려야 한다.

### `accept`는 잘못된 명령행을 거부하지 않는다

응답 핸들러가 없어 클라이언트에게 답할 수 없다. 여기서 거부하면 좌표가 읽히지 않은 채
남고 memcached가 그것을 **다음 명령행으로** 파싱한다 — 잘못된 요청 하나가 그 연결의
나머지를 망친다.

그래서 바이트 수만 보고, 나머지 파싱 실패는 대기 항목에 `Result`로 저장했다가 본문을 다
흘려보낸 뒤 핸들러가 보고한다. 거부는 **바이트 수 자체를 못 읽을 때**만 한다.

### 토큰과 ATTR

memcached의 토크나이저는 공백으로 자르면서 **토큰을 끝내는 공백을 제자리에서 `'\0'`으로
덮어쓴다.** 그래서 쪼개진 문자열을 되붙이려면 NUL을 공백으로 되돌려야 하는데, NUL은
클라이언트가 보낼 수도 있는 바이트라 복원이 모호하다.

그래서 **ATTR JSON은 인자 하나**로 받는다. 공백이 있으면 토큰이 더 생기고 그 사실만으로
거부한다. 잃는 건 없고 오히려 공백 예산을 안 나눠 쓰므로 128바이트 전 구간을 쓸 수 있다.
`FILTER`도 같은 이유로 항마다 토큰 하나다.

토큰 **개수** 한계는 우리가 지키지 않는다. `process_extension_command`가 `accept`를 부르기
전에 거부하므로(`memcached.c:10189`, `ntokens == MAX_TOKENS`) 확장에 도달하는 실토큰은
최대 28개다. 한때 이 모듈에도 같은 검사가 있었지만 도달 불가능한 죽은 코드였다.

### 모듈 지표가 자체 명령을 갖는 이유

memcached는 자기가 인식에 실패한 명령만 확장에게 묻는다. `stats` 같은 내장 명령은 오지
않으므로 arcus를 고치지 않고는 `stats vector`를 추가할 수 없다. 그래서 `vstats`가 따로 있다.

## 6. 저장 형식

인덱스 하나가 Map 아이템 하나, 벡터 하나가 Map 원소 하나다. 원소는 두 종류인데 **형식이
서로 다르다.**

### 벡터 원소 — 고정 배치

```
 off  0            2               130
     +------------+---------------+---------------+
     | alen u16   | ATTR 128B     | 양자화된 벡터 |
     +------------+---------------+---------------+
```

`alen`은 ATTR JSON의 실제 길이다. `vget`이 클라이언트가 저장한 바이트를 그대로 돌려주려면
어디서 끝나는지 알아야 하고, 그게 이 2바이트가 있는 이유다 — 검색 필터는 `}`에서 멈추므로
필요 없고, `vadd`는 클라이언트가 길이를 준다.

ATTR가 고정 128바이트인 것은 벡터가 **상수 오프셋**에서 시작하게 하려는 것이다. 그래야
`attr_of`가 계산 없이 자르고, 디코딩이 차원만 알면 벡터를 뜯을 수 있다.

**그 밖에는 아무것도 없다.** 매직도, 버전도, `dim`·`quant`도, 레코드 종류도 없다. 읽히지
않는 필드는 두지 않는다.

- `dim`·`quant` — 쓰기가 인덱스 자신의 레이아웃에서 값을 가져오고 디코딩도 같은 곳에서
  오프셋을 얻으므로, 원소에 적어두고 대조해봐야 항상 참이다. 필요한 곳은 메타데이터 원소
  하나뿐이라 그쪽에 있다.
- 레코드 종류 — 어느 종류를 읽는지는 필드명이 이미 말한다. 벡터는 클라이언트가 준 id로,
  메타데이터는 `AV META`로 지정해 읽는다.
- 매직 — `mop insert`로 들어온 바이트를 걸러냈지만, 앞 두 바이트를 맞춰 넣으면 그대로
  통과한다. 절반만 막는 검사였고, 그 경로 자체가 [미해결.md §2](미해결.md)에 "막을 수
  없다"고 적힌 구멍이다.
- 버전 — 아래.

### 메타데이터 원소 — 값 전체가 JSON

```
필드명   AV META
값       {"dim":2,"quant":"f32","metric":"cos","m":0,"efc":0,"efs":0,
          "owner":"27c6fcea7ae95557"}
```

헤더가 없다. 벡터 원소는 뒤에 벡터가 붙으므로 어디서 ATTR가 끝나는지 적어야 하지만, 이건
**값이 JSON뿐이라 엔진이 아는 원소 길이가 곧 끝**이다. `map_elem_get`은 필드명으로 찾아
그만큼을 돌려준다.

덕분에 128바이트 상한도 없다. 인덱스당 하나뿐이라 길어져도 무방하고, 키를 추가하는 것이
형식 변경이 되지 않는다.

`m`·`efc`·`efs`가 0이면 usearch 기본값을 쓰라는 뜻이다.

**필드명의 공백이 핵심이다.** 모듈이 검사해서 막는 것이 아니라 ASCII 프로토콜로 **표현이
불가능**하다.

| 경로 | 결과 | 근거 |
|---|---|---|
| `mop insert` | 생성 불가 | 필드가 명령행 토큰이고 토큰은 공백으로 분리된다 |
| `mop get`·`mop delete` | 지정 불가 | 공백 구분 목록을 `numfields`와 대조하므로 항상 2개로 쪼개져 `EBADVALUE` |
| 바이너리 프로토콜 | 경로 없음 | LOP/SOP/BOP opcode만 있고 MOP는 없다 |
| `vadd` | 충돌 불가 | id도 명령행 토큰이다 |

전체 덤프(`mop get <key> 0 0`)로는 보이므로 운영 관측성은 유지된다. 엔진은 필드를 길이와
원시 바이트로 다룬다 — 명령 로그, 체크포인트 스냅숏, 복제 change-set 전부 — 그래서 공백이
깨질 텍스트 왕복 구간이 없다.

`maxcount`·`exptime`은 넣지 않는다. 엔진이 아이템 속성으로 이미 복제·영속화하므로, 복사해
두면 `setattr`이 두 값을 어긋나게 만든다.

### 형식 버전이 없다

아이템 플래그는 `0x4156_0000`뿐이고, 원소에도 버전이 없다. 그래서 **저장 형식을 바꾸면
구 버전 빌드는 새 인덱스를 손상으로 판정하고 Map을 지운다.**

버전을 나중에 넣어도 그 넣는 변경 자체는 못 지킨다 — 버전 없는 빌드를 소급해 고칠 수 없기
때문이다. 아직 배포 전이라 위험이 없어서 두지 않았고, 배포 후에 형식을 바꿔야 한다면 그
전에 버전을 먼저 넣는 릴리스가 필요하다. [미해결.md §4](미해결.md)에 자리 선택까지
적어두었다.

### 원소 끝의 `\r\n`

arcus는 컬렉션 원소 크기를 **종결자 포함으로** 잡는다. 내장 명령이 클라이언트 바이트를
원소 안으로 그대로 `nread`하기 때문이다. 되읽는 곳은 없다 — `mop get`은 `nbytes - 2`를 값
길이로 보고하고 나머지를 줄 끝으로 내보낸다.

이 모듈은 `nread`할 수 없다. 와이어에는 십진 텍스트가 오고 원소에는 양자화된 바이트가
들어가서 크기도 내용도 다르다. 그래서 종결자를 직접 쓴다. 안 쓰면 엔진이 길이를 두 바이트
짧게 넘기고 **벡터의 마지막 두 바이트를 종결자로 오인한다.**

### 소유 토큰

`RandomState`로 만든다. 프로세스당 한 번 OS에서 씨앗을 받고 호출마다 키를 전진시키므로,
고정값을 새 해셔에 통과시키면 조율 없이 서로 다른 `u64`가 나온다.

이름 기반은 전부 실패한다 — `pid`는 컨테이너마다 1, 호스트명은 보장이 아니라 관례,
`getsockname`은 *연결의* 로컬 주소라 로컬 헬스체크가 복구를 유발하면 어디서나 `127.0.0.1`이
된다.

무엇을 판정하는 값인지는 §7.2에 있다.

### 손상 판정

메타데이터를 못 읽으면 손상이고, 손상이면 Map을 지운다. metric과 HNSW 파라미터 없이는 다시
인덱스가 될 수 없으므로, 남겨두면 이후 모든 명령이 성공할 수 없는 복구를 반복한다. 지우기
때문에 실패 backoff도 필요 없다 — 재시도할 대상이 없다.

지우기 전에 `looks_like_index()`로 아이템 플래그를 본다. 우리 것이 아닌 Map은 건드리지
않는다.

## 7. 복구 로직

### 7.1 왜 필요한가

arcus EE의 복제는 **Map 원소는 나르지만 그래프는 안 나른다.** switchover로 승격된 노드는
벡터를 다 갖고도 탐색할 그래프가 없다.

더 어려운 건 강등됐다 다시 승격된 노드다. 프로세스가 죽은 적이 없어 마스터 시절 그래프를
그대로 들고 있는데, 그 사이 상대 노드의 쓰기가 **확장보다 하위 계층인 복제 경로**로 이
노드의 Map에 반영됐다. 통보받을 수단이 없다. 증상은 조용한 불일치다.

```
Map 원소 수      4
vlist(그래프)    3
vget  v4         정상 반환   — Map을 직접 읽으므로
vsim  (v4 방향)  v4 누락     — 거리 0인 벡터가 결과에 없음
```

**역할(master/slave) 폴링으로는 못 잡는다.** A→B→A에서 A의 역할은 전후 모두 `master`라
어떤 주기로도 변화가 없다. 달라진 건 역할이 아니라 그래프이므로, 판정 근거는 그래프마다
구별되고 양쪽 노드가 다 볼 수 있는 곳 — Map — 에 있어야 한다.

퍼시스턴스(`ENABLE_PERSISTENCE`)도 같은 상황을 만든다. 재시작 후 체크포인트와 명령
로그로 아이템이 복원되면 Map은 살아 있고 그래프는 비어 있다. 그래서 `cfg(recovery)`는
복제 **또는** 퍼시스턴스에서 켜진다.

### 7.2 판정 — `owner` 하나

메타데이터 원소의 `owner` 토큰을 메모리의 것과 비교한다. `0`은 예약값이라 발급되지 않으며
그것으로 "복구 중"을 표현한다.

| Map | 메모리 | 의미 | 처리 |
|---|---|---|---|
| 토큰 | 같은 토큰 | 이 그래프가 이 Map을 설명한다 | 정상 |
| 토큰 | 다른 값 | 다른 노드가 서빙했다 | 인수 → 복구 |
| `0` | `0` | 이 노드가 복구 중 | 읽기 `UNREADABLE`, 쓰기 통과 |
| `0` | 토큰 | 복구하던 노드가 사라짐 | 인수 → 복구 |

3행과 4행의 구분이 핵심이다. 복구 중인 노드만 메모리에도 `0`을 들고 있으므로, "Map은 `0`
인데 메모리는 토큰"은 복구 주체가 소멸했다는 뜻이고, 그때 남은 그래프야말로 못 믿을
그래프다.

**역할을 묻지 않는다.** 토큰이 어긋난 레플리카는 인수를 시도하는데, 인수는 아무것도 버리기
전에 Map에 stamp부터 하고 그건 쓰기라 엔진이 `ENGINE_REPL_SLAVE`로 거부한다. 토큰이
일치하는 레플리카의 그래프는 실제로 자기 Map을 정확히 설명한다 — 마스터가 원소보다 토큰을
먼저 쓰고 복제가 그 순서를 보존하므로, "일치하는 토큰 + 낡은 데이터"는 성립하지 않는다.

의도적 귀결: 레플리카는 토큰이 일치하는 동안 읽기를 답하고, 마스터가 인수하는 순간 답하지
않는다. 읽기 분산에 쓸 거면 이 성질을 전제해야 한다.

### 7.3 3단계

```
워커 스레드   ① 메모리에 "복구 중" 표시    ← 이 시점부터 읽기가 UNREADABLE
              ② Map에 owner = 0 stamp     ← 아직 아무것도 안 버렸다
              ③ 그래프를 비우고 큐에 등록
                 │
복구 스레드   ④ 메타데이터 읽기(손상 판정)
              ⑤ 원소 수만큼 용량 사전 확보
              ⑥ get_all → 원소마다 add_unless_known
              ⑦ "다 채웠다" 표시.  쓰기는 한 줄도 안 한다
                 │
워커 스레드   ⑧ (다음 명령) Map 재확인 → 새 토큰 발급·기록 → 조회 재개
```

**①②③의 순서가 리뷰 포인트다.** ②가 ③보다 앞이라 레플리카에서 stamp가 거부돼도 그래프가
남는다. 순서가 반대였다면 애초에 성공할 수 없는 쓰기 때문에 그래프를 잃고, 인덱스가 큐에도
없이 복구 중으로 남는다.

**복구 스레드가 쓰기를 안 하는 이유.** 연결 없는 스레드에는 cookie가 없고 엔진의 쓰기 경로는
그것을 역참조한다. `do_check_master_switchover_done`이 `get_thread_index(cookie)`를 널 검사
없이 호출하므로, switchover 중인 마스터에서 분리 스레드가 쓰면 프로세스가 죽는다 — 그리고
switchover 중이라는 건 복구가 돌 개연성이 가장 높은 시점이다. 실제로 SIGSEGV로 서버가
내려갔던 건이다.

읽기는 안전하다. `ACTION_BEFORE_READ`는 `ENABLE_MIGRATION` 없이는 비어 있고,
`rp_after_check`는 thread-local cookie가 널이면 즉시 반환하며, arcus 자신도 슬레이브
switchover 검사를 cookie 없이 호출한다.

**그래프를 미리 비우는 이유.** 새 그래프를 옆에 만들면 복구 중에도 서빙할 수 있지만 메모리가
두 배다. usearch는 비어 있지 않은 인덱스당 약 16.8 MB에서 시작하므로 1024차원 `i8` 100만
개면 약 1 GB를 두 벌 든다. 이미 낡은 것으로 판명된 그래프에서 답하는 것보다 `UNREADABLE`이
정직하다.

### 7.4 복구 중에도 쓰기를 받는다

큰 인덱스의 복구는 수 분이고, 그동안 쓰기를 거부하면 switchover가 쓰기 장애로 관측된다.
그 대가로 하나의 그래프에 writer가 둘이 되고, 누가 이기는지는 `AnnIndex`가 양쪽 모르게
정한다.

| 순서 | 위험 | 해소 |
|---|---|---|
| 스냅숏 이후 삽입 | 복구가 옛 값으로 새 값을 덮음 | `add_unless_known` — 이미 아는 id는 건너뜀 |
| 스냅숏 이후 삭제 | 스냅숏에 남아 되살아남 | tombstone — 복구 종료 시 일괄 해제 |

두 판정 모두 **삽입을 지키는 그 락 아래서** 이뤄진다. §9.

### 7.5 실패

| 상황 | 응답 | Map |
|---|---|---|
| 메타데이터 손상(부재·매직·파싱) | `NOT_FOUND` | **삭제**, 로그 |
| 모르는 상위 버전 | `NOT_FOUND` | 보존 |
| 그 외 복구 실패 | `SERVER_ERROR` | 보존, 다음 명령이 재시도 |
| 레플리카에서의 인수/쓰기 | `SERVER_ERROR …replica…` (엔진 발) | 보존 |

**지우는 실패는 손상 하나뿐이다.** metric과 HNSW 파라미터가 없으면 다시 인덱스가 될 수
없으므로, 남겨두면 이후 모든 명령이 성공 불가능한 복구를 반복한다. 지우니까 실패 backoff도
필요 없다 — 재시도할 대상이 없다.

**단, ABI 불일치가 걸린 뒤에는 지우지 않는다.** vtable이 어긋나면 엔진의 "원소 없음"을 믿을
수 없고, 그걸 손상으로 읽으면 빌드 실수가 데이터 삭제가 된다. §11.

그 외 실패는 레지스트리 항목만 버린다. 다음 명령이 빈 그래프를 새로 만들고 **무조건** 인수
하므로 복구가 재개된다. 이 "무조건"이 없으면 Map은 `0`인데 레지스트리는 비어 있는 상태가
"누가 복구 중"으로 보여 아무도 복구를 걸지 않는 교착이 된다.

### 7.6 복구가 꺼진 빌드

`resolve`는 레지스트리 조회 하나다. 그래프보다 오래 사는 게 없으니 레지스트리가 모르는
이름은 존재하지 않는 이름이다. 남아 있는 Map은 건드리지 않고 지목한다.

```
vcreate orphan 2
→ CLIENT_ERROR a Map already exists at 'orphan' and this build cannot rebuild
  an index from it; drop it with 'vdrop orphan' and create it again
```

메타데이터 원소는 복구가 꺼져 있어도 그대로 쓴다. 온디스크 형식을 조건부로 만들지 않기
위해서고, 덕분에 복구를 켠 빌드로 바꾸면 그 Map을 그대로 되살릴 수 있다.

## 8. 명령별 동작과 안전성

밑에 깔린 규칙은 §1의 것 하나다 — **Map 먼저, 그래프 나중.**

### 공통 전처리 `resolve`

```
① 메타데이터 읽기      부재·복호화 실패 → 손상 판정
                       상위 버전       → NOT_FOUND (변경 없음)
② 손상이면             flags가 우리 것 → Map 삭제 + 등록 해제
③ 레지스트리 조회      없으면 메타데이터로 빈 그래프 생성 (fresh 표시)
④ fresh || 토큰 불일치 → 인수 후 반환
⑤ 복구 완료 대기분     → 토큰 발급·기록, 정상 전환
```

### 명령별

| 명령 | 쓰기 1 | 쓰기 2 | 사이에서 죽으면 | 누가 고치나 |
|---|---|---|---|---|
| `vcreate` | Map 아이템 생성 | 메타데이터 기록 | **빈 Map** | 다음 `resolve`가 손상 판정 → 제거 |
| `vadd` | Map 원소 | 그래프 삽입 | 검색에 안 보이는 벡터 | 다음 복구 |
| `vdel` | Map 원소 삭제 | 그래프 삭제 | 그래프의 유령 노드 | `vsim`이 결과에서 제외, 복구가 정리 |

세 경우 모두 **남는 쪽이 원본이고 잃는 쪽이 캐시다.** 이게 순서를 고정한 근거이고, 복구가
항상 Map → 그래프 단방향인 근거이기도 하다.

`vcreate`의 위험 구간이 안전한 이유는 순서에서 나온다. 원소는 메타데이터 이후에만 들어올
수 있으므로 "데이터를 가진 Map + 메타데이터 없음"은 생기지 않는다. 지워지는 건 항상 빈
Map이다. 그래프 객체를 Map보다 **먼저** 만드는 것도 같은 이유 — 지원되지 않는 metric이면
거기서 실패해야 빈 Map을 안 남긴다.

**기존 Map을 지우지 않는다.** 복제가 배달했거나 영속화가 복원한 것일 수 있다. 예전 구현은
자기가 만들지 않은 Map을 고아로 보고 지운 뒤 다시 만들었는데, 승격된 노드에서 복제된 벡터를
전부 날렸다.

`vadd`의 용량 검사가 기존 id인지 **먼저** 보는 것도 의도다. 기존 id 갱신은 원소 수를 안
늘리므로 정원이 찬 인덱스에서도 통과해야 한다. `max_element_bytes`는 런타임에 낮출 수 있어
만들 때 들어가던 게 지금은 안 들어갈 수 있으므로 다시 검사한다.

`vget`은 그래프를 **한 번도 보지 않는다.** 항상 원본을 읽으므로 복제가 방금 배달한 원소도
그대로 읽힌다. 복구 중에 막는 건 정확성이 아니라 일관성 때문이다 — `vget`만 답하면 같은
노드의 두 조회 경로가 다른 세계를 보여준다.

## 9. 동시성

락은 두 개이고 서로 독립이며 역할이 다르다.

| 락 | 무엇을 배제하나 | 획득 |
|---|---|---|
| 그래프 `RwLock<Index>` | 용량 재할당 대 나머지 전부 | 삽입·삭제·탐색은 **읽기**락 |
| id 매핑 `RwLock<IdMap>` | 매핑의 판정과 실행 | 삽입·삭제는 **쓰기**락, 탐색은 노드당 짧은 읽기락 |

그래프의 동시 변경은 usearch가 내부에서 처리한다. 그래서 그래프 락은 동시성 장치가 아니라
**재할당 배제 장치**다. 라이브러리가 이미 하는 일을 밖에서 또 잡으면 동시성만 깎인다.

**삽입과 삭제의 경합은 id 매핑 락 하나가 해소한다.** 둘 다 판정과 실행을 쪼개지 않고 매핑
락을 배타적으로 쥔 채 수행하므로, "존재 확인 후 삽입 전에 삭제가 끼어드는" 구간이 없다.

```rust
// remove                                  // add_unless_known
let index = self.inner.read();             let index = self.inner.read();
let mut ids = self.ids.write();  //←같은 락→ let mut ids = self.ids.write();
let key = if rebuilding {                  if ids.is_known(id) { return Ok(false) }
    ids.forget_tombstoned(id)              let (key, _) = ids.intern(id);
} else { ids.forget(id) };
index.remove(key)?;                        self.typed_add(&index, key, vector)?;
// 여기까지 락을 쥔 채                      // 여기까지 락을 쥔 채
```

| 먼저 잡는 쪽 | 경과 | 최종 상태 |
|---|---|---|
| 삭제 | tombstone이 남고 뒤따르는 삽입이 `is_known`에서 걸림 | 삭제됨 |
| 복구의 삽입 | 벡터가 들어가고 뒤따르는 삭제가 제거 | 삭제됨 |

**락 순서 규칙(그래프 → 매핑)은 정확성이 아니라 교착 회피용이다.** 탐색 술어가 그래프 락
아래에서 매핑 락을 잡으므로 나머지를 거기 맞췄다.

**대가.** 모든 삽입·삭제가 매핑 락을 usearch 호출까지 쥐므로 **쓰기는 인덱스 단위로
직렬화된다.** id가 달라도 마찬가지다. 탐색은 매핑 락을 노드당 짧게만 잡아 서로 간섭하지
않는다. usearch가 지원하는 동시 삽입을 못 쓰는 셈인데, 그게 tombstone의 판정과 실행을 한
락 아래 붙여둔 값이다. 복구가 용량을 미리 일괄 확보하는 것도 이 직렬화 구간을 짧게 하려는
조치다.

### usearch 스레드 컨텍스트 함정

usearch의 Rust 바인딩은 항상 `any_thread()`로 들어가고 이건 **고정 크기 풀**에서 컨텍스트를
꺼낸다. 비면 블록하지 않고 "Reserve capacity ahead of insertions!"로 실패한다. arcus는 어떤
상수도 가정할 수 없는 수의 워커를 허용하므로(`-t`가 64를 넘어도 경고만), 정확성을 워커 수에
기댈 수 없다.

```
동시 진입 <= 허가 수 == 예약 컨텍스트 수   ⇒   pop은 실패할 수 없다
```

모든 진입이 세마포어에서 허가를 받는다. 남는 워커는 실패가 아니라 대기한다. `THREAD_SLOTS`
= 64는 정확성에 걸린 값이 아니고 — 불변식은 어떤 값에서도 성립한다 — 처리량과 메모리의
절충이다.

## 10. 검색 경로

```
vsim
 └─ for_read              복구 중이면 UNREADABLE
 └─ ann.search(q, k, accept)
      └─ accept(key)      노드마다: id 조회 → Map에서 ATTR 읽기 → FILTER 평가
 └─ 히트마다              Map에서 원소를 다시 읽어 응답 구성
 └─ 걸러낸 뒤 개수를 세어 QUERY 헤더에 기록
```

**그래프가 후보를 내고 Map이 결정한다.** 모든 히트를 응답에 넣기 전에 Map에서 되읽으므로,
그래프는 아는데 Map에는 없는 원소는 결과에서 그냥 빠진다 — `vadd`/`vdel`이 두 번째 쓰기에서
실패해 남긴 유령 노드가 여기서 흡수된다. 개수를 마지막에 세는 것도 같은 이유다.

**`for_read`가 반드시 필요한 이유.** usearch에는 "아직 준비 안 됨"이라는 상태가 없다. 절반만
채워진 그래프에 질의하면 아무 불평 없이 그 절반에서 답을 만들어 준다. 거부는 이쪽에서 해야
한다.

술어는 방문 노드마다 호출되므로 싸야 한다. **ATTR를 `serde_json`으로 파싱하지 않는 이유가
이것이다** — 실측으로 제자리 스캔 30.5ns 대 `serde_json::from_slice` 442.6ns, 14.5배다.
파싱은 문서 하나를 트리로 만들면서 키·값마다 할당하고, 스캔은 찾는 필드에서 멈추며 원본을
가리키는 슬라이스를 돌려준다. 후보를 300개 방문하는 질의라면 9µs 대 133µs이고, 뒤쪽은
질의 전체(k=10에 65µs)보다 크다.

첫 노드 이후로는 아무것도 할당하지 않고,
`id_of`는 빌림이 아니라 `Arc`를 돌려준다 — 술어가 이어서 엔진 호출을 하는데 그동안 매핑
락을 쥐고 있으면 모든 검색이 모든 삽입 뒤에 줄을 선다.

## 11. vtable은 단일 ABI가 아니다

`engine_interface_v1`은 **오프셋으로 호출되는데** arcus에는 레이아웃이 하나가 아니다. 소스
트리가 일부를 정하고(`JHPARK_OLD_SMGET_INTERFACE`는 OSS `types.h`에만 있다), `configure`가
나머지를 정한다. 잘못된 조합으로 빌드한 라이브러리는 그 오프셋에 앉은 아무 함수나 부른다.

이 크레이트가 부르는 API 중 그 블록 안에 있는 건 하나도 없다. 플래그가 바꾸는 건 우리 호출
두 개가 *어디에 앉느냐*다.

**런타임 판별자가 없다.** `ENGINE_HANDLE::interface`는 모든 변종에서 1이고, 엔진은 기능
목록을 노출하지 않으며, 그런 걸 보고할 만한 것 자체가 정렬이 의심되는 그 vtable을 통해
도달된다. 그래도 두 사실은 얻을 수 있다.

- **바인딩이 어느 트리에서 왔는지** — 빌드 시점에 헤더 *텍스트*로. OSS 헤더는 `rp_cmd`를
  `#ifdef` 안에서조차 언급하지 않으므로 어떤 define을 줬는지에 좌우되지 않는다.
- **서버가 어느 트리인지** — `server_version()`. `SERVER_CORE_API`에 있는데 이건
  `get_server_api`로 도달하는 다른 구조체이고 앞 17개 멤버가 두 트리에서 동일하다. 엔진
  vtable이 아무리 어긋나 있어도 안전하게 부를 수 있다. EE는 버전에 홀로 선 `E`를 찍는다
  (`0.9.5-E-139`), OSS는 아니다(`1.16.1`).

검사는 셋이고 순서가 중요하다.

1. **교차 트리를 먼저 거부.** 바로 다음 호출에서 죽는 조합이라서다 — `get_config`가 OSS
   레이아웃에서 슬롯 60이고 EE에서는 `cachedump`다. *기능*이 아니라 *트리*를 비교하는 게
   오탐을 없애는 핵심이다. 복제 없이 빌드한 EE 트리는 실재하는 구성이고 복제 있는 것과 같은
   버전을 보고하므로, 기능 기반 규칙은 그걸 거부해버린다.
2. **널 멤버 거부.** arcus는 멤버를 미설정으로 출하하지 않는다.
3. **오작동하는 호출을 지목.** 널 검사에는 구멍이 있다 — 잘못된 오프셋에서 읽은 멤버는 대개
   다른 진짜 함수에 떨어져 포인터는 유효하고 결과만 틀리다. `put_elem`이 그 경우를 잡는다:
   엔진이 원소를 할당해 놓고 그것을 서술하지 못하는 조합은 런타임 조건이 아니다.

**3번은 래치를 건다.** 한 번 걸리면 이후 모든 벡터 명령이 실행되지 않고 같은 에러로 답한다.
메시지 품질 때문만이 아니다. vtable이 어긋나면 엔진의 대답을 믿을 수 없는데, 그중 "이
원소가 없다"를 복구 경로가 손상으로 읽고 **Map을 지운다.** 앞에서 막지 않으면 빌드 실수가
데이터 삭제가 된다.

```
ArcVector: ENGINE ABI MISMATCH — get_elem_info did not describe the element it allocated.
vcreate → SERVER_ERROR engine ABI mismatch …
vadd    → SERVER_ERROR engine ABI mismatch …
```

근본 해결은 여기 없다. EE가 멤버를 중간에 끼우지 않고 `errinfo` 뒤에 덧붙였다면 공통
접두부가 안정적이었을 것이고 라이브러리 하나로 모든 빌드를 감당했을 것이다.

## 12. 에러

핸들러는 `Result<Reply, Error>`를 돌려주고 크레이트 루트의 한 곳이 ASCII 응답으로 바꾼다.
`CLIENT_ERROR`인지 `SERVER_ERROR`인지는 에러 자신에게서 따라 나오므로 호출부가 정할 일이
없다.

| 상황 | 응답 |
|---|---|
| 잘못된 명령행, 범위 밖 인자 | `CLIENT_ERROR` |
| 인덱스 없음 | `NOT_FOUND` |
| 복구 중 읽기 | `UNREADABLE` (엔진의 `ENGINE_UNREADABLE`) |
| 레플리카에서의 쓰기 | `SERVER_ERROR` (엔진이 준 문구) |
| ABI 불일치 | `SERVER_ERROR engine ABI mismatch` |
| 인덱스가 가득 참 | `OVERFLOWED` |

`EWOULDBLOCK`은 **실패가 아니다.** 동기 모드 복제 마스터에서 `rp_after_check`는 연산이 이미
성공한 뒤에 돌면서 호출자를 슬레이브 ack의 대기자로 등록한다. "아직 답하지 말라"는 뜻이지
"일어나지 않았다"가 아니다. 이걸 실패로 읽는 것이 이 모듈이 서버를 죽이던 방식이다 —
`put_elem`이 엔진이 방금 링크한 원소를 해제하고 `map_elem_free`가 `elem->linked == 0`을
단언하며 죽었다.

아직 없는 건 **기다림**이다. 그래서 벡터 쓰기는 동기 마스터에서도 비동기 내구성으로 답한다.
서버 API에 `waitfor_io_complete`가 있는데도 왜 못 쓰는지, 고치려면 뭐가 필요한지는
[미해결.md §1](미해결.md)에 있다.

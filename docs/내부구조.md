## 1. 무엇인가

arcus-memcached 서버는 **ASCII 프로토콜 확장**을 적재할 수 있다. 콜백 서술자를 등록하고 그
대가로 명령어 이름을 점유하는 공유 라이브러리다. ArcVector가 그런 확장이고, 서버 프로세스
*안에서* 서버의 워커 스레드 위에 얹혀 돌며, memcached 자신이 쓰는 것과 같은 `engine_interface_v1`
vtable로 스토리지 엔진과 이야기한다.

인덱스는 두 계층이다.

```
질의 ──▶ usearch HNSW 그래프 ──▶ 근접 키 ──▶ arcus Map ──▶ 속성
         (탐색 가속)                          (원본)
```

인덱스 하나가 Map 아이템 하나(키 = 인덱스 이름), 벡터 하나가 Map 원소 하나(필드 = 벡터 id).
Map을 고른 이유는 키 조회·복제·TTL이 이미 그 경로에 있기 때문이다.

**전체를 지배하는 규칙이 하나 있다.**

> usearch 인덱스는 언제든 Map으로부터 재구성 가능한 **캐시**다.
> Map에 없으면 존재하지 않는다.

재시작, 축출, TTL 만료, 복제 슬레이브가 전부 여기서 따라 나온다 — 네 가지 사례가 아니라
하나다. 그리고 **모든 쓰기는 Map을 먼저, 그래프를 나중에** 바꾼다. 그 순서 때문에 "그래프에는
있는데 Map에는 없다"는 상태가 구조적으로 생기지 않는다.

## 2. 빌드와 실행

### 2.1 빌드

```sh
cargo build --release          # → target/release/libarcusv.{so,dylib}
```

`build.rs`가 `include/`의 arcus 헤더에 bindgen을 돌리므로 libclang이 필요하고, usearch가
C++ 코어를 컴파일하므로 C++17 툴체인도 필요하다. 생성물은 `OUT_DIR`로 나가 소스 트리를
건드리지 않는다.

### 2.2 피처 — 축이 둘이다

이 크레이트의 피처는 **기능 요청이 아니라 memcached 서버에 대한 사실 선언**이다. 켠다는
건 "내가 붙일 서버가 그렇게 빌드돼 있다"는 뜻이므로, 서버의 `config.h`를 보고 맞춰야 한다.

**축 1 — vtable 레이아웃.** 선택이 아니다. 틀리면 엉뚱한 함수를 부른다.

| 피처 | 효과 |
|---|---|
| `replication` | `engine_interface_v1`에 멤버 7개 추가 |
| `migration` | 멤버 6개 추가 |
| `cluster-aware` | `SERVER_CORE_API`에 2개 추가 |

피처 이름은 서버의 `configure` 플래그에서 arcus가 붙이는 `ENABLE_` 접두사만 뗀 것이다.
`build.rs`가 그 접두사를 도로 붙여 bindgen에 넘기므로 — `replication` → `-DENABLE_REPLICATION`
— 이름을 두 군데 적지 않는다. `ENABLE_`은 우리가 고른 이름이 아니라 헤더가 `#ifdef`로
검사하는 매크로라서 그대로 정의해야 한다.

**축 2 — 복구를 돌릴 것인가.** 배포 선택이다.

| 피처 | ABI 영향 | 의미 |
|---|---|---|
| `persistence` | **없음** | 서버가 재시작 때 아이템을 복원한다 |

`ENABLE_PERSISTENCE`는 `engines/default/*.h`에만 있고 `include/memcached/`에 닿지 않아
define을 넘기지 않는다. 순수한 사실 선언이다.

`build.rs`는 **replication이나 persistence 중 하나라도 켜지면** `cfg(recovery)`를 켠다.
둘 다 없다는 건 그래프보다 오래 사는 것이 없다는 뜻이므로, 소유 토큰 비교도 명령마다의
메타데이터 읽기도 복구 스레드도 전부 컴파일되지 않는다. §7.6.

```sh
cargo build --release --features replication
cargo build --release --features replication,persistence
cargo build --release                                    # 복제도 퍼시스턴스도 없는 서버
ARCVECTOR_ENGINE_INCLUDE=/path/to/tree/include cargo build --release   # 다른 헤더 트리
```

### 2.3 적재와 확인

```sh
memcached -E .../default_engine.so -X .../libarcusv.so
```

적재 직후 첫 엔진 호출 때 지문 한 줄이 로그에 나온다. **왼쪽이 서버, 오른쪽이 빌드**다.

```
ArcVector: memcached 0.9.5-E-139, built for ee tree, 76 members,
           features=[replication,scan], headers=include
```

`features`는 우리가 요청한 값이 아니라 **생성된 vtable을 되읽은 결과**다. `scan`처럼
헤더에서 딸려온 것과, 요청했는데 안 들어온 것을 구분하기 위해서다. 오프셋을 정하는 건
실제 구조체 모양이니까.

`ARCVECTOR_ABI_DEBUG=1`을 주면 필요한 멤버가 각각 해소됐는지 나열한다.

### 2.4 테스트

| 종류 | 명령 | 서버 |
|---|---|---|
| 단위 | `make unit` | 불필요 |
| 통합 | `make test` (컨테이너) | 이미지가 포함 |
| 복제 | `cargo test --features replication-tests --test replication -- --test-threads=1` | 마스터/슬레이브 짝을 직접 띄워야 함 |

통합 테스트를 호스트에서 돌리려면 서버 경로를 준다.

```sh
ARCVECTOR_MEMCACHED=/path/memcached ARCVECTOR_ENGINE=/path/default_engine.so \
  cargo test --features integration,replication
```

> **신선도 검사가 있다.** `cargo test`는 서버가 적재하는 `cdylib`을 다시 빌드하지 않으므로,
> 소스가 라이브러리보다 새로우면 **패닉으로 거부한다.** 낡은 결과는 없는 결과가 아니라
> 틀린 결과다. `cargo build`를 먼저 돌려야 한다.

**복제 짝 구성.** ZooKeeper와 EE 서버가 필요하다. 필수 스위트에 넣지 않은 이유는, 초록불이
switchover를 검증했다는 뜻이 되면 안 되기 때문이다.

```sh
# 1. ZK에 서비스 코드와 복제 그룹 znode 등록 (한 번)
#    /arcus_repl/cache_list/<svc>/<ip>:<port>-<hostname>
#    /arcus_repl/cache_server_group/<svc>/<group>/{lock,<ip>:<port>}
# 2. 두 노드를 같은 그룹으로 띄운다
memcached -E .../default_engine.so -X .../libarcusv.so \
          -l 127.0.0.1 -p 11311 -m 256 -z 127.0.0.1:2181
memcached ... -p 11312 -z 127.0.0.1:2181
# 3. 역할 확인
printf 'stats replication\r\n' | nc 127.0.0.1 11311 | head -1
```

테스트는 시작할 때마다 역할을 다시 조회한다. switchover가 짝을 뒤집으므로 어느 쪽이
마스터인지 가정하지 않는다.

## 3. 명령 API

| 명령 | 형태 | 응답 |
|---|---|---|
| `vcreate` | `vcreate <index> <dim> [METRIC][QUANT][M][EFC][EFS][MAXCOUNT][EXPTIME]` | `CREATED` · `EXISTS` |
| `vadd` | `vadd <index> <id> <veclen> <dim> [ATTR <len> <json>]` + 본문 | `STORED` · `OVERFLOWED` |
| `vgetattr` | `vgetattr <index> <id>` | `VALUE`+attr+`END` · `NOT_FOUND` |
| `vsetattr` | `vsetattr <index> <id> <attrlen> <json>` | `STORED` · `NOT_FOUND` |
| `vdel` | `vdel <index> <id>` | `DELETED` · `NOT_FOUND` |
| `VSIM VECTOR` | `VSIM VECTOR <index> <num> <bytes> <dim> [FILTER <n> <term>…] [WITHATTR]` + 본문 | `QUERY` 그룹들 + `END` |
| `VSIM KEY` | `VSIM KEY <index> <num> <key> [FILTER …] [WITHATTR]` | 위와 동일 |
| `vdrop` | `vdrop <index>` | `DROPPED` · `NOT_FOUND` |
| `vlist` | `vlist` | `INDEX …` 여러 줄 + `END` |
| `vstats` | `vstats` | 모듈 메모리 + `END` |

`vsetattr`은 ATTR 영역 **전체**를 바꾼다. 그래서 `<attrlen> 0`(JSON 토큰 없이)이 속성을 지우는
방법이고, 부분 갱신은 없다 — 클라이언트가 읽고 고쳐서 다시 쓴다. 벡터는 손대지 않으므로 검색은
같은 좌표에서 같은 id를 계속 찾는다. `ATTR` 키워드를 쓰지 않는 것은 뒤에 올 것이 없어서다.

`FILTER`와 `WITHATTR`은 순서를 가리지 않고, 둘 다 생략할 수 있다. `FILTER 0`은 조건 없음을
뜻하고 속성 반환과는 무관하다. 선언한 항 수 다음에 오는 토큰은 절 이름으로 읽히므로,
`FILTER 1 a b`는 항 개수 불일치가 아니라 `b`가 알 수 없는 절이라는 에러다.

### `WITHATTR`이 응답 형식을 가른다

```
WITHATTR 있음    VALUE <id> <distance> <attrlen>\r\n<attr JSON>\r\n
WITHATTR 없음    VALUE <id> <distance>\r\n
```

없으면 **히트당 엔진 읽기가 0**이다. 속성은 Map에만 있으므로 돌려주지 않으면 읽을 이유가 없고,
`vsim`이 그래프만으로 답한다.

대가는 그 경로가 **삭제된 원소의 id를 돌려줄 수 있다**는 것이다. 이름은 있는데 원소가 지워진
노드(§9의 창이 남기는 것)를 걸러낼 읽기가 없기 때문이다. `FILTER`가 있으면 걸러진다 — 없는
원소는 콜백도 읽을 수 없어 후보에서 빠진다. 즉 노출되는 조합은 `FILTER`도 `WITHATTR`도 없는
가장 빠른 경로 하나다.

| FILTER | WITHATTR | 노드당 | 히트당 | 삭제된 id가 나갈 수 있나 |
|---|---|---|---|---|
| 없음 | 없음 | 0 | **0** | **그렇다** |
| 없음 | 있음 | 0 | k | 아니오 |
| 있음 | 없음 | **0** (역참조뿐) | 0 | 아니오 |
| 있음 | 있음 | **0** (역참조뿐) | **0** | 아니오 |

**그래도 만료된 Map의 그래프가 답하는 일은 없다.** 히트당 0이라는 것은 원소를 안 읽는다는
뜻이고, 이름이 아직 인덱스인지는 그 전에 `resolve`가 확인한다 — 명령마다 한 번,
`map_elem_get(META)` 하나로. 빌드로 갈리지 않는다.

한때 이 자리에 `getattr`을 붙이려 했는데 그것으로는 부족하다. `getattr`은 Map이 **있다**까지만
말하고, 만료된 이름에 평범한 `mop` Map이 새로 생긴 경우를 통과시킨다. 아이템 플래그의 우리 태그로
거르면 될 것 같지만 그 플래그는 클라이언트가 `mop create`로 설정할 수 있어 권위가 없다(§미해결).
**이름이 우리 인덱스인지 답하는 것은 메타데이터 원소뿐이다.**

```
NoMap        Map이 없다 — 만료·축출·다른 노드의 삭제 → 그래프를 놓고 NOT_FOUND
Damaged      Map은 있는데 우리 것이 아니다 — 메타 원소가 없거나 안 읽힌다 → 그래프를 놓는다
Unknown      엔진이 답을 못 했다 → 아무것도 놓지 않고 그대로 올린다
Usable       메타데이터를 읽었다 → owner 판정으로
```

`Unknown`을 `NOT_FOUND`로 뭉개지 않는 것이 중요하다. 엔진이 한 번 딸꾹질할 때마다 멀쩡한
인덱스가 없다고 답하게 되고, ABI 불일치도 같은 말로 나가 버린다.

`owner`가 하는 일은 빌드로 갈린다. recovery 빌드에서는 소유가 실제로 바뀌므로(복제 전송, 재시작
복원, 다른 노드의 인수) 토큰 불일치가 재구축을 띄운다. 아닌 빌드에서는 Map이 이 프로세스보다
오래 살 수 없어 소유가 바뀌는 사건 자체가 없다 — 그래서 그 비교는 **돌지 않아야 정상인 분기**로
남겨 뒀다. 걸리면 재구축할 것이 없으므로 그래프를 놓고 `NOT_FOUND`로 답한다.

**`FILTER`의 노드당 비용이 조회에서 역참조로 바뀌었다.** 노드의 키가 곧 그 원소의
주소이므로, 필드로 찾을 필요 없이 `get_elem_info` 한 번으로 ATTR을 읽는다 — 해시 조회도,
refcount 증감 한 쌍도 없다. 방문 노드가 질의당 100개쯤이니 그 자리가 가장 뜨겁다.

**이 읽기는 엔진 락 밖이다.** 그래서 두 가지가 받쳐야 한다. 원소가 해제되지 않을 것 — 보유
집합의 읽기 락 아래에서 집합이 든 주소에 대해서만 부르므로 그렇다. 그리고 원소가 **바뀌지 않을
것** — 링크된 원소는 불변이고, 값을 고치는 것은 언제나 새 원소로의 교체다(§6). 우리 쪽 경로는
그 규칙을 지킨다.

**통과한 것만 붙든다.** `map_elem_get`으로 보유를 잡는 것은 술어를 통과한 `k`개뿐이고, 이유는
성능이 아니라 일관성이다 — 렌더가 다시 읽으면 그 사이의 쓰기를 가로질러 **필터가 판단한 것과
다른 바이트**가 나갈 수 있다. 보유는 `HeldElem`의 `Drop`이 놓으므로 조기 반환이나 패닉에도
누수가 없고, 보유 중인 원소만큼 메모리가 회수되지 않는 것이 그 값이다.

이름·키워드·열거값은 대소문자를 가리지 않는다. 좌표는 **공백으로 구분된 십진 텍스트**다.
에러는 요청 잘못이면 `CLIENT_ERROR`, 우리 쪽이면 `SERVER_ERROR`.

복구 중 조회는 `UNREADABLE`로 답한다. 엔진이 정의한 `ENGINE_UNREADABLE`이라 클라이언트
어휘가 늘지 않는다.

자세한 옵션과 예시는 [README](../README.md)에 있다.

## 4. 모듈 지도

두 갈래다. **`command`는 와이어, `handler`는 실행**이고, 백엔드 셋은 handler 안에 있다.
괄호는 테스트를 뺀 줄 수.

```
lib.rs (134)              C ABI — 등록과 memcached의 네 콜백
  command/                와이어: 명령행 하나 들어와 타입 하나 나간다   (순수)
    tokens (75)             토큰 배열을 읽는 유일한 모듈
    request/
      mod (181)             명령당 타입 하나
      layout (67)           각 명령의 인자가 몇 번째 토큰인가 — 유일한 위치 상수
      parse (319)           토큰 → 요청
    nread (…)               본문을 기다리는 명령 — 연결 슬롯에 얹힘
    filter/
      mod (290)             FILTER 절의 작은 언어
      json (157)            ATTR에서 필드 하나 읽기 — 무할당
  handler/                명령을 수행하는 모든 것
    mod (64)                run — Store를 만들고 명령을 배분, 답을 정한 뒤 청소를 한 번 본다
    cmd/                    명령 자신의 논리만
      index (246)             vcreate, vdrop, vlist, vstats
      vector (284)            vadd, vgetattr, vsetattr, vdel
      search (206)            vsim 두 형태 — WITHATTR과 보유 원소
      coords (44)             십진 텍스트 → f32                        (순수)
    access/                 어느 그래프가 이 이름을 섬기나  ★
      mod (220)               resolve — 모든 명령의 첫 걸음
      meta (35)               `AV META` 원소 읽기 — 이름이 인덱스인지 답하는 유일한 것
      sweep (207)             차가운 이름을 고르고 해체하는 스레드 — 커넥션은 getattr 하나만  ★
    quant (151)             한 좌표를 어떻게 표현하는가   (순수, 양쪽이 씀)
    arcus/                  저장 — 원본
      element (326)           그 바이트가 원소 어디에 놓이는가 — 그래프는 안 들어온다  (순수)
      engine/
        mod (131)             핸들 해소와 Store             (원시 포인터)
        error (95)            엔진 코드, 그중 무엇이 실패인가  ★
        map (116)             Map 아이템 — 속성·probe·형식 버전, 생성 호출은 없다
        elem (794)            그 안의 원소들 — 예약/채우기/insert 분리, 보유, 주소로 읽기  ★

    usearch/                검색 — 캐시
      index (935)             용량과 락, staging, 두 저장소를 묶는 hold   ★
      held (133)              그래프가 refcount를 든 원소 주소들 — 키가 곧 주소다  ★
      metric (67)             거리 척도
    registry (460)          살아 있는 인덱스 목록, 발행 시계, 접근 시각  ★
    recovery (206)          그래프가 Map과 어긋났을 때 — 인수·복구 스레드·토큰 발급  ★

```

★ 표시가 최근 작업에서 논리가 바뀐 곳이다. **`access/meta` → `access` → `recovery` →
`usearch/index`** 순으로 보면 이름 판정부터 복구까지가 이어진다.

**`cmd/`는 명령 자신의 논리만 담는다.** 어느 그래프가 이 이름을 섬기는지(`access`), 두 저장소,
레지스트리는 전부 그 옆이지 그 안이 아니다. 그래서 `cmd/`의 파일 하나를 읽는 것이 명령 하나를
읽는 것이 된다.

**`access/`는 한 질문의 세 조각이다.** `resolve`가 "이 이름이 아직 우리 인덱스인가, 어느
그래프로 섬기나"를 모든 명령에 답하고, `meta`가 그 앞절반을 답할 수 있는 **유일한** 것이며,
`sweep`은 같은 질문을 **아무 명령도 묻지 않는 이름**에 대해 던진다.

`meta`가 `recovery` 밖에 있는 이유가 그것이다 — 메타데이터를 읽는 것은 복구가 있든 없든 모든
명령의 첫 걸음이다. 한때 `recovery` 안에 있었고, 그래서 복구가 꺼진 빌드는 이름이 아직
인덱스인지 확인하지 못했다.

`quant`이 `arcus`·`usearch`와 형제인 이유는 **둘 다 쓰기 때문**이다. 어떤 종류가 존재하는지는
usearch의 `ScalarKind`가 정하고(`b1`의 비트 순서까지), 그것이 원소에서 몇 바이트를 차지하는지는
`arcus::element::Layout`이 정한다. 어느 한쪽에 넣으면 다른 쪽이 그 안을 들여다보게 된다.

`registry`와 `recovery`가 갈린 이유도 같다. 앞은 **지금 무엇이 살아 있는가**(이름 → 쌍)이고,
뒤는 **그 쌍이 어긋났을 때 무엇을 하는가**이다. 메타데이터 원소는 복구가 그래프를 다시 만들 때
쓰는 것이라 `recovery` 안에 있다. 의존은 한 방향이다 — `recovery`가 `registry`를 쓰고 그 반대는
없다.

### 왜 백엔드가 handler 안에 있나

**엔진에 닿는 유일한 길이 명령을 수행하는 모듈이 되도록** 하기 위해서다. `command`는
엔진도 인덱스도 이름조차 부르지 않는다 — 토큰을 값으로 바꾸고 끝난다. 그래서 파서를
서버 없이 시험할 수 있고, 문법 규칙이 사는 곳이 정확히 한 군데다.

파서가 필요로 하는 어휘 셋(`Quant`, `Metric`, `ATTR_BYTES`)만 크레이트 루트에 재수출한다.
명령행이 그 이름들을 부르기 때문이지 백엔드 내부를 알아야 해서가 아니다.

`error`는 루트에 남는다. 모두가 쓰는 공용 어휘라서다.

### 경계 두 개

**파싱은 상태를 건드리지 않는다.** `request`는 토큰을 `Line`/`Body`로 바꾸고 끝나고,
`handler`는 그 값을 받고 토큰을 보지 않는다. 디렉터리가 갈라져 있어 규칙이 아니라 구조로
지켜진다.

**원시 포인터는 `arcus::engine`에만 산다.** `Store::for_cookie`가 유일한 `unsafe`
생성자이고, 그 아래는 전부 `&self`를 받아 Rust 값을 돌려준다.

### 방향

`arcus/`는 "엔진을 쓰는 모든 것"이 아니라 *벡터가 arcus에 저장되는 방식*이다. `element`는
엔진 호출을 하나도 안 하지만 그 모양을 결정하는 건 arcus다 — 크기 상한이
`max_element_bytes`이고, 고정 138바이트 오버헤드(헤더 10 + ATTR 128)도 arcus가 정한다.

`usearch/index`가 `arcus/element`에 의존하는 것도 같은 이유다. 인덱스는 저장된 레이아웃으로
구성되고 스토어가 든 바로 그 바이트를 받는다. 그래서 복구가 무손실이고, 의존 방향이
고정된다 — **캐시가 스토어를 알고 그 반대는 없다.**

## 5. 요청 흐름

memcached는 확장에 콜백 넷을 준다. 넷 다 쓴다.

| 콜백 | 역할 |
|---|---|
| `get_name` | 확장 식별 |
| `accept` | 명령 점유, 본문 바이트 수 결정 |
| `execute` | 실행하고 응답 |
| `abort` | 전송 도중 죽은 명령의 상태 해제 |

대부분은 명령행에서 바로 `execute`로 끝난다. `vadd`와 `VSIM VECTOR`는 바이트 수를 선언하고
좌표를 뒤이어 보낸다(`nread`). 이 둘은 `accept`가 버퍼를 등록하고 `execute`가 **빈 토큰
배열**로 한 번 더 호출된다 — 그게 본문이 도착했다는 신호다.

```
클라이언트 ──▶ accept ──▶ (본문 수신) ──▶ execute(빈 토큰) ──▶ 응답
                 │                            │
                 │                            ├─ command::parse()  ─▶ Request
                 │                            └─ handler::run(Request)
                 └─ 파싱 실패도 Result로 nread 상태에 실어 보낸다
```

**`command`와 `handler`는 서로를 부르지 않는다.** `lib.rs`가 하나를 부르고 그 결과를
다른 하나에 넘긴다. 둘이 공유하는 건 `Request` 타입뿐이다.

```rust
let outcome = unsafe { command::parse(cookie, &tokens) }
    .and_then(|request| unsafe { handler::run(cookie, request) });
```

### 두 콜백 사이에 상태를 어디 두나

`accept`와 `execute`는 별개의 호출이고 공통점은 **연결 cookie 하나**다. `accept`가 파싱한
것을 `execute`가 찾아야 하는데, memcached는 그 자리를 하나 준다 — `conn`마다 `void *` 하나,
`store_engine_specific`/`get_engine_specific`으로 넣고 꺼낸다.

연결은 만들어질 때 한 스레드에 묶이고(`thread.c:361`, `assert(c->thread == NULL)`) 옮겨가지
않으므로, 그 슬롯을 두 스레드가 만질 일이 없다. **곁다리 표도 락도 필요 없다.**

회수는 `abort`가 보장한다. `conn_close`가 `ascii_cmd`가 걸려 있으면 `abort`를 부르고
(`memcached.c:979`), 그 다음에야 `conn_cleanup`이 슬롯을 비운다(`:950`). 전송 도중 연결이
죽어도 포인터를 돌려받는다.

이름이 `engine_specific`인 것은 원래 스토리지 엔진 몫이라서다. 이 트리의 어느 엔진도 쓰지
않는 것을 확인하고 썼다 — 나중에 엔진이 쓰기 시작하면 서로 덮어쓰므로, 그때는 곁다리 표로
되돌려야 한다.

### `accept`는 잘못된 명령행을 거부하지 않는다

응답 핸들러가 없어 클라이언트에게 답할 수 없다. 여기서 거부하면 좌표가 읽히지 않은 채
남고 memcached가 그것을 **다음 명령행으로** 파싱한다 — 잘못된 요청 하나가 그 연결의
나머지를 망친다.

그래서 바이트 수만 보고, 나머지 파싱 실패는 대기 항목에 `Result`로 저장했다가 본문을 다
흘려보낸 뒤 핸들러가 보고한다. 거부는 **바이트 수 자체를 못 읽을 때**만 한다.

이 비대칭이 `request::parse`의 반환 타입이다. 명령행 하나를 한 번만 훑어 둘 중 하나를 낸다.

```rust
pub enum Parsed<'a> {
    Line(Line<'a>),
    Body { len: usize, request: Result<Body> },
}
```

`len`은 밖의 `Result`가 성공했다는 뜻이므로 **안의 `Result`가 실패해도 유효하다** — 흘려보낼
바이트 수는 알고 답은 모르는 상태가 타입으로 표현된다. 바이트 수를 못 읽으면 `Parsed`가
아예 나오지 않아 `Body` 단계로 들어갈 길이 없다. 토큰 위치는 `layout`에만 있고 `parse`와
디스패처가 같은 상수를 읽으므로 둘이 어긋날 수 없다.

### 토큰과 ATTR

memcached의 토크나이저는 공백으로 자르면서 **토큰을 끝내는 공백을 제자리에서 `'\0'`으로
덮어쓴다.** 그래서 쪼개진 문자열을 되붙이려면 NUL을 공백으로 되돌려야 하는데, NUL은
클라이언트가 보낼 수도 있는 바이트라 복원이 모호하다.

그래서 **ATTR JSON은 인자 하나**로 받는다. 공백이 있으면 토큰이 더 생기고 그 사실만으로
거부한다. 잃는 건 없고 오히려 공백 예산을 안 나눠 쓰므로 128바이트 전 구간을 쓸 수 있다.
`FILTER`도 같은 이유로 항마다 토큰 하나다.

토큰 **개수** 한계는 우리가 지키지 않는다. `process_extension_command`가 `accept`를 부르기
전에 거부하므로(`memcached.c:10189`, `ntokens == MAX_TOKENS`) 확장에 도달하는 실토큰은
최대 28개다. 한때 이 모듈에도 같은 검사가 있었지만 도달 불가능한 죽은 코드였다.

### 모듈 지표가 자체 명령을 갖는 이유

memcached는 자기가 인식에 실패한 명령만 확장에게 묻는다. `stats` 같은 내장 명령은 오지
않으므로 arcus를 고치지 않고는 `stats vector`를 추가할 수 없다. 그래서 `vstats`가 따로 있다.

## 6. 저장 형식

인덱스 하나가 Map 아이템 하나, 벡터 하나가 Map 원소 하나다. 원소는 두 종류인데 **형식이
서로 다르다.**

### 벡터 원소 — 고정 배치

```
 off  0        2              130
     +--------+--------------+---------------+
     | alen   | ATTR 128B    | 양자화된 벡터 |   recovery 빌드
     +--------+--------------+---------------+

     +--------+--------------+
     | alen   | ATTR 128B    |                  그 외
     +--------+--------------+
```

**벡터는 복구가 있는 빌드에만 들어간다.** 768차원 f32면 원소 3204바이트 중 3072가 벡터인데,
그것을 Map에서 읽는 곳은 재구축 하나뿐이다. usearch가 인덱스의 양자화 그대로 같은 바이트를
들고 있으므로, 복제도 영속화도 없는 빌드 — Map이 프로세스보다 오래 살 수 없는 빌드 — 에서는
사본을 둘 이유가 없다. 원소가 132바이트로 줄고, 2M 벡터면 6GB 남짓이 사라진다.

`vsim KEY`의 질의 벡터도 그래서 그래프에서 읽는다(`AnnIndex::vector_of`).
`a_stored_vector_reads_back_byte_for_byte`가 네 양자화 전부에 대해 왕복을 고정한다.
`B1`만 읽기에 손이 하나 더 간다 — 바인딩이 버퍼 길이를 `dimensions()`(이진 인덱스에서는
**비트 수**)로 나누어 검사해서 `dim/8`바이트를 거절하므로, `dim`바이트를 요청하고 앞부분만
취한다. `add`에는 그 검사가 없어 쓰기는 영향이 없다.

`Element`의 `vector` 필드는 비워 두는 대신 `cfg`로 잘라 뒀다. 저장하지 않는 빌드에서 그것을
읽는 코드가 **컴파일되지 않는다.**

**차원 한도는 빌드로 갈리지 않는다.** `check_dimension_fits`는 벡터를 넣었을 때의 크기
(`full_stored_len`)로 잰다. 그러지 않으면 같은 서버가 빌드에 따라 다른 차원을 받아들이게 되고,
인덱스를 모듈 컴파일 방식과 무관하게 설명할 수 없게 된다.

`alen`은 ATTR JSON의 실제 길이다. `vgetattr`이 클라이언트가 저장한 바이트를 그대로 돌려주려면
어디서 끝나는지 알아야 하고, 그게 이 2바이트가 있는 이유다 — 검색 필터는 `}`에서 멈추므로
필요 없고, `vadd`는 클라이언트가 길이를 준다.

**그래프에 관한 것은 하나도 없다.** 노드의 키가 이 원소의 **주소**라서, 저장할 것이 없다 —
주소는 애초에 저장할 수 있는 값이 아니고, 다음 프로세스에서 같은 뜻을 갖지도 않는다. 검색이
키를 id로 되돌리는 것은 이 원소를 역참조해 필드 바이트를 읽는 것이다([§9](#9-동시성)).

**ATTR 영역이 고정 128바이트에 패딩인 것은 자리를 아끼지 않으려는 선택이다.** 원래 노린 것은
`vsetattr`의 제자리 갱신이었다. 엔진의 `do_map_elem_update`는 길이가 같을 때만 제자리다:

```c
if (elem->refcount == 0 && elem->nbytes == nbytes) {
    memcpy(elem->data + elem->nfield, value, nbytes);   /* 제자리 */
    CLOG_MAP_ELEM_INSERT(info, elem, elem);
} else {
    ... do_map_elem_alloc + do_map_elem_replace          /* 새 원소, 주소가 바뀐다 */
}
```

**그런데 제자리 갱신은 이 설계에서 쓰면 안 되는 것이었다.** 성능 문제가 아니라 정확성이다.

키가 주소이므로 **읽는 쪽이 엔진 락 없이 그 바이트를 읽는다.** `FILTER` 술어가 방문 노드마다
`get_elem_info`로 ATTR을 읽는데, 그 읽기는 `LOCK_CACHE()` 밖이다. 제자리 `memcpy`는 그 락
안에서 돌지만 **우리 독자는 그 락을 잡지 않으므로**, 읽는 도중에 바이트가 바뀔 수 있다 — 반은
헌 JSON, 반은 새 JSON. 찢어진 값으로 판정하게 된다.

그래서 원소는 **링크된 뒤로 불변**이어야 한다. 바뀌는 것은 언제나 "새 원소를 만들고 헌 것을
unlink"이고, 헌 주소를 든 독자는 자기가 보던 스냅숏을 끝까지 본다. 이것이 주소를 키로 쓰는
설계의 바닥 불변식이고, `vsetattr`이 `map_elem_update` 대신 `map_elem_insert`를 쓰는 이유다.

`map_elem_update`가 애초에 못 쓸 도구인 이유도 있다 — **새로 할당한 원소의 주소를 돌려주지
않는다.** `ENGINE_ERROR_CODE`뿐이라 교체가 일어나도 어디로 갔는지 알 수 없고, 끝나고 다시
조회해야 한다. `map_elem_insert`는 우리가 할당한 원소를 링크하므로 주소가 호출 전에 손안에 있다.

> **`mop update`는 이 불변식 밖에 있다.** 클라이언트가 같은 길이로 갱신하면 엔진이 제자리
> `memcpy`를 하고, 그때 술어가 읽고 있으면 찢어진 값을 본다. 메모리 안전 문제는 아니다 —
> 원소는 그래프의 refcount로 살아 있고 `memcpy`는 그 안에 머문다 — 하지만 그 후보의 판정이
> 틀릴 수 있다. [미해결.md §2](미해결.md)의 직접 조작 경로에 딸린 성질이다.

**업서트가 교체를 해주지만, 안 할 때가 있다.** `do_map_elem_link`는 필드가 있으면
`do_map_elem_replace`로 **우리 원소**를 링크하고 헌 것을 unlink한다 — 그래서 주소를 미리 안다.
그런데 필드가 **없으면** 그냥 새로 넣고 `ccnt`를 올린다. 값을 준비하는 사이에 누가 그 원소를
지웠다면, `vsetattr`이 죽은 원소를 되살리는 셈이다.

그래서 `insert`가 `replaced`를 돌려주고, 거짓이면 방금 넣은 것을 도로 빼고 읽기가 그랬을 답을
낸다(`NOT_FOUND`). `vadd`는 둘 다 자기 일이라 이 값을 보지 않는다.

**그러면 고정 폭은 무엇을 하나.** 제자리 쓰기는 아니지만, ATTR이 커져도 원소가 커지지 않는다는
성질은 남는다 — `maxcount`가 세는 원소 수와 `max_element_bytes` 판정이 ATTR 내용에 흔들리지
않고, ATTR을 늘리는 갱신이 `EOVERFLOW`로 실패할 수 없다. 그리고 `vsetattr`이 `vadd`보다 싼
이유는 제자리 여부가 아니라 **그래프가 `rename` 하나로 끝난다**는 데 있다 — HNSW 재삽입
(~370us)이 없다.

**둘 — 벡터가 상수 오프셋에서 시작한다.** 그래야 `attr_of`가 계산 없이 자르고, 디코딩이 차원만
알면 벡터를 뜯을 수 있다. 벡터가 없는 빌드에서도 같은 배치를 쓴다 — 오프셋이 빌드로 달라지면
`attr_of`가 두 벌이 된다.

읽을 때도 ATTR만 복사한다. `vgetattr`과 `WITHATTR` 렌더는 `get_attr`로 홀드를 잡고 `attr_of`로
자른 뒤 그만큼만 가져온다. 예전에는 원소 전체를 복사한 뒤 ATTR을 잘랐다 — recovery 빌드에서
3KB를 복사해 50바이트를 답하던 셈이다.

**그 밖에는 아무것도 없다.** 매직도, 버전도, `dim`·`quant`도, 레코드 종류도 없다. 읽히지
않는 필드는 두지 않는다.

- `dim`·`quant` — 쓰기가 인덱스 자신의 레이아웃에서 값을 가져오고 디코딩도 같은 곳에서
  오프셋을 얻으므로, 원소에 적어두고 대조해봐야 항상 참이다. 필요한 곳은 메타데이터 원소
  하나뿐이라 그쪽에 있다.
- 레코드 종류 — 어느 종류를 읽는지는 필드명이 이미 말한다. 벡터는 클라이언트가 준 id로,
  메타데이터는 `AV META`로 지정해 읽는다.
- 매직 — `mop insert`로 들어온 바이트를 걸러냈지만, 앞 두 바이트를 맞춰 넣으면 그대로
  통과한다. 절반만 막는 검사였고, 그 경로 자체가 [미해결.md §2](미해결.md)에 "막을 수
  없다"고 적힌 구멍이다.
- 버전 — 아래.

### 메타데이터 원소 — 값 전체가 JSON

```
필드명   AV META
값       {"dim":2,"quant":"f32","metric":"cos","m":0,"efc":0,"efs":0,
          "owner":"27c6fcea7ae95557"}
```

헤더가 없다. 벡터 원소는 뒤에 벡터가 붙으므로 어디서 ATTR가 끝나는지 적어야 하지만, 이건
**값이 JSON뿐이라 엔진이 아는 원소 길이가 곧 끝**이다. `map_elem_get`은 필드명으로 찾아
그만큼을 돌려준다.

덕분에 128바이트 상한도 없다. 인덱스당 하나뿐이라 길어져도 무방하고, 키를 추가하는 것이
형식 변경이 되지 않는다.

`m`·`efc`·`efs`가 0이면 usearch 기본값을 쓰라는 뜻이다.

**필드명의 공백이 핵심이다.** 모듈이 검사해서 막는 것이 아니라 ASCII 프로토콜로 **표현이
불가능**하다.

| 경로 | 결과 | 근거 |
|---|---|---|
| `mop insert` | 생성 불가 | 필드가 명령행 토큰이고 토큰은 공백으로 분리된다 |
| `mop get`·`mop delete` | 지정 불가 | 공백 구분 목록을 `numfields`와 대조하므로 항상 2개로 쪼개져 `EBADVALUE` |
| 바이너리 프로토콜 | 경로 없음 | LOP/SOP/BOP opcode만 있고 MOP는 없다 |
| `vadd` | 충돌 불가 | id도 명령행 토큰이다 |

전체 덤프(`mop get <key> 0 0`)로는 보이므로 운영 관측성은 유지된다. 엔진은 필드를 길이와
원시 바이트로 다룬다 — 명령 로그, 체크포인트 스냅숏, 복제 change-set 전부 — 그래서 공백이
깨질 텍스트 왕복 구간이 없다.

`maxcount`·`exptime`은 넣지 않는다. 엔진이 아이템 속성으로 이미 복제·영속화하므로, 복사해
두면 `setattr`이 두 값을 어긋나게 만든다.

### 형식 버전은 아이템 플래그에 있다

```rust
pub const FORMAT_VERSION: u16 = 1;          // alen, key, ATTR, 벡터
pub const INDEX_FLAGS: u32 = INDEX_TAG | FORMAT_VERSION as u32;
const INDEX_TAG: u32 = 0x4156_0000;         // "우리 것"
```

상위 절반이 태그, 하위 절반이 버전이다. 원소에는 버전을 두지 않는다 — 인덱스 하나의 모든
원소가 같은 형식이므로 아이템 하나에 한 번 적으면 된다.

`looks_like_index()`는 **태그와 버전을 함께** 본다. 그리고 `is_tagged()`가 따로 있는 이유가
있다: **우리 것이지만 읽을 수 없는 버전의 Map은 지우거나 다시 쓰면 안 되고 거부만 해야 한다.**
손상 판정이 Map을 지우는 유일한 경로인데, 상위 버전을 손상으로 읽으면 신 버전 노드가 쓴
인덱스를 구 버전 노드가 삭제한다.

버전이 없던 때에는 형식을 바꾸는 변경 자체를 지킬 수 없었다 — 버전 없는 빌드를 소급해 고칠 수
없기 때문이다. `key`를 헤더에 넣는 변경이 그 첫 번째였고, 그래서 버전을 같은 변경에서 넣었다.
그 이전 형식으로 저장된 데이터는 읽히지 않는다.

### 원소 끝의 `\r\n`

arcus는 컬렉션 원소 크기를 **종결자 포함으로** 잡는다. 내장 명령이 클라이언트 바이트를
원소 안으로 그대로 `nread`하기 때문이다. 되읽는 곳은 없다 — `mop get`은 `nbytes - 2`를 값
길이로 보고하고 나머지를 줄 끝으로 내보낸다.

이 모듈은 `nread`할 수 없다. 와이어에는 십진 텍스트가 오고 원소에는 양자화된 바이트가
들어가서 크기도 내용도 다르다. 그래서 종결자를 직접 쓴다. 안 쓰면 엔진이 길이를 두 바이트
짧게 넘기고 **벡터의 마지막 두 바이트를 종결자로 오인한다.**

### 소유 토큰

`RandomState`로 만든다. 프로세스당 한 번 OS에서 씨앗을 받고 호출마다 키를 전진시키므로,
고정값을 새 해셔에 통과시키면 조율 없이 서로 다른 `u64`가 나온다.

이름 기반은 전부 실패한다 — `pid`는 컨테이너마다 1, 호스트명은 보장이 아니라 관례,
`getsockname`은 *연결의* 로컬 주소라 로컬 헬스체크가 복구를 유발하면 어디서나 `127.0.0.1`이
된다.

무엇을 판정하는 값인지는 §7.2에 있다.

### 손상 판정

메타데이터를 못 읽으면 손상이고, 손상이면 Map을 지운다. metric과 HNSW 파라미터 없이는 다시
인덱스가 될 수 없으므로, 남겨두면 이후 모든 명령이 성공할 수 없는 복구를 반복한다. 지우기
때문에 실패 backoff도 필요 없다 — 재시도할 대상이 없다.

지우기 전에 `looks_like_index()`로 아이템 플래그를 본다. 우리 것이 아닌 Map은 건드리지
않는다.

## 7. 복구 로직

### 7.1 왜 필요한가

arcus EE의 복제는 **Map 원소는 나르지만 그래프는 안 나른다.** switchover로 승격된 노드는
벡터를 다 갖고도 탐색할 그래프가 없다.

더 어려운 건 강등됐다 다시 승격된 노드다. 프로세스가 죽은 적이 없어 마스터 시절 그래프를
그대로 들고 있는데, 그 사이 상대 노드의 쓰기가 **확장보다 하위 계층인 복제 경로**로 이
노드의 Map에 반영됐다. 통보받을 수단이 없다. 증상은 조용한 불일치다.

```
Map 원소 수      4
vlist(그래프)    3
vgetattr v4         정상 반환   — Map을 직접 읽으므로
vsim  (v4 방향)  v4 누락     — 거리 0인 벡터가 결과에 없음
```

**역할(master/slave) 폴링으로는 못 잡는다.** A→B→A에서 A의 역할은 전후 모두 `master`라
어떤 주기로도 변화가 없다. 달라진 건 역할이 아니라 그래프이므로, 판정 근거는 그래프마다
구별되고 양쪽 노드가 다 볼 수 있는 곳 — Map — 에 있어야 한다.

퍼시스턴스(`ENABLE_PERSISTENCE`)도 같은 상황을 만든다. 재시작 후 체크포인트와 명령
로그로 아이템이 복원되면 Map은 살아 있고 그래프는 비어 있다. 그래서 `cfg(recovery)`는
복제 **또는** 퍼시스턴스에서 켜진다.

### 7.2 판정 — `owner` 하나

메타데이터 원소의 `owner` 토큰을 메모리의 것과 비교한다. `0`은 예약값이라 발급되지 않으며
그것으로 "복구 중"을 표현한다.

| Map | 메모리 | 의미 | 처리 |
|---|---|---|---|
| 토큰 | 같은 토큰 | 이 그래프가 이 Map을 설명한다 | 정상 |
| 토큰 | 다른 값 | 다른 노드가 서빙했다 | 인수 → 복구 |
| `0` | `0` | 이 노드가 복구 중 | 읽기 `UNREADABLE`, 쓰기 통과 |
| `0` | 토큰 | 복구하던 노드가 사라짐 | 인수 → 복구 |

3행과 4행의 구분이 핵심이다. 복구 중인 노드만 메모리에도 `0`을 들고 있으므로, "Map은 `0`
인데 메모리는 토큰"은 복구 주체가 소멸했다는 뜻이고, 그때 남은 그래프야말로 못 믿을
그래프다.

**역할을 묻지 않는다.** 토큰이 어긋난 레플리카는 인수를 시도하는데, 인수는 아무것도 버리기
전에 Map에 stamp부터 하고 그건 쓰기라 엔진이 `ENGINE_REPL_SLAVE`로 거부한다. 토큰이
일치하는 레플리카의 그래프는 실제로 자기 Map을 정확히 설명한다 — 마스터가 원소보다 토큰을
먼저 쓰고 복제가 그 순서를 보존하므로, "일치하는 토큰 + 낡은 데이터"는 성립하지 않는다.

의도적 귀결: 레플리카는 토큰이 일치하는 동안 읽기를 답하고, 마스터가 인수하는 순간 답하지
않는다. 읽기 분산에 쓸 거면 이 성질을 전제해야 한다.

### 7.3 3단계

```
워커 스레드   ① 메모리에 "복구 중" 표시    ← 이 시점부터 읽기가 UNREADABLE
              ② Map에 owner = 0 stamp     ← 아직 아무것도 안 버렸다
              ③ 그래프를 비우기
              ④ 원소 전체를 보유로 스냅숏(hold_all)   ← 커넥션이 있는 여기서만 가능
              ⑤ 그 배열과 함께 큐에 등록
                 │
복구 스레드   ⑥ 스냅숏 크기만큼 용량 사전 확보
              ⑦ 원소마다 get_elem_info → add_unless_known
              ⑧ "다 채웠다" 표시. 보유를 놓는다. 쓰기는 한 줄도 안 한다
                 │
워커 스레드   ⑨ (다음 명령) Map 재확인 → 새 토큰 발급·기록 → 조회 재개
```

**①②③의 순서가 리뷰 포인트다.** ②가 ③보다 앞이라 레플리카에서 stamp가 거부돼도 그래프가
남는다. 순서가 반대였다면 애초에 성공할 수 없는 쓰기 때문에 그래프를 잃고, 인덱스가 큐에도
없이 복구 중으로 남는다.

**④가 ③보다 뒤인 것도 그렇다.** 그래프를 비우고 tombstone 기록이 시작된 뒤에 스냅숏을 떠야,
그 시점부터의 삭제가 전부 덮인다.

**복구 스레드가 엔진을 거의 안 만지는 이유.** 연결 없는 스레드에는 cookie가 없고, 엔진은
**키를 받는 API마다** 그것을 훅에 넘긴다 — 쓰기만이 아니라 읽기도 그렇다(§7.5). 쓰기 경로는
특히 직접 역참조한다. `do_check_master_switchover_done`이 `get_thread_index(cookie)`를 널 검사
없이 호출하므로, switchover 중인 마스터에서 분리 스레드가 쓰면 프로세스가 죽는다 — 그리고
switchover 중이라는 건 복구가 돌 개연성이 가장 높은 시점이다. 실제로 SIGSEGV로 서버가
내려갔던 건이다.

읽기는 안전하다. `ACTION_BEFORE_READ`는 `ENABLE_MIGRATION` 없이는 비어 있고,
`rp_after_check`는 thread-local cookie가 널이면 즉시 반환하며, arcus 자신도 슬레이브
switchover 검사를 cookie 없이 호출한다.

**그래프를 미리 비우는 이유.** 새 그래프를 옆에 만들면 복구 중에도 서빙할 수 있지만 메모리가
두 배다. usearch는 비어 있지 않은 인덱스당 약 16.8 MB에서 시작하므로 1024차원 `i8` 100만
개면 약 1 GB를 두 벌 든다. 이미 낡은 것으로 판명된 그래프에서 답하는 것보다 `UNREADABLE`이
정직하다.

### 7.4 복구 중에도 쓰기를 받는다

큰 인덱스의 복구는 수 분이고, 그동안 쓰기를 거부하면 switchover가 쓰기 장애로 관측된다.
그 대가로 하나의 그래프에 writer가 둘이 되고, 누가 이기는지는 `AnnIndex`가 양쪽 모르게
정한다.

| 순서 | 위험 | 해소 |
|---|---|---|
| 스냅숏 이후 삽입 | 복구가 옛 값으로 새 값을 덮음 | `add_unless_known` — 이미 아는 id는 건너뜀 |
| 스냅숏 이후 삭제 | 스냅숏에 남아 되살아남 | tombstone — 복구 종료 시 일괄 해제 |

두 판정 모두 **삽입을 지키는 그 락 아래서** 이뤄진다. §9.

### 7.5 스냅숏은 워커가 뜬다

**커넥션 없는 스레드가 부를 수 있는 것은 정해져 있다.** 엔진은 키를 받는 API마다
`ACTION_BEFORE_READ` / `ACTION_BEFORE_WRITE`를 걸어 두고 거기에 쿠키를 넘긴다.
`ENABLE_MIGRATION`이 켜진 EE 빌드에서는 마이그레이션이 도는 동안 그것이
`mg_before_check` → `set_not_my_key_info(cookie, …)`까지 간다 — 쿠키가 널이면 널 역참조다.
마이그레이션이 없으면 곧바로 반환하므로 **평소에는 멀쩡하고 겹칠 때만 죽는다.**

| 호출 | 커넥션 없이 | 왜 |
|---|---|---|
| `map_elem_get`·`getattr`·`remove` … | **안 됨** | 키를 받는 API. 훅이 쿠키를 넘긴다 |
| `get_elem_info` | 됨 | `handle`과 `cookie`를 아예 쓰지 않는다 (OSS·EE 동일) |
| `map_elem_release` | 됨 | 쿠키를 쓰지 않고, 스스로 `LOCK_CACHE()`를 잡는다 |

`refill`이 읽던 `get_all`은 첫 행에 해당했다. 그래서 지금은 **인수를 감지한 워커**가
`hold_all`로 스냅숏을 뜨고, 보유 배열을 큐에 함께 넣는다. 복구 스레드가 부르는 것은 아래 두
행뿐이다. `HeldMap`이 `Send`인 근거가 그것이고, 청소(§8)가 워커에서 도는 이유도 같다 —
`getattr`은 키를 받는다.

같은 표가 **청소 스레드**(§8)의 분담을 정한다. 고르기와 해체가 부르는 것은 `map_elem_release`와
usearch 소멸자뿐이라 쿠키가 필요 없고, 그래서 스레드에 있다. `getattr` 하나만 워커에 남는다.

덤으로 복사가 사라졌다. 예전 `get_all`은 **모든 값을 복사한 뒤 필드명만 쓰고 버렸다** — 2M ×
3KB면 6GB를 복사해서 버리는 셈이었다. 지금 드는 것은 엔진이 잡는 포인터 배열과 원소당
refcount 하나다.

보유가 바이트를 읽을 수 있게 지켜준다. 그 사이 unlink된 원소도 refcount가 서 있는 한 해제되지
않는다. **낡을 수는 있어도 재생되지는 않는다** — `add_unless_known`이 매핑 쓰기 락 아래에서
판정하는데, 그것은 `vadd`가 두 등록에 걸쳐, `vdel`이 tombstone에 걸쳐 잡는 바로 그 락이다.
살아있는 경로가 건드린 id는 이미 known이라 건너뛴다.

같은 이름에 인수가 또 들어오면 큐의 앞선 항목을 **대체한다.** 새 스냅숏이 최신이고, 낡은 것을
버리면 그 보유가 지금 풀린다 — 더 이상 원치 않는 refill이 끝나기를 기다리지 않는다.

### 7.6 실패

| 상황 | 응답 | Map |
|---|---|---|
| 메타데이터 손상(부재·매직·파싱) | `NOT_FOUND` | **삭제**, 로그 |
| 모르는 상위 버전 | `NOT_FOUND` | 보존 |
| 그 외 복구 실패 | `SERVER_ERROR` | 보존, 다음 명령이 재시도 |
| 레플리카에서의 인수/쓰기 | `SERVER_ERROR …replica…` (엔진 발) | 보존 |

**지우는 실패는 손상 하나뿐이다.** metric과 HNSW 파라미터가 없으면 다시 인덱스가 될 수
없으므로, 남겨두면 이후 모든 명령이 성공 불가능한 복구를 반복한다. 지우니까 실패 backoff도
필요 없다 — 재시도할 대상이 없다.

**단, ABI 불일치가 걸린 뒤에는 지우지 않는다.** vtable이 어긋나면 엔진의 "원소 없음"을 믿을
수 없고, 그걸 손상으로 읽으면 빌드 실수가 데이터 삭제가 된다. §11.

그 외 실패는 레지스트리 항목만 버린다. 다음 명령이 빈 그래프를 새로 만들고 **무조건** 인수
하므로 복구가 재개된다. 이 "무조건"이 없으면 Map은 `0`인데 레지스트리는 비어 있는 상태가
"누가 복구 중"으로 보여 아무도 복구를 걸지 않는 교착이 된다.

### 7.7 복구가 꺼진 빌드

**메타데이터는 여기서도 읽는다.** 한때 `resolve`가 레지스트리 조회 한 줄이었는데, 그러면 Map이
만료·축출된 것도, 그 이름에 평범한 `mop` Map이 새로 생긴 것도 알 수 없다. 아이템 플래그만 보는
`getattr`로도 부족하다 — 그 플래그는 클라이언트가 `mop create`로 설정할 수 있어(§10.1) 권위가
없다. **이름이 아직 우리 인덱스인지 답하는 것은 메타데이터 원소뿐이다.**

갈리는 것은 판정 **뒤**다.

| | recovery | 그 외 |
|---|---|---|
| Map은 있는데 등록이 없음 | 빈 그래프 만들어 인수 | **Map을 지우고** `NOT_FOUND` |
| 토큰 불일치 | 인수 후 재구축 | 등록 해제 + `NOT_FOUND` — 돌 수 없는 분기다 |
| 손상, 플래그가 우리 것 | Map 삭제 + 등록 해제 | 등록만 해제 (만들지 않은 Map은 안 지운다) |

첫 행이 지우는 이유는, 그 빌드에서 그 Map이 **아무것도 답하지 못하는데 이름은 계속 붙들기**
때문이다 — 메타데이터 원소가 서 있는 한 `vcreate`도 그 이름을 못 가져간다. 도달 경로가 없는
상태이므로 나왔다면 버그이고, 버그의 흔적으로 이름 하나를 영영 못 쓰게 두는 쪽이 더 나쁘다.
`vcreate`가 엔진 쓰기보다 먼저 등록하므로 "Map이 인덱스다"가 참이면 등록은 이미 있었다는 것이
그 판단의 근거다.

두 번째 행이 돌 수 없는 이유는 소유가 바뀌는 사건이 없기 때문이다 — 복제 전송도 재시작 복원도
없고, `vcreate`는 등록 전에 낡은 그래프를 놓는다. 그래도 남겨 둔 것은 그 보장이 코드가 강제하는
것이 아니라 **빌드 구성**에서 나오기 때문이다.

`vcreate`가 만난 남의 Map은 지우지 않고 지목한다.

```
vcreate orphan 2
→ CLIENT_ERROR a Map already exists at 'orphan' and this build cannot rebuild
  an index from it; drop it with 'vdrop orphan' and create it again
```

메타데이터 원소는 복구가 꺼져 있어도 그대로 쓴다. 온디스크 형식을 조건부로 만들지 않기
위해서고, 덕분에 복구를 켠 빌드로 바꾸면 그 Map을 그대로 되살릴 수 있다. 반대로 **벡터는
조건부다**(§6) — 그것은 형식이 아니라 복구의 재료라서, 복구가 없으면 재료도 없다.

## 8. 명령별 동작과 안전성

밑에 깔린 규칙은 하나다 — **실패할 수 있는 일을 다 해두고, 마지막에 넣는다.**

Map 원소는 두 단계로 쓴다. `map_elem_alloc`이 원소 몸통을 잡고 우리가 채우지만 그때까지
아무도 그것을 볼 수 없다. `map_elem_insert`가 Map에 넣는 순간에 보이기 시작한다. 그 전에는 같은 id로 `vgetattr`을 해도 없다. 그래서
쓰기 명령은 **잡고 → 나머지를 다 하고 → 넣는다.** `PendingElem`이 그 사이를 들고 있고,
`insert` 없이 떨어지면 `Drop`이 공간을 반납한다.

**insert가 마지막인 이유는 복제다.** `CLOG_MAP_ELEM_INSERT`가 `do_map_elem_link` 안에서
발행되고(`coll_map.c:246, 283, 392`), 그것이 복제본과 영속화 로그에 쓰기를 실어보낸다.
`map_elem_alloc`은 CLOG를 내지 않고, `ACTION_BEFORE_WRITE`는 `ENABLE_MIGRATION` 아래에서만
정의된다. 즉 **쓰기가 이 노드를 떠나는 지점은 insert 하나**다.

```
alloc     로컬          복제·로그에 아무것도 안 나간다
stage     로컬          usearch는 이 프로세스 안에만 있다
insert    ← CLOG 발행   복제본과 로그가 이 쓰기를 갖는다
publish   로컬          실패할 수 없다
```

그래서 실패할 수 있는 일은 전부 insert **앞**에 있어야 한다. insert를 앞으로 당기면 복제본이
쓰기를 받은 뒤 마스터가 실패하는 상황이 생기고, 그건 마스터에 없고 복제본에 있는 원소를
남긴다 — 지금까지 다룬 어떤 불일치보다 나쁘다. 반대로 실패한 insert는 아무것도 발행하지
않았으므로 `discard`가 정리할 것은 로컬 상태뿐이다.

그 대가로 실패한 `stage`가 그래프에 흔적을 남긴다. HNSW에는 삽입을 되돌리는 연산이 없다 —
`remove`는 키를 `free_key_`로 표시하고 슬롯을 free 리스트에 올릴 뿐이고, 삽입 때
`form_reverse_links_`가 밀어넣은 역링크와 자리를 만들려고 밀어낸 링크는 그대로다. 다만 유계다:
실패한 삽입은 `free_keys_`에서 같은 슬롯을 계속 재사용하므로 손상이 한 곳에 머문다. 실측으로
recall@10이 0.9440 → 0.9397(−0.43 pp)에서 **포화**했고, 반복을 20k에서 500k로 늘려도 같았다.

usearch에 정리 API는 있다. `isolate()`가 모든 노드의 이웃 리스트를 훑어 삭제된 것을 지우고,
`compact()`가 슬롯을 재번호한다. 역인덱스가 없어 전체 순회가 필요하므로 삭제 연산에 붙어 있지
않다. 우리는 둘 다 부르지 않는다 — Rust 바인딩이 `compact()`만 노출하고, 그마저
`inner.write()`를 잡는 전체 재구성이라 서빙 중에 쓸 수 없다. 실질 정리는 복구 경로가 Map에서
그래프를 새로 만드는 것이다.

insert도 실패할 수 있다는 게 중요하다. `maxcount`(`EOVERFLOW`)와 해시 노드 할당(`ENOMEM`)이
`map_elem_insert`가 부르는 `do_map_elem_link` 안에서 검사되므로, alloc이 성공했다는 게 insert도
성공한다는 뜻이 아니다. 따라서 insert의 실패는 **그 사이에 한 일을 되돌릴 수 있어야** 하고,
되돌리기는 실패할 수 없어야 한다.

### 공통 전처리 `resolve`

①은 **빌드와 무관하게** 돈다. 명령이 무엇이든 이름이 아직 우리 인덱스인지부터 확인하고, 그
답을 내는 것은 메타데이터 원소뿐이다 — `getattr`은 Map이 있다까지만 말하고, 만료된 이름에 새로
생긴 `mop` Map을 통과시킨다. ②부터가 갈린다.

```
① 메타데이터 읽기      NoMap    → 그래프를 놓고 NOT_FOUND
   (양쪽 빌드)         Damaged  → ②
                       Unknown  → 아무것도 놓지 않고 에러 그대로
                       상위 버전 → NOT_FOUND (변경 없음)

② 손상이면  recovery   flags가 우리 것 → Map 삭제 + 등록 해제
            아니면     등록만 해제 — 우리가 만들지 않은 Map은 지우지 않는다

③ 레지스트리 조회      recovery: 없으면 메타데이터로 빈 그래프 생성 (fresh 표시)
                       아니면  : 없으면 NOT_FOUND — 다시 만들 근거가 없다
④ 토큰 판정  recovery   fresh || 불일치 → 인수 후 반환
            아니면     불일치 → 등록 해제 + NOT_FOUND (돌지 않아야 정상인 분기)
⑤ 복구 완료 대기분     → 토큰 발급·기록, 정상 전환 (recovery만)
```

**메타데이터를 먼저 읽고, 레지스트리는 그 뒤에 한 번 본다.** 판정하는 것이 메타데이터이므로
순서가 그렇다. 다만 읽기 **앞**에 시각을 하나 집는다 — `registry::now()`, 원자 로드 하나이고
조회도 락도 아니다.

시각이 필요한 이유는 판정이 락 밖에서 나오기 때문이다. 판정이 나오고 레지스트리에 도달하는
사이에 그 이름이 **다른 인덱스**를 들고 있을 수 있다 — `vcreate`가 그 사이에 등록한 경우가
정확히 그것이다. 이름만 보고 지우면 방금 만든 Map을 아무도 섬기지 않게 되고, 재구축이 없는
빌드에서는 `vdrop` 전까지 돌아올 길이 없다. 그래서 `remove_if_stale`은 **그 시각보다 먼저
발행된 항목만** 지운다.

시각은 발행 순서를 센다. `VectorIndex::publish`가 전역 시계를 한 칸 돌리고 **돌리기 전 값**을
찍으므로, 같은 값을 읽은 판정은 그 발행보다 늦지 않았다는 뜻이 되어 그 항목을 건드리지 않는다.
그리고 **발행되지 않은 항목(`0`)은 어떤 판정도 건드리지 않는다** — 그것이 `vcreate`가 이름을
claim하고 Map을 아직 안 쓴 구간이다.

Map은 있는데 등록이 없는 경우는 두 빌드가 다르게 답한다. recovery 빌드는 메타데이터로 빈 그래프를
만들어 인수한다(③). 아닌 빌드는 **Map을 지운다.** 그 빌드에서 그 Map은 아무것도 답하지 못하고,
메타데이터 원소가 서 있는 한 `vcreate`도 그 이름을 못 가져간다 — 손으로 `vdrop`을 하기 전까지
죽은 이름이다. 로그를 크게 남기고 지운다.

이 판단이 성립하는 근거는 `vcreate`가 **엔진 쓰기보다 먼저 등록**한다는 것이다. 그래서 "Map이
인덱스다"가 참이면 등록은 이미 있었다 — 없다는 것은 그 뒤에 사라졌다는 뜻이고, 그럴 경로가
없으므로 버그다. 버그의 흔적으로 이름 하나를 영영 못 쓰게 두는 쪽이 더 나쁘다.

`vcreate`가 그 구간의 주인이다. 아래 §`vcreate`를 보라.

recovery가 없는 빌드에서 ④가 돌 수 없는 이유는 소유가 바뀌는 사건이 없기 때문이다 — 복제 전송도
재시작 복원도 없고, `vcreate`는 등록 전에 낡은 그래프를 놓는다. 그래도 남겨 둔 것은 그 보장이
코드가 강제하는 것이 아니라 **빌드 구성**에서 나오기 때문이다.

### 만료·축출된 인덱스는 청소가 놓아준다

명령마다 자기가 받은 이름에 대해서는 Map이 없으면 그 자리에서 그래프를 놓는다. 그런데 **아무도
다시 찾지 않는 인덱스**는 그 기회가 오지 않는다 — `EXPTIME`으로 만료됐든 메모리 압박에
축출됐든, usearch 그래프와 그것이 붙들고 있는 원소 refcount가 프로세스가 끝날 때까지 남는다. 이 모듈이 들고 있는 것 중
가장 큰 것들이다.

**일은 스레드가 하고, 커넥션은 쿠키가 필요한 호출 하나만 빌려준다.**

```
sweeper 스레드     가장 차가운 BATCH(10)개 이름을 골라 내놓는다   ← 전체 엔트리를 읽는다
  커넥션 ①         getattr(이름₁) → 없다, 돌려준다               ← 이거 하나. 끝
  커넥션 ②         getattr(이름₂) → 있다, 잊는다
  …
sweeper 스레드     없다고 온 것들을 레지스트리에서 빼고 해체한다
```

`sweep::maybe`가 하는 일은 원자 로드 하나(`OFFERED`)로 내놓은 게 있는지 보고, 있으면 하나 집어
`getattr` 한 번을 하고, `KEY_ENOENT`면 돌려주는 것이 전부다. 그 외 결과는 이름에 대해 아무것도
증명하지 않으므로 버린다. **훑지도, 지우지도, 해체하지도 않는다.**

이 분담의 기준은 하나다 — **쿠키가 필요한가.** `getattr`은 키를 받는 API라 필요하고([§7.5](#75-스냅숏은-워커가-뜬다)),
고르는 것과 해체하는 것은 필요 없다. 그래서 필요 없는 쪽은 전부 스레드에 있다.

*고르기*는 스레드가 1초마다 한다. 엔트리마다 `last_access`(아래)를 읽어 정렬하고 가장 차가운
10개를 내놓는다. O(N)이지만 커넥션이 무는 O(N)이 아니다. 이전 판이 여기서 틀렸었다 — 커서를
어떻게 만들든 "다음 이름"을 고르려면 키를 전부 훑어야 했고, 그 훑기가 커넥션에 남아 있었다.

내놓은 10개를 다 소진하기 전에는 다시 채우지 않는다. 채우면 같은 차가운 이름만 계속 나오고
나머지는 영영 차례가 안 온다.

*해체*도 스레드가 한다. 아래를 보라.

### 접근 시각은 왜 기록하나

`VectorIndex`에 `last_access`가 있고 `registry::get`이 갱신한다. 두 가지 때문이다.

**차례를 정한다.** 해시맵에는 순서가 없으니 "다음"이라는 게 없다. 마지막 접근 순으로 세우면
그 자체가 순서가 되고, 커서 같은 별도 상태가 필요 없다.

**있을 법한 곳부터 본다.** 방금 명령이 만진 인덱스는 방금 Map이 있었던 인덱스다. 차가운 쪽부터
찌르는 것이 뭔가 사라졌을 가능성이 높은 쪽부터 찌르는 것이다.

시계는 진짜 시각이 아니라 스레드가 1초마다 올리는 `ACCESS_TICK` 카운터다. 명령마다 시각을
읽으면 이 용도에 비해 비싸고, 필요한 건 누가 누구보다 차가운가뿐이다. `touch`는 **읽고 나서
다르면 쓴다** — 같은 틱 안에서는 값이 이미 맞으므로, 엔트리의 캐시 라인이 다른 코어에게
깨끗하게 남는다.

**별도 스레드가 아니라 워커 스레드에서 도는 것이 핵심이다.** `getattr`은 키를 받는 API라
쿠키가 필요하다([§7.5](#75-스냅숏은-워커가-뜬다)의 표). 커넥션 없는 스레드가 그것을 부르면
마이그레이션 중에 널 역참조다. 청소는 자기를 촉발한 명령의 `Store`를 빌려 쓴다.

청소가 훑는 것은 `registry::names()`, 곧 **재구축 중인 것까지 포함한 전부**다. 재구축 도중 Map이
사라진 인덱스야말로 놓아줘야 할 것이라 `snapshot()`(서빙 가능한 것만)을 쓰지 않는다.
`RUNNING` 플래그는 `Drop`으로 푼다 — 패닉으로 켜진 채 남으면 이후 청소가 전부 멈추고, 막으려던
것이 조용히 무한해진다.

### 해체도 같은 스레드가 한다

레지스트리에서 항목을 빼는 일 자체는 **해시맵에서 하나 빼는 것**이 전부여야 한다. 그런데 그
자리에서 마지막 `Arc`가 떨어지면 `AnnIndex::drop`이 이어 붙는다 — 벡터마다 refcount 하나를
돌려주고(`map_elem_release`가 100개마다 엔진 캐시 락을 잡는다) usearch 그래프를 소멸시킨다.
200만 벡터짜리면 그 시간이 전부 **레지스트리 쓰기 락 안에서** 흐르고, 모든 명령의 이름 조회가
그동안 선다.

그래서 레지스트리를 떠난 항목은 `sweep::retire`로 간다. 큐에 넣고 깨우면 `arcvector-sweep`
스레드가 락 밖에서 떨어뜨린다. 쿠키가 필요 없는 쪽이라 스레드에 둘 수 있다 — 해체가 부르는 것은
`map_elem_release`와 usearch 소멸자 둘뿐이다([§7.5](#75-스냅숏은-워커가-뜬다)).

레지스트리를 나가는 길은 전부 이 규칙을 따른다: `remove_if_stale`, `remove`(`vdrop`),
`remove_observed`, `unput`, 그리고 `vcreate`가 낡은 그래프를 밀어낼 때의 `previous`. 어느 쪽이든
**가드를 놓은 다음** 넘긴다. 청소가 부르는 `remove_if_stale`도 예외가 아니다 — 스레드가
자기 큐에 넣고 다음 바퀴에 떨어뜨린다.

마지막 `Arc`가 아니면 넘겨도 참조 하나가 줄 뿐이고, 아직 들고 있는 명령이 끝날 때 그 스레드가
해체를 문다. 그건 원래 그 인덱스를 쓰고 있던 스레드라 새로 생기는 비용이 아니다. 수거가 실제로
막는 것은 청소가 만드는 경우 — **아무도 안 쓰는데** 해제하는 쪽이 값을 치르는 상황이다.

큐를 못 늘리면(`try_reserve` 실패) 그 자리에서 떨어뜨린다. 느린 것이 그래프를 새는 것보다는
낫다.

### 명령별

| 명령 | 준비 | 공개 | 공개가 실패하면 |
|---|---|---|---|
| `vcreate` | 그래프 객체 → 메타데이터 원소 alloc | 원소 insert(속성 동봉, 이름 판정도 겸한다) | 엔진이 Map까지 되돌린다 |
| `vadd` | 원소 몸통 예약 → 태그 붙은 노드 삽입 | hold { 원소 link → 노드를 그 주소로 rename } | `discard`가 자기 노드만 뗀다 |
| `vsetattr` | 현재 값·주소 읽기 → ATTR 덮어쓰기 | hold { 업서트로 교체 → 노드를 새 주소로 rename } | 되돌릴 것이 없다 — 헌 원소가 그대로 링크돼 있다 |
| `vdel` | — | hold { 원소 take(주소) → 집합에서 뗀다 } | 그래프 노드만 남고, 아무도 안 들어 검색이 걸러낸다 |
| `vdrop` | Map 삭제 | 레지스트리 해제 | Map 삭제가 실패하면 레지스트리를 건드리지 않는다 |

**그래프에도 공개 단계가 있다 — 이름 붙이기다.** `resolve`가 태그 붙은 키를 버리므로,
**아무도 이름 붙이지 않은 키 아래의 노드는 그래프에 있어도 보이지 않는다.** 그래서 `stage`는
가짜 키로 HNSW에 넣기만 하고 그 노드를 주소로 옮기지 않는다.

`vsetattr`은 이 표에서 유일하게 **그래프에 노드를 넣지도 빼지도 않는다.** 원소가 교체되니
노드가 새 주소로 따라갈 뿐이고, 그것은 `rename` 하나다.

`stage`가 이름을 붙이지 않는다는 게 핵심이다. 한때 `stage`에서 바로 이름을 옮겼는데, 그러면
원소 링크 전에 노드가 공개되므로 그 사이에 끼어든 `vdel`이 **아직 링크도 안 된 노드**를 지우고
그 이름을 잊는다. 그 다음 링크가 성공하면 Map에는 원소가 있고 그래프에는 아무것도 없다 —
검색으로 영원히 안 잡히는 원소다. 창을 좁히는 게 아니라 공개 시점을 맞춰야 닫히는 구멍이다.

키가 주소가 된 뒤에도 그렇다. 바뀐 것은 **무엇이 이름이냐**이고 staging이 지키는 것은
**언제 이름을 갖느냐**다. 주소를 처음부터 키로 쓰면 삽입이 끝난 순간부터 노드가 이름을 갖고,
원소 링크는 아직이다.

```
  reserve    원소 몸통 확보          값은 아직 안 씀
  stage      HNSW 삽입, 이름 없음    아무도 못 봄
┌ hold ────────────────────────────────────────────────┐
│ insert    Map에 넣는다             CLOG가 여기서 나간다 │
│ rename    노드를 그 주소로 옮긴다   그래프 쪽 공개     │
└──────────────────────────────────────────────────────┘
```

**두 공개가 한 hold 안이다.** 그리고 조회의 해석도 같은 hold를 잡으므로 그 사이를 관측할 수
없다. 순서가 `insert` 먼저인 것은 주소가 링크되기 전에는 이름이 될 수 없기 때문이다 — 그 전에
이름을 붙이면 Map에 없는 원소의 id가 나간다.

`reserve`가 먼저인 것은 그것이 메모리 압박에서 가장 잘 실패하는 단계이기 때문이다. 값이 키를
담지 않으니 순서를 이렇게 둘 수 있고, 실패하면 되돌릴 노드가 없다.

`vdel`은 원소를 **읽고 지우는 것을 한 엔진 호출로** 한다. `map_elem_get`에 `delete` 플래그가
있어서, 확인과 삭제 사이에 쓰기가 끼어들 틈이 없다.

`discard`는 되돌릴 게 없다. 이름을 붙인 적이 없으므로 예전 주소와 예전 노드가 그대로 있고,
자기가 넣은 노드만 떼면 끝이다. `publish`는 이름을 붙이고 밀려난 노드를 회수한다. 둘 다
해시맵 조작과 컨텍스트를 쓰지 않는 `remove`·`rename`뿐이라 실패할 수 없다. 예전 벡터를 읽어뒀다가
다시 삽입하는 설계였다면 되돌리기가 HNSW 삽입이 되고, 그것이 또 실패할 수 있었다.

창 안에서 `vdel`이 끼어들면 그것은 예전 주소만 보고 지운다. 이어서 insert가 성공하면 Map은
원소가 있다고 말하므로 `publish`가 새 노드에 이름을 붙인다 — 늦게 도착한 쓰기가 이긴 것이고
상태는 일관적이다. insert가 실패하면 `discard`가 자기 노드만 떼고 삭제가 그대로 선다.

### hold 안에 들어온 것

두 공개가 한 hold 안이므로, 그 hold를 잡는 것은 아무것도 사이에 끼지 못한다.

| hold 중에 들어온 것 | 결과 |
|---|---|
| `vgetattr` | Map만 읽으므로 hold와 무관. 링크 전이면 예전 값, 후면 새 값 |
| `vsim`의 `resolve` | **기다린다.** 그래서 등록 전이나 링크 후만 본다 |
| `vsim`의 FILTER 콜백 | 노드마다 짧은 읽기락이라 기다린다 — 검색 내내 잡으면 모든 쓰기가 멈추므로 노드 단위로 뒀다 |
| 같은 id `vadd`·`vdel`·`vsetattr` | **들어오지 못한다.** 배타 hold에서 기다린다 |
| 다른 id `vadd`·`vdel`·`vsetattr` | **들어오지 못한다.** hold는 인덱스 단위다 — 대가는 아래 |

FILTER 콜백의 읽기락을 **노드마다** 잡는 것은 지금도 그렇다. 키가 주소가 되면서 술어가 그
락 안에서 원소를 역참조하게 됐지만(§키), 범위는 그대로 노드 하나다. 검색 전체에 걸쳐 잡아
보니 정확히 위에 적힌 값이 나온다 — 쓰기가 그 검색이 끝날 때까지 선다.

**hold가 id별이 아니라 인덱스별이라는 게 이 설계의 대가다.** 스트라이프 락을 없앤 값이고,
쓰기 쪽 비용은 대체로 없다(엔진 호출이 어차피 엔진 캐시 락에 줄을 선다). 새로 생긴 것은
**필터 없는 `vsim`이 쓰기의 엔진 호출을 간접적으로 기다린다**는 것이다 — 전에는 엔진 락을
아예 건드리지 않았다.

창 안의 엔진 호출은 하나가 아니다. 주소를 키로 쓰면서 `vadd`가 셋이 됐다 — 밀려날 원소 찾기,
링크, 새 원소 hold. 매핑이 있을 때는 밀어낼 노드를 해시 조회로 알았고 refcount도 필요 없었다.
`vsetattr`도 셋이다(alloc·업서트·hold). 그 길이는 아직 재지 않았다.

### held 락이 무엇을 닫았나

두 저장소가 같은 쓰기 쌍을 다르게 정렬했다. 노드는 원소를 넣기 전에 들어가므로 **그래프의
승자는 나중에 `stage`한 쪽**이고 **Map의 승자는 나중에 원소를 넣은 쪽**이다 — 독립된 두
순서다. 어긋나면
원소는 한 쓰기의 벡터를 갖고 그래프는 다른 쓰기의 것을 갖고, 그 id에 다음 쓰기가 올 때까지
아무것도 고치지 않는다.

`AnnIndex::insert_published`가 **held 집합의 쓰기 락을 엔진 호출 위에 들고** 두 순서를 하나로
만든다. 들고 있어도 되는 이유는 둘이다: `map_elem_insert`가 이미 엔진의 캐시 락에서
직렬화되므로 이 락이 줄 세우는 쓰기는 어차피 줄을 서고 있었고, `ENGINE_EWOULDBLOCK`은 커넥션
단위다 — 원소는 반환 전에 link되고 그 커넥션만 내구성 통보를 기다리므로 지연하는 엔진이 이 락을
열어두지 않는다.

**같은 락이 조회의 해석도 덮는다.** `resolve`가 hold 하나로 hit 목록 전체를 id로 바꾸므로,
조회는 등록 전이나 원소 링크 후만 보고 그 사이를 못 본다. 그게 없으면 FILTER도 `WITHATTR`도
없는 빠른 경로가 **아직 Map에 없고 실패할 수도 있는 쓰기의 id**를 반환한다. 삭제된 유령을
반환하는 기존 노출과 달리 이건 좁은 경합이 아니라 진행 중인 모든 삽입이다.

배타 hold라 같은 id의 쓰기를 스스로 정렬한다. 그래서 예전에 있던 **id별 스트라이프 락
(1024개)이 통째로 없어졌다** — 락이 셋에서 둘로 줄었다.

`vdel`도 같은 hold를 잡는다. 안 잡으면 다른 쓰기의 원소 링크와 이름 붙이기 사이에 끼어들어,
그 쓰기가 Map에 없는 원소의 노드에 이름을 붙인다. 복구의 refill도 잡는다 — 복구와 `vadd`가
같은 id에 겹치면 낡은 값을 재생할 수 있다.

승자를 정하는 것은 hold이지 어느 비교도 아니다. 한때 `bind`가 키를 비교해 큰 쪽을 이기게 했는데,
그것이 정하는 순서가 Map의 순서와 달라서 애초에 어긋남의 원인이었다. 지금은 밀려나는 주소를
**이 hold 안에서 Map에 물어** 알아낸다 — 밖에서 물으면 같은 id의 두 쓰기가 같은 답을 받는다.

**해제도 이 락이 지킨다.** 조회는 읽기 락 안에서 멤버십을 확인하고 역참조하므로, 쓰기 락이
필요한 해제는 그 사이에 끼어들 수 없다. 그것이 없으면 역참조가 방금 반납된 주소를 읽는다.

락 순서는 하나다: **`inner` 다음 `held`.** 노드 제거는 두 가드를 다 놓은 뒤에 한다. 둘을
동시에 드는 곳은 `clear`·`add_unless_known`·`insert_published`이고, 셋 다 `inner`를 먼저 잡는다 —
`insert_published`가 `rename` 때문에 둘 다 필요한데 순서를 뒤집었더니 `clear`와 데드락이었다.

### 키는 원소의 주소다

```rust
live:       HashSet<u64>   // 이 그래프가 refcount를 든 원소들의 주소
tombstones: HashSet<u64>   // 재구축 중 삭제된 주소
```

usearch 키가 **그 노드가 서 있는 Map 원소의 주소**다. 그래서 `key → id`가 조회가 아니라
**역참조**다 — 원소가 자기 필드 바이트를 들고 있고, 그게 id다. `get_elem_info`가 그 포인터와
길이를 준다.

한때 여기 `id ↔ key` 양방향 매핑이 있었다. 슬롯 배열, `by_id` 해시맵, 인터닝된 문자열, 키에 박은
세대, 슬롯 발급·퇴역·회수, 그리고 회수 시점을 재던 `searching` 카운터. 2M 항목에 165MB였고,
지금 자리를 대신하는 주소 집합이 40MB 남짓이다.

**주소를 주소로 유지하는 것이 refcount다.** 엔진은 refcount가 0일 때만 원소를 해제하므로
(`do_map_elem_unlink`, `do_map_elem_replace`), 삭제나 덮어쓰기로 unlink된 원소도 그래프가 들고
있는 동안은 같은 자리에 남는다. 그것이 없으면 슬랩이 그 주소를 다음 원소에게 내주고, 역참조가
남의 id를 읽는다.

**나머지 안전은 락이 맡는다.** 조회는 읽기 락을 잡고 멤버십을 확인한 뒤 **그 락 안에서**
역참조하고, 해제는 쓰기 락을 잡는다. 확인과 역참조 사이에 주소가 돌아갈 수 없다 — 쓰기가
기다린다. 지연 해제 목록도, 진행 중인 검색을 세는 카운터도 필요 없다.

### staged 노드는 태그 붙은 가짜 키를 쓴다

주소를 키로 쓰면 곤란한 자리가 하나 있다. `alloc_elem`이 **필드 바이트를 이미 써 두므로**,
링크 전에 그 주소를 역참조하면 id가 읽힌다 — 아직 어느 Map에도 없는 원소의 id가 검색 결과로
나갈 수 있고, 그 쓰기는 아직 실패할 수 있다.

그래서 `stage`는 주소가 아니라 `1 << 63 | 일련번호`를 키로 넣는다. 유저 공간 주소가 쓰지 않는
비트라, 조회는 **비트 검사 하나**로 그 행을 버린다. 맵도 집합도 보지 않는다.

링크가 성공하면 `insert_published`가 `Index::rename(placeholder, addr)`로 키를 바꾼다.
usearch의 `rename`은 `slot_lookup_` 엔트리 하나와 슬롯의 `key` 필드만 고치고 **그래프는 건드리지
않는다.** 이름이 붙는 시점이 링크 뒤라는 성질은 그대로다.

### 밀려난 주소는 hold 안에서 읽는다

덮어쓰기는 헌 노드를 떼어내야 하는데, 그래프는 나가는 원소를 **주소로만** 안다. 어느 주소인지는
Map만 답할 수 있으므로 `insert_published`가 클로저를 받아 **hold 안에서** 부른다.

밖에서 읽으면 이렇게 된다:

```
쓰기 A: hold_addr("v1") → X
쓰기 B: hold_addr("v1") → X
쓰기 A: [hold] 링크 Y, 발행, take(X) → 성공, 해제
쓰기 B: [hold] 링크 Z, 발행, take(X) → 이미 없음
        → Y가 영영 held로 남고, "v1"에 노드가 둘이다
```

hold 안에서 읽으면 한 이름에 대한 쓰기가 직렬화되므로 B는 Y를 본다. 이건 테스트를 옮기다가
드러난 실제 경쟁이다.

### 드롭이 전부 놓아준다

마지막 `Arc`가 떨어질 때는 레지스트리 항목이 **이미 빠진 뒤**라, 놓아달라고 부탁할 호출자가
없다. 그래서 `AnnIndex`가 `Arc<dyn Elements>`를 들고 있고 `Drop`이 `take_all()`을 해제한다.
이게 없으면 만료된 인덱스가 원소를 프로세스 끝까지 붙잡고, 그동안 엔진의 회계는 그것을 이미
비웠다고 센다.

구현이 **detached**인 이유는 그래프가 모든 커넥션보다 오래 살기 때문이다. `Store`는 쿠키를
들고 있어 넣을 수 없고, 넣을 필요도 없다 — 여기서 부르는 `get_elem_info`와 `map_elem_release`는
쿠키를 쓰지 않는다(§7.5). 그 덕에 이 `Drop`을 수거 스레드에서 돌릴 수 있다(§8).

### 검색은 epoch를 확인한다

`clear`는 붙들고 있던 주소를 **전부 돌려준다.** 그러면 엔진이 그 자리를 다른 원소에게 내줄 수
있고, 그 전에 키를 캡처한 검색이 역참조하면 **엉뚱한 id**를 읽는다. 멤버십 검사로는 못 막는다 —
새 원소가 우연히 같은 주소를 받으면 집합에 정말로 들어 있다.

그래서 `clear`가 epoch를 올리고, 검색은 진입할 때 읽어두고 해석할 때 비교해 다르면 결과를 전부
버린다. `Staged`의 owner 토큰을 독자 쪽에 적용한 것이다.

캡처와 해석이 **한 호출(`search`)** 인 것도 관련이 있다. 뒷절반이 원소 주소를 역참조하는데,
그것을 안전하게 만드는 락을 아는 것은 이쪽뿐이다.

키가 원소마다 새로 붙지만 키를 이름으로 쓰는 곳은 그래프 안뿐이다. 응답에는 id만 나가고,
복구는 Map의 field에서 id를 다시 읽는다 — 저장된 어디에도 노드 번호가 없으니 그래야 하고,
주소는 애초에 저장할 수 있는 값이 아니다. 이름 없는 노드는 `len`에도 안 잡히므로 `vadd`의
정원 검사도 부풀지 않는다.

**실패는 아무것도 남기지 않는다.** `stage`가 실패해도 되돌릴 것이 없다 — 발급한 것은 가짜 키
하나이고 집합에 넣은 적이 없다. 원소 쓰기가 실패하면 `insert_published`는 그 노드만 떼면 된다:
태그가 붙은 채였으므로 그 사이 아무도 이름으로 쓸 수 없었고, 밀려난 주소는 손대지 않았다.
집합에만 남으면 `len`이 부풀고, `len`은 `vadd`가 `maxcount`와 견주는 값이라 **다른** id의
`vadd`가 `Overflowed`로 잘못 거절될 수 있다.

### 삽입 순서

```
① reserve_elem      원소 몸통만 확보 (값 미작성).  여기서 주소가 정해진다
② ③ ④ stage         가짜 키 발급 → in_flight++ → HNSW 삽입, 몸통 채우기
⑤ ┌ inner.read() → held.write() ────────────────────────────┐
  │ displaced()      밀려날 원소를 Map에서 찾는다 (주소+hold)│
  │ pending.insert() 엔진 링크 = 결과 확정                   │
  │ hold_addr()      새 원소의 refcount — 그래프가 가져간다  │
  │ rename(가짜→주소) 노드가 이름을 갖는다                   │
  │ publish(주소)     집합에 들어간다                        │
  │ take(밀려난 주소) → refcount 둘 다 반납                  │
  └──────────────────────────────────────────────────────────┘
⑦ 밀려난 노드 제거, in_flight--  (Staged의 Drop)
```

alloc이 먼저인 것은 그것이 메모리 압박에서 가장 잘 실패하는 단계이기 때문이다 — 먼저 하면
실패가 이 호출 하나로 끝나고, 되돌릴 노드가 없다. 값이 키를 담지 않으니 순서를 이렇게 둘 수
있다. 주소가 거기서 정해지는 것은 부수 효과다: `map_elem_insert`는 우리가 준 그 할당을 링크하고,
교체일 때도 새 원소가 우리 것이다.

②~④가 락 밖인 것은 값이 비싸기 때문이다: 768차원 HNSW 삽입이 **367us**로 측정됐고, 락 안에
남은 집합 쓰기는 **0.22us**다. 그리고 태그 붙은 노드는 아무도 못 보므로 밖에 둬도 된다.

락 안에 엔진 호출이 셋이 됐다 — 밀려난 원소 찾기, 링크, 새 원소 hold. 앞뒤 둘이 매핑을 없앤
대가다. 매핑이 있을 때는 밀어낼 노드를 해시 조회로 알았고 refcount는 필요 없었다.

삭제는 대칭이다 — `in_flight++` → hold { 엔진 take(주소+hold), 집합에서 제거, refcount 반납 }
→ 노드 제거 → `in_flight--`. 삭제에도 `in_flight`를 올리는 이유가 있다: hold 직전에 키를 해석한
조회가 hold 뒤에 렌더하면 읽을 원소가 없어 그 행이 탈락하므로, 하나 더 요청해야 답이 `k`개다.

`vcreate`는 메타데이터 원소가 없는 Map을 **만들 수가 없다.** `map_elem_insert`에 `attrp`를
넘기면 엔진이 Map이 없을 때 그 속성으로 만들고 원소를 넣는데, 원소가 안 들어가면 방금 만든
Map을 다시 unlink한다 — 그것도 `LOCK_CACHE()` 아래 한 번에.

```c
if (ret == ENGINE_KEY_ENOENT && attrp != NULL) {
    it = do_map_item_alloc(key, nkey, attrp, cookie);
    ...  *created = true;
}
if (ret == ENGINE_SUCCESS) {
    ret = do_map_elem_insert(it, elem, replace_if_exist, replaced, cookie);
    if (ret != ENGINE_SUCCESS && *created)
        do_item_unlink(it, ITEM_UNLINK_NORMAL);
}
```

그래서 `map_struct_create`를 부르지 않는다. 한때 Map을 먼저 만들고 `put_elem`을 하고 실패하면
`drop_map`으로 되가져왔는데, 그건 엔진이 원자적으로 하는 일을 두 호출로 쪼갠 뒤 그 사이의 창을
직접 메우는 것이었다. 되가져오기 자체가 실패하면 고아 Map이 남는 경로도 함께 사라졌다.

**등록이 먼저이고 엔진 쓰기가 마지막이다.** 이 모듈이 어디서나 지키는 규칙이다 —
`map_elem_insert`가 `CLOG_MAP_ELEM_INSERT`를 내보내 쓰기가 이 노드를 떠나는 지점이므로, 실패할
수 있는 일은 전부 그 앞에 둔다. 레지스트리 등록도 그중 하나다(해시맵이 자라야 한다). 뒤에 두면
이미 만든 Map에 대해 답한 뒤 실패하는 것이고, 되돌릴 방법이 Map 삭제밖에 없다.

```
AnnIndex::new(...)      ← 그래프 객체 (메모리)
registry::put(index)    ← 이름을 claim. 미발행 상태로 들어간다 — 엔진을 만지기 전에
alloc_elem(...)         ← 원소 몸통 확보 (아직 Map에 안 붙는다)
map_elem_insert(...)    ← 엔진 쓰기, 마지막
  Ok(true) → registered.publish()  — 실패할 수 없는 유일한 마지막 단계
  그 외    → registry::unput(내 항목, 이전 항목)
```

`put`이 `alloc_elem`보다도 앞인 이유는 같다 — 자라야 하는 자료구조는 레지스트리 하나뿐이므로
가장 먼저 물어보고, 거절당하면 엔진에는 아무 일도 일어나지 않는다.

**등록만 되고 Map이 아직 없는 구간을 덮는 것이 "미발행"이다.** 그 사이에 들어온 명령은 "이
이름은 인덱스인데 Map이 없다"고 읽는데, 그건 낡은 판정이 아니라 자기가 본 것에 대한 **옳은**
판정이라 시각 비교로도 막히지 않는다. 막을 수 있는 것은 항목 자신뿐이다 — 아직 답할 준비가
안 됐다고 말하는 것. 그래서 어떤 판정도 미발행 항목을 놓지 않는다.

이 방식이면 **엔진 호출에 걸쳐 락을 잡지 않는다.** 레지스트리 락은 `put`·`unput`·해제에서 각각
짧게만 잡힌다. 전역 쓰기 락을 `map_elem_insert` 내내 쥐고 있으면 그동안 모든 명령의 이름 조회가
대기하는데, 엔진 캐시 락이 붐비는 서버에서 그 대가는 작지 않다.

`unput`은 **이름이 아직 내 항목을 들고 있을 때만** 되돌린다. 같은 이름에 `vcreate`가 하나 더
들어와 내 항목을 밀어냈다면 그건 그쪽 것이다. 그리고 되돌리기는 할당하지 않는다 — 값만 바꾸거나
지우고, 키는 `put`이 이미 넣어 뒀다.

`replace_if_exist`는 **거짓**이다. 참이면 그 사이 다른 커넥션이 같은 이름으로 만든
메타데이터를 덮어써서 owner와 설정을 날리게 된다. 원소가 이미 있으면 거부되고, 경합에서 정확히
한쪽만 이긴다.

**그리고 이 호출 하나가 이름에 대한 판정 전부다 — 앞서 `getattr`로 있는지 보지 않는다.**
한때는 `probe_map`으로 먼저 확인하고 없을 때만 insert를 했는데, probe는 *이미 지나간* 순간에
대한 답이라 그 뒤에 Map이 생기는 창이 남았고, 그래서 어차피 insert 결과로 다시 판정해야 했다.
그 판정에 필요한 것은 전부 insert가 돌려준다 — 그것도 `LOCK_CACHE()` 안에서 결정된 것이라
보는 것과 하는 것 사이에 창이 없다.

```
Ok(true)          이름이 비어 있었다 → Map도 원소도 우리 것 → 인덱스 등록
Ok(false)         메타데이터 없는 Map이 있었다 → 원소를 되빼고 "이미 있다"로 답한다
Err(ElemExists)   메타데이터가 있는 Map, 곧 이미 인덱스다 → "이미 있다"로 답한다
Err(BadType)      Map이 아닌 아이템이 그 이름을 쓰고 있다 → CLIENT_ERROR
```

`Ok(false)`가 따로 있는 이유: **메타데이터가 없는 Map에는 insert가 성공한다.** 평범한 `mop`
Map이거나 복제 전송이 아직 채우는 중인 Map일 수 있고, 어느 쪽이든 우리가 만든 것이 아니다.
그래서 그 원소를 다시 지우고 Map을 찾았을 때 그대로 돌려놓는다 (`delete_elem`은
`drop_if_empty`를 거짓으로 넘기므로 비어도 지워지지 않는다).

probe를 뺀 김에 따라온 것이 하나 더 있다. 예전에는 probe가 실패하면 "Map이 없다"로 보고
`map_is_gone`으로 레지스트리의 그래프를 놓아줬는데, probe는 일시적인 엔진 오류로도 실패한다 —
멀쩡한 인덱스의 그래프를 날리는 경로였다. 지금은 `Ok(true)`, 곧 **우리가 방금 만들었다**는
사실 뒤에서만 부르므로 그 오판이 없다. `ENGINE_ELEM_EEXISTS`와 `ENGINE_EBADTYPE`을
`StoreError`로 옮긴 것도 이 때문이다. 전에는 둘 다 `Engine(56)` / `Engine(50)`이라는 뭉뚱그린
숫자로 올라와서, 정보가 없는 게 아니라 버려지고 있었다.

남는 비용은 이미 있는 인덱스에 `vcreate`를 다시 쳤을 때 그래프 객체와 원소 alloc이 헛일이
된다는 것 하나뿐이다. `PendingElem`의 `Drop`이 원소를 돌려주고, `vcreate`는 hot path가 아니다.

그래프 객체를 원소보다 **먼저** 만드는 것도 같은 이유 — 지원되지 않는 metric이면 거기서
실패해야 Map을 안 남긴다.

`vdrop`은 **성공하지 않은 삭제를 성공이라고 답하지 않는다.** `KeyGone`만 "원래 없었다"로
취급하고 나머지 엔진 실패는 에러로 올린다. 예전에는 `is_ok()`로 둘을 묶어서, 레플리카나
엔진 장애에서 로컬 인덱스만 날리고 `DROPPED`를 답한 뒤 Map은 그대로 남았다.

### 불변식은 방향이 아니다

"항상 Map에 남고 그래프에서 잃는다"는 말은 틀렸다. 실제로 도달하는 상태는 셋이고 양쪽
방향이 다 있다.

| Map | 그래프 | 언제 | 해악 |
|---|---|---|---|
| 없음 | 없음 | 원소 링크 전, `discard` 후 | 없음 |
| 없음 | 이름 없는 노드 | `stage`~hold 사이 | 안 보인다. 실패하면 `discard`가 뗀다 |
| 있음 | 없음 | 원소는 링크됐는데 `owner` 판정이 이름 붙이기를 무효화, 또는 크래시 | 복구까지 `vsim`에서 빠진다 |
| 있음 | 있음 | 성공 | — |

**"없음 / 이름 있는 노드"는 이제 도달하지 않는다.** 원소 링크와 매핑 등록이 한 hold 안이고
`vdel`도 같은 hold를 잡으므로 그 사이에 끼어들 수 없다. 조회도 같은 hold로 변환하니 그 상태를
관측할 수조차 없다.

성립하는 것은 둘이다.

**어떤 상태에서도 Map에 없는 데이터가 나가지 않는다.** 두 등록이 한 hold 안이고 조회의 변환도
같은 hold라, 이름이 붙은 노드는 원소가 링크된 노드다. `WITHATTR`이나 FILTER가 붙으면 그 위에
Map 되읽기가 한 겹 더 걸리고, 읽히지 않으면 그 히트를 버린다.

**모든 불일치는 그 id에 대한 다음 쓰기나 복구가 정리한다.** 복구가 Map → 그래프 단방향인
것은 이 두 번째 성질 때문이고, 첫 번째 성질이 그 사이를 안전하게 만든다.

**기존 Map을 지우지 않는다.** 복제가 배달했거나 영속화가 복원한 것일 수 있다. 예전 구현은
자기가 만들지 않은 Map을 고아로 보고 지운 뒤 다시 만들었는데, 승격된 노드에서 복제된 벡터를
전부 날렸다.

**`vadd`는 정원을 미리 검사하지 않는다.** 엔진이 insert에서 `maxcount` 초과를 `EOVERFLOW`로
거절하고, Map은 메타데이터 원소 한 칸을 더해 `maxcount + 1`로 만들어지므로 정확히 벡터
`maxcount`개에서 걸린다. 원소를 세는 엔진이 권위다.

그래프의 `len`은 권위가 아니다. 실패한 쓰기나 재구축과 겹친 쓰기가 수를 어긋나게 할 수 있고,
그렇게 수가 높게 나오면 **들어갈 수 있는 id를** `OVERFLOWED`로 거절한다. 한때 `ann.len() >= maxcount`로 미리 걸렀는데, 엔진 검사와 중복이면서
틀릴 수 있는 검사였다. 대가는 정원이 찬 인덱스에 계속 쓰기가 오면 HNSW 삽입을 했다가
`discard`로 되뭉리는 헛일을 한다는 것이다.

`max_element_bytes`는 런타임에 낮출 수 있어 만들 때 들어가던 게 지금은 안 들어갈 수 있으므로
다시 검사한다.

`vgetattr`은 그래프를 **한 번도 보지 않는다.** 항상 원본을 읽으므로 복제가 방금 배달한 원소도
그대로 읽힌다. 복구 중에 막는 건 정확성이 아니라 일관성 때문이다 — `vgetattr`만 답하면 같은
노드의 두 조회 경로가 다른 세계를 보여준다.

## 9. 동시성

락은 셋이다. 순서를 지켜야 하는 것은 앞의 둘뿐이고, 항상 **`inner` → `ids`**다 — 그래서 노드
제거는 `ids`를 놓은 뒤에 한다. 키 발급기는 둘 중 어느 것과도 겹쳐 잡지 않으므로 순서에 들지
않는다.

| 락 | 무엇을 배제하나 | 획득 |
|---|---|---|
| 그래프 `RwLock<Index>` | 용량 재할당 대 나머지 전부 | 삽입·삭제·탐색은 **읽기**락 |
| id 매핑 `RwLock<IdMap>` | 두 저장소의 변경을 하나로 묶는다 | 쓰기·삭제는 **쓰기**락을 **엔진 호출 위에** 들고, 조회는 변환 한 번의 **읽기**락 |
| 키 발급기 `Mutex<Keys>` | free·retired 리스트와 `next_slot` | `stage`가 발급할 때, 노드를 뗄 때. **`ids`와 따로** 잡는다 — 발급이 검색의 변환 뒤에 줄 설 이유가 없다 |

id별 스트라이프 락은 없어졌다. 매핑의 배타 hold가 같은 id의 쓰기를 이미 정렬하므로 두 번째
락이 하는 일이 없었다.

`ids`를 잡는 곳이 크게 줄었다. 검색은 FILTER가 없으면 usearch에 콜백을 넘기지 않으므로 노드마다
잡던 것이 사라졌고, 히트를 렌더할 때만 잡는다. 노드마다 잡을 때는 8스레드에서 질의당 2.3 →
20.8 us로 **코어를 늘리면 느려졌고**, 검색당 하나로 묶으니 이름 붙이기 p50이 0.5 → 83 us로
쓰기 쪽으로 옮겨갔다. 그 검사가 필요 없다는 것이 답이었다 — FILTER는 없는 원소를 읽을 수 없어
저절로 거부하고, FILTER가 없으면 렌더 단계가 이름 없는 키를 버린다.

그래프의 동시 변경은 usearch가 내부에서 처리한다. 그래서 그래프 락은 동시성 장치가 아니라
**재할당 배제 장치**다. 라이브러리가 이미 하는 일을 밖에서 또 잡으면 동시성만 깎인다.

**삽입과 삭제의 경합은 id 매핑 락 하나가 해소한다.** 둘 다 판정과 실행을 쪼개지 않고 매핑
락을 배타적으로 쥔 채 수행하므로, "존재 확인 후 삽입 전에 삭제가 끼어드는" 구간이 없다.

```rust
// remove                                  // add_unless_known
let index = self.inner.read();             let index = self.inner.read();
let mut ids = self.ids.write();  //←같은 락→ let mut ids = self.ids.write();
let key = if rebuilding {                  if ids.is_known(id) { return Ok(false) }
    ids.forget_tombstoned(id)              let (key, _) = ids.intern(id);
} else { ids.forget(id) };
index.remove(key)?;                        self.typed_add(&index, key, vector)?;
// 여기까지 락을 쥔 채                      // 여기까지 락을 쥔 채
```

| 먼저 잡는 쪽 | 경과 | 최종 상태 |
|---|---|---|
| 삭제 | tombstone이 남고 뒤따르는 삽입이 `is_known`에서 걸림 | 삭제됨 |
| 복구의 삽입 | 벡터가 들어가고 뒤따르는 삭제가 제거 | 삭제됨 |

**락 순서 규칙(그래프 → 매핑)은 정확성이 아니라 교착 회피용이다.** 탐색 술어가 그래프 락
아래에서 매핑 락을 잡으므로 나머지를 거기 맞췄다.

**대가는 삭제 쪽에만 남았다.** `remove`는 매핑 락을 usearch 호출까지 쥐므로 **삭제는 인덱스
단위로 직렬화된다.** tombstone의 판정과 실행이 한 락 아래여야 하기 때문이다. 복구의
`add_unless_known`도 `is_known` 판정과 삽입이 갈라지면 안 되므로 같은 값을 낸다.

`vadd`의 삽입은 그렇지 않다. `stage`가 매핑 락을 키 하나 발급하는 동안만 잡고 놓은 뒤 HNSW
삽입에 들어가므로, id가 다른 삽입은 서로를 기다리지 않는다 — usearch가 지원하는 동시 삽입을
그대로 쓴다. 이름을 붙이는 것과 노드를 넣는 것을 갈라놓은 데서 따라온 이득이다. 탐색은 매핑
락을 노드당 짧게만 잡아 서로 간섭하지 않는다.

그래서 `stage`는 `live + 1`이 아니라 `live + THREAD_SLOTS`를 예약한다. 동시 삽입자는 각자
`live`를 읽고 나서 거기에 더하므로, `+ 1`이면 N명이 합쳐서 노드 하나 분량만 예약하게 된다.
용량 경계에서 정상 요청이 `Reserve capacity ahead of insertions!`로 실패하는 경로였다.
동시 진입자 수는 `THREAD_SLOTS`로 이미 묶여 있으니 그만큼이 상한이다. 복구가 용량을 미리
일괄 확보하는 것도 같은 구간을 짧게 하려는 조치다.

### usearch 스레드 컨텍스트 함정

usearch의 Rust 바인딩은 항상 `any_thread()`로 들어가고 이건 **고정 크기 풀**에서 컨텍스트를
꺼낸다. 비면 블록하지 않고 실패한다. 진입점마다 `if (!lock)`으로 걸러 `add_result_t{}.failed
("Reserve capacity ahead of insertions!")`를 내고, cxx가 그것을 예외로 올려 우리 쪽에서
`Error::Index`가 되고, 클라이언트는 `SERVER_ERROR`를 받는다. 크래시는 아니다 — 실패한 락의
`thread_id`는 `SIZE_MAX`이고 그 값이 곧바로 `cast_buffer_`의 오프셋으로 쓰이므로, usearch가
명시적으로 방어해뒀기 때문에 안전한 거절이 된다.

**동시 진입자는 `num_threads + 1`이다** — 벡터 명령을 실행 중인 워커들과 복구 빌더 스레드
하나. `THREAD_SLOTS` = 64는 memcached 자신이 워커 수 권고를 멈추는 지점이라(`-t`가 64를
넘으면 경고) 그가 권하는 모든 구성이 들어온다. 그보다 큰 `-t`에서는 초과 요청이
`SERVER_ERROR`로 실패한다. 확장은 이 상황을 감지할 수 없다 — `server_api.h`에 `num_threads`
getter가 없고 cookie별 `get_thread_index`뿐이라 풀을 배포에 맞춰 잡을 방법이 없다.

한동안 이 자리에 세마포어가 있었다. 초과 워커를 실패가 아니라 대기시켰지만, 지키는 구성이
memcached가 이미 권하지 않는 구성뿐이었고 그 대가로 연산마다 mutex 두 번과 condvar notify
한 번을 냈다. 슬롯을 키우는 쪽이 대안이 되지 못하는 것도 적어둔다 — 슬롯은 선형으로
비싸다. usearch가 스트라이프 락 테이블을 `ceil2(threads × connectivity_max × 4)` 캐시
라인으로 잡기 때문에, 빈 인덱스 하나가 슬롯 4에서 147 KB, 64에서 1,154 KB, 256에서
4,372 KB다(실측). 인덱스 개수만큼 곱해진다.

**실패는 매핑을 남기지 않는다.** `typed_add`가 실패하면 그 호출이 만든 `intern`을 되돌린다.
매핑만 남으면 `len`이 부풀고, `len`은 `vadd`가 `maxcount`와 견주는 값이라 **다른** id의
`vadd`가 `Overflowed`로 잘못 거절될 수 있다. 이미 있던 id를 덮어쓰다 실패한 경우는 매핑을
그대로 둔다 — Map에 원소가 남아 있고, 그 id에 대한 다음 쓰기가 그래프를 고친다.

**`reset`은 컨텍스트도 같이 해제한다.** 예약 컨텍스트 수가 0이 되고, `search`는 용량을
예약하지 않으므로 그 상태의 첫 검색은 실패한다. 그래서 `clear`는 비운 직후 `MIN_CAPACITY`를
다시 예약한다 — `AnnIndex`는 생성부터 소멸까지 검색이 집어갈 컨텍스트가 없는 순간이 없다.
복구 경로는 `reserve(probe.count)`가 먼저 재예약하므로 여기 걸리지 않았지만, `reserve(0)`
하나로 열리는 창이었다.

**천장.** arcus는 연결마다 안정적인 워커 id를 준다(`get_thread_index`, `0..num_threads-1`).
usearch의 `thread` 인자가 원하는 게 정확히 그것이고, 넘길 수 있으면 풀을 안 쓰고 컨텍스트도
실제 워커 수만큼만 잡으므로 이 절 전체가 사라진다. Rust 바인딩의 cxx 브리지가 그 인자를
노출하지 않아서 못 한다.

## 10. 검색 경로

```
vsim
 └─ for_read              복구 중이면 UNREADABLE
 └─ epoch 읽어둠           clear가 그 사이 돌면 결과를 통째로 버린다
 └─ ann.search(q, k + in_flight, accept)
      └─ accept(key)      FILTER가 있을 때만, 노드마다:
                            [읽기락] 태그·멤버십 검사 → 주소 역참조로 id
                                     → ATTR 역참조 → 평가 → 통과분만 원소 보유
      resolve             읽기락 하나로 키 목록 → id 목록. 태그가 붙었거나
                          집합이 안 든 주소면 탈락
 └─ 상위 k개              WITHATTR이면 보유한 원소에서, 없으면 Map에서 한 번 더
 └─ 걸러낸 뒤 개수를 세어 QUERY 헤더에 기록
```

**그래프가 후보를 내고 보유 집합이 결정한다.** 해석이 태그 붙은 키와 집합에 없는 주소를
버리므로, 아직 공개되지 않은 노드와 방금 삭제된 노드가 여기서 흡수된다. 개수를 마지막에 세는
것도 같은 이유다.

**캡처와 해석이 한 호출인 것은 의도다.** 뒷절반이 원소 주소를 역참조하는데, 그것을 안전하게
만드는 락을 아는 것은 그래프뿐이다.

`k`에 `in_flight`를 더해 요청하는 이유가 이것이다. 진행 중인 쓰기·삭제가 결과 슬롯을 차지하고
렌더에서 탈락하므로, 그만큼 더 요청해야 답이 `k`개다. 과소 집계는 무해하다 — 검색이 본 뒤에
시작된 쓰기라는 뜻이니까.

**`for_read`가 반드시 필요한 이유.** usearch에는 "아직 준비 안 됨"이라는 상태가 없다. 절반만
채워진 그래프에 질의하면 아무 불평 없이 그 절반에서 답을 만들어 준다. 거부는 이쪽에서 해야
한다.

**FILTER가 없으면 콜백이 아예 없다.** usearch가 자기 `is_dummy` 경로를 타고, 이쪽은 노드마다
아무것도 안 한다. 노드마다 매핑 락을 잡던 때는 8스레드에서 질의당 2.3 → 20.8us로 **코어를
늘리면 느려졌다.**

술어는 방문 노드마다 호출되므로 싸야 한다. **ATTR를 `serde_json`으로 파싱하지 않는 이유가
이것이다** — 실측으로 제자리 스캔 30.5ns 대 `serde_json::from_slice` 442.6ns, 14.5배다.
파싱은 문서 하나를 트리로 만들면서 키·값마다 할당하고, 스캔은 찾는 필드에서 멈추며 원본을
가리키는 슬라이스를 돌려준다. 후보를 300개 방문하는 질의라면 9µs 대 133µs이고, 뒤쪽은
질의 전체(k=10에 65µs)보다 크다.

첫 노드 이후로는 아무것도 할당하지 않고,
`id_of`는 빌림이 아니라 `Arc`를 돌려준다 — 술어가 이어서 엔진 호출을 하는데 그동안 매핑
락을 쥐고 있으면 모든 검색이 모든 삽입 뒤에 줄을 선다.

## 11. vtable은 단일 ABI가 아니다

`engine_interface_v1`은 **오프셋으로 호출되는데** arcus에는 레이아웃이 하나가 아니다. 소스
트리가 일부를 정하고(`JHPARK_OLD_SMGET_INTERFACE`는 OSS `types.h`에만 있다), `configure`가
나머지를 정한다. 잘못된 조합으로 빌드한 라이브러리는 그 오프셋에 앉은 아무 함수나 부른다.

이 크레이트가 부르는 API 중 그 블록 안에 있는 건 하나도 없다. 플래그가 바꾸는 건 우리 호출
두 개가 *어디에 앉느냐*다.

**런타임 판별자가 없다.** `ENGINE_HANDLE::interface`는 모든 변종에서 1이고, 엔진은 기능
목록을 노출하지 않으며, 그런 걸 보고할 만한 것 자체가 정렬이 의심되는 그 vtable을 통해
도달된다. 그래도 두 사실은 얻을 수 있다.

- **바인딩이 어느 트리에서 왔는지** — 빌드 시점에 헤더 *텍스트*로. OSS 헤더는 `rp_cmd`를
  `#ifdef` 안에서조차 언급하지 않으므로 어떤 define을 줬는지에 좌우되지 않는다.
- **서버가 어느 트리인지** — `server_version()`. `SERVER_CORE_API`에 있는데 이건
  `get_server_api`로 도달하는 다른 구조체이고 앞 17개 멤버가 두 트리에서 동일하다. 엔진
  vtable이 아무리 어긋나 있어도 안전하게 부를 수 있다. EE는 버전에 홀로 선 `E`를 찍는다
  (`0.9.5-E-139`), OSS는 아니다(`1.16.1`).

검사는 셋이고 순서가 중요하다.

1. **교차 트리를 먼저 거부.** 바로 다음 호출에서 죽는 조합이라서다 — `get_config`가 OSS
   레이아웃에서 슬롯 60이고 EE에서는 `cachedump`다. *기능*이 아니라 *트리*를 비교하는 게
   오탐을 없애는 핵심이다. 복제 없이 빌드한 EE 트리는 실재하는 구성이고 복제 있는 것과 같은
   버전을 보고하므로, 기능 기반 규칙은 그걸 거부해버린다.
2. **널 멤버 거부.** arcus는 멤버를 미설정으로 출하하지 않는다.
3. **오작동하는 호출을 지목.** 널 검사에는 구멍이 있다 — 잘못된 오프셋에서 읽은 멤버는 대개
   다른 진짜 함수에 떨어져 포인터는 유효하고 결과만 틀리다. `put_elem`이 그 경우를 잡는다:
   엔진이 원소를 할당해 놓고 그것을 서술하지 못하는 조합은 런타임 조건이 아니다.

**3번은 래치를 건다.** 한 번 걸리면 이후 모든 벡터 명령이 실행되지 않고 같은 에러로 답한다.
메시지 품질 때문만이 아니다. vtable이 어긋나면 엔진의 대답을 믿을 수 없는데, 그중 "이
원소가 없다"를 복구 경로가 손상으로 읽고 **Map을 지운다.** 앞에서 막지 않으면 빌드 실수가
데이터 삭제가 된다.

```
ArcVector: ENGINE ABI MISMATCH — get_elem_info did not describe the element it allocated.
vcreate → SERVER_ERROR engine ABI mismatch …
vadd    → SERVER_ERROR engine ABI mismatch …
```

근본 해결은 여기 없다. EE가 멤버를 중간에 끼우지 않고 `errinfo` 뒤에 덧붙였다면 공통
접두부가 안정적이었을 것이고 라이브러리 하나로 모든 빌드를 감당했을 것이다.

## 12. 에러

핸들러는 `Result<Reply, Error>`를 돌려주고 크레이트 루트의 한 곳이 ASCII 응답으로 바꾼다.
`CLIENT_ERROR`인지 `SERVER_ERROR`인지는 에러 자신에게서 따라 나오므로 호출부가 정할 일이
없다.

| 상황 | 응답 |
|---|---|
| 잘못된 명령행, 범위 밖 인자 | `CLIENT_ERROR` |
| 인덱스 없음 | `NOT_FOUND` |
| 복구 중 읽기 | `UNREADABLE` (엔진의 `ENGINE_UNREADABLE`) |
| 레플리카에서의 쓰기 | `SERVER_ERROR` (엔진이 준 문구) |
| ABI 불일치 | `SERVER_ERROR engine ABI mismatch` |
| 인덱스가 가득 참 | `OVERFLOWED` |
| 원소를 읽을 수 없음 (설명이 앞뒤가 안 맞음) | `SERVER_ERROR`, 그 id를 그래프에서 뗀다 |
| 자라야 할 자료구조가 못 자람 | `SERVER_ERROR` — abort가 아니다 |

`EWOULDBLOCK`은 **실패가 아니다.** 동기 모드 복제 마스터에서 `rp_after_check`는 연산이 이미
성공한 뒤에 돌면서 호출자를 슬레이브 ack의 대기자로 등록한다. "아직 답하지 말라"는 뜻이지
"일어나지 않았다"가 아니다. 이걸 실패로 읽는 것이 이 모듈이 서버를 죽이던 방식이다 —
엔진이 방금 링크한 원소를 해제하려 들면서 `map_elem_free`가 `elem->linked == 0`을 단언하며
죽었다.

아직 없는 건 **기다림**이다. 그래서 벡터 쓰기는 동기 마스터에서도 비동기 내구성으로 답한다.
서버 API에 `waitfor_io_complete`가 있는데도 왜 못 쓰는지, 고치려면 뭐가 필요한지는
[미해결.md §1](미해결.md)에 있다.

### 엔진이 알려준 크기를 믿기 전에 검사한다

`get_elem_info`는 원소 헤더의 값을 그대로 옮겨준다 — `nscore`는 `nfield`(`uint8_t`),
`nbytes`는 `nbytes`(`uint16_t`), `score`는 `elem->data`, `value`는 `elem->data + nfield`.
그 길이로 슬라이스를 만드는 순간, 값이 틀리면 **할당 밖을 읽는다.** 그래서 만들기 전에 본다:

```
score·value 가 널이 아님
naddnl == 0                     Map 원소는 쪼개지지 않는다
nscore <= 255                   uint8_t가 담을 수 있는 한계
nbytes <= 65535, max_element_bytes 이하
value == score + nscore         두 포인터가 같은 할당에 속한다는 유일한 관계
```

마지막 줄이 가장 강하다. 주소만 비교하므로 읽지 않고도 구조가 맞는지 본다.

**검사가 호출 뒤에 있는 것은 앞에 둘 수 없기 때문이다.** 역참조는 `get_elem_info` 안에서
일어난다 — 인자를 읽는 C 함수를 밖에서 감쌀 방법이 없다. 그런데 그 역참조는 **폴트를 내지
않는다.** `do_slabs_free`는 청크를 슬랩 클래스의 free 리스트에 돌려놓을 뿐이고, 슬랩 페이지를
OS에 반납하는 것은 `slabs_final`, 곧 종료 시점뿐이다. 해제된 주소도 프로세스가 사는 동안
계속 매핑돼 있다.

그래서 죽은 주소를 넘겨도 읽기는 성공하고, 그 자리에 지금 들어있는 것 — 다른 Map 원소,
list·set·btree 원소, `hash_item`, free 리스트의 next 포인터 — 을 `map_elem_item`으로 해석한
숫자가 나온다. **시그널도 예외도 없으므로 `try`/`catch`로 될 일이 아니다.** 잡을 수 있는 것은
그 숫자가 앞뒤가 안 맞는다는 사실뿐이고, 위의 다섯 줄이 그것을 본다. `value == score + nscore`는
`map_elem_item`의 레이아웃에서만 성립하므로, 다른 타입이 들어와 있으면 거의 확실히 깨진다.

(`USE_SYSTEM_MALLOC` 빌드는 예외다. `do_slabs_free`가 진짜 `free(ptr)`를 부르므로 할당기가
페이지를 반납할 수 있고, 그러면 폴트가 난다 — 그리고 거기서는 할 수 있는 것이 없다. 테스트용
옵션이다.)

**지금 구조에서는 이 상황이 오지 않는다.** `get_elem_info`에 넘기는 `eitem`은 전부
`map_elem_get`이 refcount를 올려 넘겨준 것이거나 우리가 `map_elem_alloc`한 것이다. 죽은
포인터가 들어갈 경로가 없다. 이 검사는 vtable 오정렬이나 엔진 버그에 대한 **심층 방어**이지
use-after-free 방어가 아니며, 그렇게 만들 수도 없다 — 그래서 usearch 키를 원소 주소로 두는
설계가 성립하지 않는다(§미해결).

걸리면 `StoreError::CorruptElement`이고, 읽기 경로는 **그 id를 그래프에서 뗀 뒤**
`SERVER_ERROR`로 답한다. 떼는 이유는 놔두면 검색이 렌더할 수 없는 행을 계속 돌려주기
때문이고, **Map은 건드리지 않는다** — 믿지 못하는 설명을 근거로 지우는 것은 같은 오독을 두 번
하는 것이다. 재구축 중이면 tombstone을 남겨 refill이 되살리지 못하게 한다.

`FILTER` 술어만 예외다. `bool`을 돌려주는 자리라 명령을 실패시킬 수 없고, 술어는 노드 제거를
부를 수 없다(같은 락 재진입). 그 후보를 빼기만 하고, 렌더나 다음 `vgetattr`이 표면화한다.

### 메모리가 없을 때 무엇이 응답이고 무엇이 abort인가

엔진과 usearch는 할당 실패를 **값으로** 돌려준다 — `ENGINE_ENOMEM`과 usearch의 `Result`.
Rust 표준 컬렉션은 그러지 않는다. `handle_alloc_error`를 부르고 그것은 `abort()`이며,
stable에서 이 훅을 가로챌 방법은 없다(`#[alloc_error_handler]`는 nightly·no_std 전용).
따라서 **증가형 할당은 커지기 전에 `try_reserve`로 물어야** 데몬이 서 있다.

물어보는 자리는 셋이고, 전부 **변형 전**이다 — 실패해도 아무것도 안 바뀌게.

| 자라는 것 | 어디서 예약하나 | 실패하면 되돌릴 것 |
|---|---|---|
| `registry`의 `HashMap` | `registry::put` 안, **엔진 쓰기 앞** | 없음 — 아직 아무것도 안 썼다 |
| `IdMap`의 `slots`·`by_id` | `insert_published`의 hold 안, bind 앞 | 이 호출의 노드 하나 (`drop_node`) |
| `IdMap`의 `tombstones` | `remove_published`, **엔진 삭제 앞** | 없음 — 아직 아무것도 안 지웠다 |

세 번째의 순서가 중요하다. 원소가 이미 지워진 뒤에는 보고할 실패가 없다 — 삭제는 이미
복제본으로 떠났고, 거기서 거절하면 존재하지 않는 상태에 대해 답하는 것이 된다.

첫 번째가 예전에는 이미 만든 Map을 지워서 되돌렸다. 지금은 등록이 엔진 쓰기보다 앞이라 되돌릴
것이 없다 — 실패하면 Map은 애초에 만들어지지 않는다.

롤백이 실패할 수 없는 근거는 **복원이 할당하지 않는다**는 것이다. `insert_published`가
되돌릴 때 부르는 `bind`는 `by_id`가 이미 들고 있는 id를 이미 존재하는 슬롯에 다시 쓸 뿐이다.
`restoring_a_displaced_binding_allocates_nothing`이 그 성질을 용량으로 확인한다.

**그래도 "절대"는 아니다.** `Arc::from(id)`, `format!`, 응답 `String`의 증가처럼 단건이거나
`try_reserve`가 없는 할당은 남아 있고, 실패하면 여전히 abort다. 남은 자리는
[미해결.md §7](미해결.md)에 적었다. 실질적으로는 Linux 기본 overcommit에서 malloc이 null을
잘 돌려주지 않고 OOM killer가 먼저 오므로, 위 셋이 값을 하는 곳은 cgroup 한도가 걸린 컨테이너와
큰 단일 재할당(`Vec`)이다.

## 13. 미해결

[미해결.md](미해결.md)에 열 항목이 있다 — EWOULDBLOCK 대기 없음, `mop insert` 직접 조작,
레플리카 읽기 가용성, 저장 형식 버전, 큰 `M`의 스레드 점유, 자동 테스트가 없는 경로,
Rust 쪽 단건 할당의 abort, 원소 주소를 키로 쓴 대가,
커넥션 없는 스레드의 호출 규칙, `mop delete`로 지운 원소. 각각 증상과 조사 내용,
고치려면 무엇이 필요한지가 적혀 있다.

### 벡터 하나에 드는 바이트

Map 원소, 그것을 담는 arcus 구조물, 그리고 그래프가 든 주소 하나다. **주소 집합은 벡터당
고정**이고 차원·양자화와 무관하다 — 해시 항목 하나이고, 벡터가 3072바이트든 16바이트든 같다.
벡터 1000만, id 평균 13바이트 기준:

| | 768d f32 | 128d b1 |
|---|---|---|
| 양자화된 벡터 (recovery 빌드만) | 3,072 | **16** |
| ATTR 영역 (고정) | 128 | 128 |
| `alen` 헤더 | 2 | 2 |
| arcus 아이템·해시 노드 | ~48 | ~48 |
| held 집합 (`u64` 하나 + 해시 여유) | ~20 | ~20 |
| **합 — recovery** | 3,270 | 214 |
| **합 — 그 외** | **198** | **198** |

읽는 방향이 둘이다.

**복구가 있는 빌드에서는 양자화의 효과가 바닥에 막힌다.** `b1`은 벡터가 512 → 16바이트로 줄어도
**261바이트가 남는다.** 그 바닥에서 가장 큰 항목은 ATTR 고정 영역(128)이다 — 벡터가 상수
오프셋에서 시작하게 하려던 것인데, 저차원 양자화에서는 그 대가가 벡터 자체의 8배다.

**복구가 없는 빌드에서는 그 바닥이 전부다.** 벡터를 저장하지 않으므로(§6) 768d f32도 261바이트,
곧 3,333 → 261로 **13배**다. usearch가 벡터를 따로 들고 있으니 프로세스 전체로 보면 벡터 한 벌은
남지만, 그건 검색이 실제로 쓰는 사본이다.

여기가 두 번 줄었다. `id ↔ key` 양방향 매핑일 때 2M 항목에 **165MB**(그 전, 해시맵 두 개였을
때는 268MB)였고, 키를 원소 주소로 바꾸면서 역방향이 자료구조가 아니라 역참조가 되어 **~40MB**가
됐다. 벡터를 Map에서 뺀 지금, 벡터당 가장 큰 단일 항목은 **ATTR 고정 영역(128)**이고 그것은
`vsetattr`의 전제라 회수 대상이 아니다(§6).

### 지금 구조로 오기까지 물러난 자리

읽는 사람이 같은 길을 다시 걷지 않게, 시도했다가 되돌린 것을 남긴다.

**`id → key`를 원소 헤더에 두기.** `by_id` 테이블을 없애 벡터당 ~30바이트를 아꼈지만, 밀어낼
노드를 알려고 **교체할 값을 엔진에서 읽어야** 했다. 그 읽기가 락 창 안에 들어가서 엔진 호출이
둘이 됐고, `map_elem_insert`가 어차피 같은 원소를 찾는데 그 조회를 한 번 더 하는 모양이었다.

**키를 단조 증가만 시키기.** 유일성이 공짜였지만 배열 인덱싱을 못 쓴다. 페이지 배열(radix)로
바꿔봐도 안 된다 — 키 범위가 총 쓰기만큼 자라는데 살아있는 수는 고정이라, 오래된 생존자 하나가
페이지 하나를 붙잡는다. 쓰기가 살아있는 수의 100배에 이르면 페이지 4096으로 16GB다.

**검색 전체를 보유 집합의 읽기락으로 덮기.** 쓰기의 이름 붙이기 p50이 0.5 → 83us였다. 키가
주소가 된 뒤 술어가 그 락 안에서 역참조하게 되면서 한 번 더 이 모양이 됐다가 되돌렸다 —
범위는 여전히 노드 하나다. 술어 **바깥에서** 노드마다 락을 잡는 설계(usearch 콜백이 아니라
우리 쪽 생존 확인용)는 그보다 나빴다 — 8스레드에서 질의당 2.3 → 20.8us로 **코어를 늘리면
느려졌다.**

**id별 스트라이프 락(1024개).** 같은 id의 쓰기만 직렬화해서 조회를 전혀 막지 않았다. 대신 좁은
창에서 막 쓴 벡터가 검색에 한 박자 늦게 잡혔다. 매핑 hold가 그것까지 없애는 대신, **조회가
쓰기의 엔진 호출을 간접적으로 기다린다** — `cache_lock`이 전역 뮤텍스 하나라, 무관한 트래픽이
그것을 들고 있으면 그 인덱스의 조회 전부가 선다. 조회가 압도적으로 많은 배치라면 스트라이프
쪽이 나을 수 있다.

**`vcreate`가 먼저 `getattr`로 있는지 보기.** probe는 이미 지나간 순간에 대한 답이라 그 뒤에
Map이 생기는 창이 남고, 결국 insert 결과로 다시 판정해야 했다. 그 판정에 필요한 것은 전부
insert가 돌려준다 — 그것도 엔진 캐시 락 안에서 정해진 것이라 보는 것과 하는 것 사이에 창이 없다.

**등록과 엔진 쓰기를 레지스트리 락 하나로 묶기.** 등록만 되고 Map이 없는 구간을 감추려던
것인데, 메타데이터를 먼저 읽는 판정에는 통하지 않는다 — 명령이 hold 안으로 들어와 Map 없음을
읽는다. 그 구간을 덮는 것은 락이 아니라 항목의 **미발행** 표식이고, 그러고 나니 전역 쓰기 락을
FFI 호출에 걸쳐 잡을 이유도 없어졌다.

**절 없는 `vsim`에만 `getattr` 하나 붙이기.** Map이 만료된 것은 잡지만, 그 이름에 평범한 `mop`
Map이 새로 생긴 것은 통과시킨다. 아이템 플래그의 태그는 클라이언트가 설정할 수 있어 권위가 없다.
결국 메타데이터 읽기를 `resolve`로 올려 모든 명령이 거치게 했다.

**`vsetattr`을 제자리 갱신으로.** 고정 128바이트가 노린 것이었고, 그래프가 그 순간만 refcount를
놓으면 `refcount == 0` 조건도 맞출 수 있었다. 접은 이유는 성능이 아니라 정확성이다 — 키가
주소라 독자가 **엔진 락 없이** 그 바이트를 읽는데, 제자리 `memcpy`는 그것을 읽는 도중에 바꾼다.
원소는 링크된 뒤로 불변이어야 한다(§6).

**원소 주소를 usearch 키로 두되 refcount를 안 잡기.** 매핑은 없어지지만 검색 결과를 id로
되돌리려면 그 주소를 역참조해야 하고, 붙들지 않으면 그 시점에 원소가 살아 있다는 보장이 없다.
슬랩이 페이지를 OS에 반납하지 않아 폴트는 안 나지만, 그 자리에 다른 원소가 들어와 **남의 id를
조용히 읽는다.** 그래서 refcount를 잡는 쪽으로 갔다(§9). 대가는 만료·축출이 즉시 회수하지
못하는 것이고, 청소와 `Drop`이 그 지연을 묶는다.

### `THREAD_SLOTS`는 상수 64로 둔다

빈 인덱스 하나가 약 1.1MB다(인덱스 1000개면 1.1GB). 그 값은 usearch에 동시에 들어갈 수 있는
워커 수의 천장이라 **줄이면 `-t 16` 서버의 9번째 워커가 `SERVER_ERROR`를 받는다.** 서버 API에
워커 수가 없어(`get_thread_index`는 인덱스만 준다) 본 적 있는 최대 인덱스를 추적해야 하는데,
쓰기마다 원자 비교가 붙고 늘릴 때 스트라이프 락 테이블을 재할당한다.

### 남은 것

**ATTR을 가변 길이로.** 위 표에서 가장 큰 항목이고, 벡터를 저장하지 않는 빌드에서는 원소의
대부분이다(261 중 128). 원래는 `vsetattr`의 제자리 갱신 때문에 못 건드린다고 봤는데, 그 갱신이
어차피 교체가 되면서(§6) 그 이유는 없어졌다. 남은 이유는 셋이다 — 벡터 오프셋이 `alen`에 따라
움직여 디코딩과 `attr_of`가 계산을 하게 되고, `max_element_bytes` 판정이 ATTR 내용에 흔들리고,
ATTR을 늘리는 갱신이 `EOVERFLOW`로 실패할 수 있게 된다. 셋 다 감당할 만하다면 128바이트가
그대로 돌아온다.

~~**id 텍스트 인터닝.**~~ 해결됐다 — id 텍스트를 이 프로세스가 아예 들고 있지 않다. 키가 원소
주소이므로 이름은 필요할 때 그 원소에서 읽는다(§9).

**`vadd`의 엔진 왕복 줄이기.** 주소를 키로 쓰면서 hold 안의 엔진 호출이 하나에서 셋이 됐다 —
밀려난 원소 찾기, 링크, 새 원소 hold. 앞의 것은 새 id에는 헛일이다. `replace_if_exist`를 거짓으로
먼저 넣어 보고 `ELEM_EEXISTS`일 때만 찾는 방법이 있는데, 대량 적재(전부 새 id)가 그 이득을 다
가져가고 덮어쓰기 위주 워크로드는 한 번 더 무는 셈이다. 재보고 정할 일이다.

**hold 안 `map_elem_insert`의 길이.** 필터 없는 `vsim`이 그만큼 기다리는데 재지 않았다. 엔진이
붙은 서버에서 `vadd` 부하 중 `vsim` p50/p99를 봐야 안다.

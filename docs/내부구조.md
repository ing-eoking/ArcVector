# ArcVector 내부 구조

모듈이 어떻게 짜여 있고, 자명하지 않은 결정이 왜 그렇게 되어 있는지를 다룬다.
명령어 사용법은 [../README.md](../README.md), 모듈별 세부 사항은
[모듈-노트.md](모듈-노트.md), 복제 환경의 동작은
[replication-flows.md](replication-flows.md)에 있다.

---

## 1. 무엇인가

arcus-memcached는 **ASCII 프로토콜 확장**을 적재할 수 있다. 콜백 서술자를 등록하고
그 대가로 명령어 이름을 점유하는 공유 라이브러리다. ArcVector가 그런 확장이다.
데몬 *안에서*, 데몬의 워커 스레드 위에서 돌고, memcached 자신이 쓰는 것과 같은
`engine_interface_v1` vtable을 통해 스토리지 엔진과 이야기한다.

인덱스는 두 계층으로 이루어진다.

```
질의 ──▶ usearch HNSW 그래프 ──▶ 근접 키 ──▶ arcus Map ──▶ 속성
         (탐색 가속)                          (원본)
```

둘은 키로 이어진다. 그래프가 후보를 찾고, Map이 실제 바이트를 갖는다.

## 2. 모듈 지도

세 계층이고, 최상위 배치가 곧 구조다.

```
lib.rs           C ABI — 등록과 memcached의 네 콜백
  command/       명령을 받고, 해석하고, 실행한다
    tokens         토큰 배열을 읽고 응답 한 줄을 쓴다
    request/       명령행 -> 타입 있는 요청                    (순수)
      parse          토큰을 받아 요청으로
    pending        본문을 기다리는 명령
    filter/        FILTER 절의 작은 언어                       (순수)
      json           저장된 ATTR에서 필드 하나 읽기
    handler/       실제 작업 — 두 백엔드를 호출
      access         이 노드가 서빙해도 되는가, 어느 그래프로
      coords         십진 텍스트 -> f32                        (순수)
      index          vcreate, vdrop, vlist, vstats
      vector         vadd, vget, vdel
      search         vsim 두 형태
  arcus/         arcus 엔진에 벡터를 저장 — 원본
    quant          한 좌표를 어떻게 표현하는가                 (순수)
    element        그 바이트가 Map 원소 어디에 놓이는가        (순수)
    engine/        vtable                              (원시 포인터 전담)
      error          엔진 코드, 그중 무엇이 실패인가
      map            인덱스를 담는 Map 아이템
      elem           그 안의 원소들
    abi            빌드-데몬 vtable 대조
  usearch/       검색 — arcus 쪽의 캐시
    index          라이브러리 래퍼: 용량과 락
    idmap          String <-> u64, 그리고 복구용 tombstone
    metric         거리 척도
    threads        예약 컨텍스트 불변식
  registry/      살아 있는 짝, 그리고 한쪽에서 다른 쪽 복구
    metadata       인덱스가 무엇인지를 적은 예약 원소
    recovery       Map으로부터 그래프 채우기
  error          단일 에러 타입과 책임 소재
```

한 파일이 두 가지 일을 하고 있던 곳은 디렉터리로 나눴다. 자르는 기준은 **함께
바뀌는 것끼리 묶는다**이다. `engine`은 무엇을 다루느냐로(Map 아이템 / 그 안의 원소 /
둘 다 돌려받는 코드), `handler`는 명령 그룹으로, `request`는 어휘와 파싱으로,
`filter`는 식과 그 술어가 수행하는 JSON 스캔으로 갈랐다. 의미 있는 파일 중 400줄을
넘는 것은 없다.

### 경계 두 개

**파싱은 상태를 건드리지 않는다.** `command::request`는 토큰을 `Line`/`Body` 값으로
바꾸고 끝난다. `command::handler`는 그 값을 받고 토큰을 보지 않는다. 그래서 문법
규칙이 사는 곳은 정확히 한 군데이고, 핸들러는 서버 없이 단위 테스트로 도달할 수 있다.

**원시 포인터는 `arcus::engine`에만 산다.** `Store::for_cookie`가 유일한 `unsafe`
생성자이고, 그 아래 모든 메서드는 `&self`를 받아 소유값이나 빌린 Rust 값을 돌려준다.
`arcus::element`와 `command::filter`는 순수하며 데몬의 존재를 모른다.

### 방향

`arcus/`를 "엔진을 쓰는 모든 것"이 아니라 *벡터가 arcus에 저장되는 방식*으로 묶은 게
중요하다. `element`는 엔진 호출을 하나도 하지 않지만, 그 모양을 결정하는 것이 arcus다 —
크기 상한은 `max_element_bytes`이고, 고정 144바이트 오버헤드는 arcus의 슬랩 클래스에
잘 들어맞게 고른 값이다.

`usearch/index`가 `arcus/element`에 의존하는 것도 같은 이유다. 인덱스는 저장된 레이아웃
으로부터 구성되고, 스토어가 들고 있는 바로 그 바이트를 넘겨받는다. 그래서 복구가
무손실이고, 의존 방향이 고정된다 — **캐시가 스토어를 알고, 그 반대는 없다.**

## 3. 요청 수명주기

memcached는 확장에 네 개의 콜백을 준다. ArcVector는 넷 다 쓴다.

| 콜백 | 역할 |
|---|---|
| `get_name` | 확장을 식별 |
| `accept` | 명령을 점유하고, 본문 바이트 수를 정함 |
| `execute` | 실행하고 응답 |
| `abort` | 전송 도중 죽은 명령의 상태 해제 |

대부분의 명령은 명령행에서 바로 `execute`로 끝난다. `vadd`와 `VSIM VECTOR`는 바이트
수를 선언하고 좌표를 뒤이어 보낸다 — memcached는 이를 `nread`라 부른다. 이 둘은
`accept`가 버퍼를 등록하고, `execute`가 **빈 토큰 배열**로 한 번 더 호출된다. 그것이
본문이 도착했다는 신호다.

### `accept`는 잘못된 명령행을 거부하지 않는다

`accept`에는 응답 핸들러가 없다. 클라이언트에게 답할 수 없다. 여기서 거부하면 좌표가
연결 버퍼에 읽히지 않은 채 남고, memcached는 그것을 **다음 명령행으로** 파싱한다.
잘못된 요청 하나가 그 연결의 나머지를 망친다.

그래서 `accept`는 바이트 수만 본다. 나머지도 파싱은 하지만 실패는 대기 항목 안에
`Result`로 저장되고, 본문을 다 흘려보낸 뒤 핸들러가 보고한다. 거부는 **바이트 수 자체를
읽을 수 없을 때**만 한다. 그때는 얼마나 버려야 할지 알 방법이 없기 때문이다.

### 모듈 지표가 자체 명령을 갖는 이유

memcached는 자기가 이미 인식에 실패한 명령에 대해서만 확장에게 묻는다
(`memcached.c`의 `unknown_command` 경로). `stats` 같은 내장 명령은 우리에게 오지
않으므로, arcus를 고치지 않고서는 여기서 `stats vector` 섹션을 추가할 방법이 없다.
그래서 `vstats`가 따로 있다.

### ATTR JSON에 공백을 금지하는 이유

memcached의 토크나이저
([`mc_util.c:238`](https://github.com/naver/arcus-memcached/blob/master/mc_util.c))는
공백으로 자르면서 **토큰을 끝내는 공백을 제자리에서 `'\0'`으로 덮어쓴다.** 그래서 쪼개진
JSON을 되붙이려면 그 NUL을 공백으로 되돌려야 하는데, NUL은 클라이언트가 보낼 수도 있는
바이트라 복원이 모호하다.

그래서 ATTR JSON은 **인자 하나**로 받는다. 공백이 있으면 토큰이 더 생기고, 그 사실만으로
거부한다.

```
vadd docs v1 7 2 ATTR 23 {"abc":123,"def":"abc"}     ← 통과
vadd docs v1 7 2 ATTR 15 {"cat": "tech"}            ← CLIENT_ERROR, 공백을 지목
```

잃는 것은 없다. 오히려 공백 예산을 나눠 쓰지 않으므로 **128바이트 전 구간을 쓸 수 있다.**
공백을 허용하던 시절에는 `json.dumps` 스타일이 14필드/120바이트, 콜론·쉼표마다 공백을
넣으면 7필드에서 토큰 한계에 먼저 걸렸다.

토큰 수 한계 자체는 우리가 지키지 않는다. `process_extension_command`가 `accept`를 부르기
전에 거부한다.

```c
// memcached.c:10189
if (ntokens == MAX_TOKENS) {          /* MAX_TOKENS == 30 */
    out_string(c, "ERROR too many arguments");
    return;
}
```

한때 이 모듈에도 같은 검사가 있었지만 도달 불가능한 죽은 코드였다.

검색 필터도 같은 이유로 항마다 토큰 하나를 쓴다. 자유 형식 식을 명령행에 실으면 같은
모호성이 생긴다.

## 4. 원소 레이아웃

인덱스 하나가 Map 아이템 하나(키 = 인덱스 이름)이고, 벡터 하나가 Map 원소 하나
(필드 = 벡터 id)다.

```
 off  0    2   3     4       6        8       16              144
     +----+---+-----+-------+--------+-------+---------------+---------------+
     |"AV"|ver|quant|dim u16|alen u16|rsvd 8B| ATTR 128B     | 양자화된 벡터 |
     +----+---+-----+-------+--------+-------+---------------+---------------+
```

### 왜 뒤에 `\r\n`이 붙는가

arcus는 컬렉션 원소의 크기를 **끝의 `\r\n`을 포함하도록** 잡는다. 내장 명령들이
클라이언트 바이트를 원소 안으로 그대로 `nread`하기 때문에 종결자가 함께 들어온다.
그 두 바이트를 되읽는 곳은 없다 — `mop get`은 값 길이로 `nbytes - 2`를 보고하고 나머지를
줄 끝으로 내보낸다. 그래서 종결자 없이 쓴 원소는 엔진이 길이를 두 바이트 짧게 넘기고
벡터의 마지막 두 바이트를 종결자로 오인하게 만든다.

이 모듈은 원소 안으로 `nread`할 수 없다. 와이어에는 십진 텍스트가 오고 원소에는 양자화된
바이트가 들어가서 크기도 내용도 다르기 때문이다. 그래서 종결자를 직접 쓴다.

### 헤더가 스스로를 설명한다

`dim`과 `quant`가 메타데이터 원소를 포함한 **모든** 원소의 헤더에 있다. 그래서 어느
원소를 집어도 자기 모양을 말할 수 있고, 이웃과 일치함이 구조적으로 보장된다. 반대로
`maxcount`와 `exptime`은 헤더에 없다. 엔진이 아이템 속성으로 이미 복제·영속화하는
값이라, 복사해 두면 `setattr`이 둘을 어긋나게 만들 수 있다.

바이트 8은 **레코드 종류**다. 0이면 벡터, 1이면 메타데이터. 하나의 프레이밍과 하나의
매직으로 두 종류를 담으므로 디코더의 분기가 하나로 끝난다.

## 5. 일관성: 규칙 하나

> **usearch 인덱스는 언제든 Map으로부터 재구성 가능한 캐시다.
> Map에 없으면 존재하지 않는다.**

재시작, 축출(eviction), TTL 만료, 복제 슬레이브가 전부 여기서 따라 나온다 — 네 가지
사례가 아니라 하나다.

- **재시작** — 그래프가 비어 있으므로 첫 검색이 Map에서 복구한다.
- **축출·만료** — Map 아이템이 사라지면 인덱스도 사라진다. 엔진이 알려준다.
- **복제** — Map 원소는 복제되지만 그래프는 복제되지 않는다. 그래서 승격된 노드는
  벡터를 다 갖고도 그래프가 없다. §6.

이 규칙에서 나오는 쓰기 순서가 전체를 관통한다. **모든 쓰기는 Map을 먼저 바꾸고
그래프를 나중에 바꾼다.** 그 순서 덕에 "그래프에는 있는데 Map에는 없다"는 상태가
구조적으로 생기지 않고, 그 역방향만 생긴다. 후자는 검색에서 잠시 안 보일 뿐 복구가
고친다.

### 아직 참이 아닌 곳

ArcVector를 거치지 않고 인덱스 키를 직접 건드리는 경로(`mop insert` 등)는 데이터를
바꾸면서 소유 토큰을 갱신하지 않는다. 그런 원소는 `AV` 매직이 없어 다음 복구 때
디코딩에서 걸리지만, 그 전까지는 검색에 보이지 않는다. 메타데이터 원소는 예외다 —
필드명에 공백이 들어 있어 프로토콜로는 만들 수도 읽을 수도 없다
([모듈-노트.md](모듈-노트.md#arcuselement)).

## 6. 복제와 인덱스 복구

전체 설계는 [design-replication-recovery.md](design-replication-recovery.md), 명령별
흐름은 [replication-flows.md](replication-flows.md)에 있다. 여기서는 구조에 미치는
영향만 적는다.

판단에 쓰는 값은 Map 메타데이터 원소의 `owner` 토큰 하나다. 그래프를 만들 때마다 새로
발급하고, 인덱스 객체도 자기가 어느 토큰으로 만들어졌는지 기억한다. `0`은 예약값이라
발급되지 않으므로 별도 필드 없이 "복구 중"을 표현한다.

| Map | 메모리 | 의미 | 처리 |
|---|---|---|---|
| 토큰 | 같은 토큰 | 이 그래프가 이 Map을 설명한다 | 정상 |
| 토큰 | 다른 값 | 다른 노드가 서빙했다 | 인수 → 복구 |
| `0` | `0` | 이 노드가 복구 중 | 읽기 `UNREADABLE`, 쓰기는 통과 |
| `0` | 토큰 | 복구하던 노드가 사라짐 | 인수 → 복구 |

구조상 중요한 결과가 셋이다.

**복구는 별도 스레드지만 쓰기를 하지 않는다.** 연결 없는 스레드에는 cookie가 없고 엔진의
쓰기 경로는 그것을 역참조한다. 그래서 복구에 필요한 두 번의 쓰기가 모두 워커에 남고,
비싼 부분(전체 순회와 그래프 구축)만 스레드로 나간다. 이것이 `registry/recovery`가
3단계로 쪼개진 이유다.

**복구 중에도 쓰기를 받는다.** 그 결과 하나의 그래프에 두 writer가 붙고, 누가 이기는지는
`AnnIndex`가 양쪽 모르게 정한다 — 복구는 id 맵이 모르는 id만 넣고, 삭제는 거기에
tombstone을 남겨 복구가 되살리지 못하게 한다. 두 판정 모두 삽입을 지키는 그 락 아래서
이뤄지므로 두 스레드의 도착 순서가 결과를 바꾸지 못한다.

**역할(master/slave)을 묻지 않는다.** `owner` 비교가 같은 질문에 답하기 때문이다.
자세한 근거는 [design-replication-recovery.md](design-replication-recovery.md) §4.1.

## 7. vtable은 단일 ABI가 아니다

`engine_interface_v1`은 **오프셋으로 호출된다.** 그런데 arcus에는 레이아웃이 하나가
아니다. 소스 트리가 일부를 정하고(`JHPARK_OLD_SMGET_INTERFACE`는 OSS `types.h`에 있고
EE에는 없다), `configure`가 나머지를 정한다(`ENABLE_REPLICATION`이 7개,
`ENABLE_MIGRATION`이 6개를 추가하며, 둘 다 `get_item_info`와 `get_elem_info` 앞에
놓인다). 잘못된 조합으로 빌드한 라이브러리는 그 오프셋에 앉아 있는 아무 함수나 호출한다.

이 크레이트가 호출하는 API 중 그 블록 안에 있는 것은 하나도 없다 — 복제·마이그레이션·
클러스터 API를 전혀 쓰지 않는다. 플래그가 바꾸는 것은 우리 호출 두 개가 *어디에
앉느냐*다.

런타임 판별자는 없다. `ENGINE_HANDLE::interface`는 모든 변종에서 1이고, 엔진은 기능
목록을 노출하지 않으며, 그런 걸 보고할 만한 것 자체가 정렬이 의심되는 그 vtable을 통해
도달된다.

그래도 두 가지 사실은 얻을 수 있고, 그 둘을 짝지으면 위험한 경우가 가려진다.

- **바인딩이 어느 트리에서 왔는지**는 빌드 시점에 헤더 *텍스트*로 정해진다. OSS 헤더는
  `rp_cmd`를 `#ifdef` 안에서조차 언급하지 않으므로, 어떤 define을 줬는지에 답이
  좌우되지 않는다.
- **데몬이 어느 트리인지**는 `server_version()`에서 온다. 이건 `SERVER_CORE_API`에
  있는데, `get_server_api`로 도달하는 다른 구조체이고 앞의 17개 멤버가 두 트리에서
  동일하다(EE는 뒤에 덧붙이기만 한다). 그래서 엔진 vtable이 아무리 어긋나 있어도 안전
  하게 호출할 수 있다. EE는 버전에 홀로 선 `E`를 찍고(`0.9.5-E-139`), OSS는 아니다
  (`1.16.1`).

검사는 셋이고 순서가 중요하다.

1. **교차 트리를 먼저 거부한다.** 바로 다음 호출에서 죽는 조합이기 때문이다 —
   `get_config`는 OSS 레이아웃에서 슬롯 60이고 EE에서는 `cachedump`다. *기능*이 아니라
   *트리*를 비교하는 것이 오탐을 없애는 핵심이다. 복제 없이 빌드한 EE 트리는 실재하는
   구성이고 복제 있는 것과 같은 버전을 보고하므로, 기능 기반 규칙은 그것을 거부해버린다.
2. **널 멤버를 거부한다.** arcus는 멤버를 미설정으로 출하하지 않으므로, 널이면 이
   바인딩이 서술하는 구조체가 아니라는 뜻이다.
3. **오작동하는 호출을 지목한다.** 널 검사에는 진짜 구멍이 있다. 잘못된 오프셋에서 읽은
   멤버는 대개 다른 진짜 함수에 떨어지므로 포인터는 유효하고 결과만 틀리다.

무엇이 걸리든 지문(데몬 버전과 생성된 레이아웃)을 로그에 남긴다. 어떤 검사도 예상하지
못한 경우까지 사람이 읽을 수 있게 하기 위해서다.

근본 해결은 여기 없다. EE가 멤버를 중간에 끼우지 않고 `errinfo` 뒤에 덧붙였다면 공통
접두부가 안정적이었을 것이고, 라이브러리 하나로 모든 빌드를 감당했을 것이다.

운영자용 설명은 [engine-abi.md](engine-abi.md)에 있다.

## 8. `EWOULDBLOCK`은 "실패"가 아니라 "기다려"다

동기 모드 복제 마스터에서 `rp_after_check`는 연산이 **이미 성공한 뒤에** 돌면서 호출자를
슬레이브 ack의 대기자로 등록한다(`replication.c`의 `rp_wait`). 이 코드는 "아직 답하지
말라"는 뜻이지 "일어나지 않았다"가 아니다.

이걸 실패로 읽는 것이 이 모듈이 데몬을 죽이던 방식이다. `put_elem`이 엔진이 방금 링크한
원소를 해제하고, `map_elem_free`가 `elem->linked == 0`을 단언하며 죽었다. `vcreate`는
방금 만든 Map을 `drop_map`했다.

아직 없는 것은 **기다림**이다. 내장 명령은 `c->ewouldblock`을 세우고 `conn_parse_cmd`가
`notify_io_complete`가 올 때까지 연결을 세워두는데, 확장은 그 필드에 손댈 수 없다.
그래서 응답이 슬레이브 ack보다 먼저 나간다. 즉 벡터 쓰기는 동기 마스터에서도 비동기
내구성으로 답한다.

## 9. usearch 스레드 컨텍스트 함정

usearch의 Rust 바인딩은 항상 `any_thread()`로 C++에 들어가고, 이것은 **고정 크기 풀**
에서 컨텍스트를 하나 꺼낸다. 풀이 비면 블록하지 않고 "Reserve capacity ahead of
insertions!"로 실패한다. arcus는 어떤 상수도 가정할 수 없는 수의 워커 스레드를 허용
하므로(`-t`가 64를 넘어도 경고만 한다), 정확성을 워커 수에 기댈 수 없다.

대신 usearch로 들어가는 모든 진입이 예약 컨텍스트 수만큼의 세마포어에서 허가를 받는다.

```
동시 진입 <= 허가 수 == 예약 컨텍스트 수   =>   pop은 실패할 수 없다
```

남는 워커는 실패가 아니라 대기한다.

## 10. 락

락은 두 개이고, 서로 독립이며, 역할이 다르다.

| 락 | 무엇을 배제하나 | 획득 방식 |
|---|---|---|
| 그래프 (`RwLock<Index>`) | 용량 재할당 대 나머지 전부 | 삽입·삭제·탐색은 **읽기**락 |
| id 매핑 (`RwLock<IdMap>`) | 매핑의 판정과 실행 | 삽입·삭제는 **쓰기**락, 탐색은 노드당 짧은 읽기락 |

그래프의 동시 변경은 usearch가 내부에서 처리한다. 그래서 그래프 락은 동시성 장치가
아니라 **재할당 배제 장치**다. 라이브러리가 이미 하는 일을 밖에서 한 번 더 잡으면
동시성만 깎인다.

**삽입과 삭제의 경합은 id 매핑 락 하나가 해소한다.** 두 연산 모두 판정과 실행을 쪼개지
않고 매핑 락을 배타적으로 쥔 채 수행하므로, "존재 여부를 확인한 뒤 삽입하기 전에 삭제가
끼어드는" 구간이 없다.

**락 획득 순서 규칙(그래프 → 매핑)은 정확성이 아니라 교착 회피용이다.** 탐색 술어가
그래프 락 아래에서 매핑 락을 잡으므로 나머지를 거기 맞췄다.

대가: 모든 삽입과 삭제가 매핑 락을 usearch 호출까지 쥐므로 **쓰기는 인덱스 단위로
직렬화된다.** id가 달라도 마찬가지다. 탐색은 매핑 락을 노드당 짧게만 잡아 서로 간섭하지
않는다.

## 11. 검색 경로

```
vsim
 └─ for_read           복구 중이면 UNREADABLE
 └─ ann.search(query, k, accept)
      └─ accept(key)   노드마다: id 조회 → Map에서 ATTR 읽기 → FILTER 평가
 └─ 히트마다           Map에서 원소를 다시 읽어 응답 구성
 └─ 걸러낸 뒤 개수를 세어 QUERY 헤더에 기록
```

그래프가 후보를 내고 Map이 결정한다. 모든 히트를 응답에 넣기 전에 Map에서 되읽으므로,
그래프는 아는데 Map에는 없는 원소는 결과에서 그냥 빠진다. 개수를 마지막에 세는 것도 같은
이유 — 헤더의 수와 실제 행 수가 어긋나지 않아야 한다.

술어는 `accept`가 되고, 방문 노드마다 한 번 호출되므로 싸야 한다. 첫 노드 이후로는
아무것도 할당하지 않는다.

## 13. 에러

핸들러는 `Result<Reply, Error>`를 돌려주고, 크레이트 루트의 한 곳이 그것을 ASCII 응답으로
바꾼다. `CLIENT_ERROR`인지 `SERVER_ERROR`인지는 에러 자신에게서 따라 나오므로 호출부가
정할 일이 없다.

| 상황 | 응답 |
|---|---|
| 잘못된 명령행, 범위 밖 인자 | `CLIENT_ERROR` |
| 인덱스 없음 | `NOT_FOUND` |
| 복구 중 읽기 | `UNREADABLE` (엔진의 `ENGINE_UNREADABLE`) |
| 레플리카에서의 쓰기 | `SERVER_ERROR` (엔진이 준 문구) |
| ABI 불일치 | `SERVER_ERROR engine ABI mismatch` |

통합 테스트에는 신선도 검사가 있다. `cargo test`는 데몬이 적재하는 `cdylib`을 다시 빌드
하지 않으므로, 소스가 라이브러리보다 새로우면 **패닉으로 거부한다.** 낡은 결과는 없는
결과가 아니라 틀린 결과이기 때문이다. `cargo build`를 먼저 돌려야 한다.
